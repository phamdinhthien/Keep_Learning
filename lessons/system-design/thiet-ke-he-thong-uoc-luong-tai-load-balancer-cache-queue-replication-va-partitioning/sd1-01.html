02. Bản đồ

Mỗi chặng trên request path đều có cách hỏng riêng

Request path là chuỗi chặng một request đi qua, từ trình duyệt tới nơi lưu dữ liệu rồi quay lại. Quy ước vẽ cho cả khóa: request đi từ trái sang phải, thành phần nào giữ state (dữ liệu mà request sau bắt buộc phải đọc lại) thì đánh nhãn hoặc đóng khung nổi bật. Lúc cao điểm có khoảng 300 req/s vào các endpoint cần đăng nhập, khoảng 1.500 người dùng đồng thời.

ChặngCách có thể hỏng
DNSTrả IP cũ sau khi chuyển hạ tầng, client kết nối vào server đã tắt
Load balancerHết instance healthy, hoặc chính proxy chạm trần → 502 Bad Gateway
App instanceRò rỉ bộ nhớ hết RAM, CPU chạm trần, process bị hệ điều hành tắt
DatabaseCạn connection pool, truy vấn giữ khóa lâu khiến request phía trước xếp hàng tới timeout
▸ Lần theo một request lúc 14:20
GET /orders/history   cookie: sid=… (tạo ở App A)
  DNS          # bỏ qua: IP đã có trong cache của trình duyệt
  LB           → round-robin chọn App B
  App B        → tra Map session trong RAM của B … không có sid
  Postgres     # không được gọi tới
  ← 401 Unauthorized

Không chặng nào "hỏng" theo nghĩa thông thường: DNS, LB, B và Postgres đều khoẻ. Request lỗi chỉ vì dữ liệu nó cần đang nằm ở chặng khác. (ví dụ minh hoạ dựa trên các bước của bài)

Điểm mấu chốt: khi gom session vào biến Map trong RAM của process, bạn đã biến tầng app thành nơi giữ state cục bộ, dù sơ đồ vẫn vẽ nó như tầng "chỉ xử lý".
03. Cơ chế

Xác suất rơi vào instance không có session là (N − 1) / N

Round-robin chia request lần lượt A → B → C → A… Bạn POST /login vào A, A tạo session ID, lưu vào Map trong RAM của nó và trả cookie. Bạn bấm GET /orders/history, request sang B; B tra Map của nó không thấy → 401 Unauthorized. Với N instance và tải chia gần đều, mỗi request cần đăng nhập chỉ có 1/N cơ hội rơi đúng máy.

Hình 2 — Round-robin A → B → C: chỉ 1 trong 3 lượt rơi đúng instance giữ session (bước 1–2 theo bài, bước 3–4 minh hoạ thêm)

N = 2 và N = 4 là mình tự tính từ cùng công thức để thấy xu hướng; bài chỉ dùng N = 3
▸ Phép tính — khớp với số đo trên dashboard
N = 3
P(hit)  = 1/3           ≈ 33,3%
P(miss) = 1 − 1/3 = 2/3 ≈ 66,7%

Tính toán : 300 req/s × 2/3 ≈ 200 req/s trả 401
Đo thực tế: 63%–65%          ≈ 189–195 req/s   # lệch vài % do keep-alive, phân bố người dùng

Lỗi này có từ lúc chỉ chạy 1 instance: mỗi lần deploy ban đêm, process khởi động lại xoá trắng Map, cả ~1.500 người online bị đăng xuất. Chỉ lác đác 1–2 ticket nên không ai để ý. Lên 3 instance không tạo ra lỗi mới, mà biến lỗi tiềm ẩn mỗi tuần thành lỗi mỗi phút.

04. Cách sửa

Đưa session ra session store dùng chung để instance không còn giữ state

Session store là kho đặt ngoài process app (thường là Redis hoặc một bảng trong database) mà instance nào cũng đọc được. Request rơi vào instance nào thì instance đó cũng nhận ra người dùng; thêm hay bớt instance không còn làm ai bị đăng xuất.

Hình 3 — Ba instance bình đẳng; state chỉ còn ở Redis và Postgres
▸ Code — middleware xác thực đổi từ RAM sang Redis
// Trước: đọc từ RAM của chính instance
// const session = inMemorySessionMap.get(sessionId);

// Sau: đọc từ session store mà mọi instance cùng trỏ tới
const sessionData = await redisClient.get(`session:${sessionId}`);
if (!sessionData) {
  return response.status(401).json({ error: "Unauthorized" });
}
const session = JSON.parse(sessionData);

Phạm vi bảo đảm: session không mất khi đổi số instance. Một instance tắt đột ngột đúng lúc đang xử lý dở thì request dở dang đó vẫn có thể lỗi.

Tách session có giá: thêm một round trip, thêm một điểm lỗi

PHẢI CHỊU THÊM

  • Mỗi request cần đăng nhập thêm ≥ 1 round trip, khoảng 0,5 ms trong cùng datacenter
  • Redis sập thì mọi thao tác cần đăng nhập đều lỗi, dù app vẫn khỏe
  • Thêm một thành phần phải theo dõi RAM, cấu hình, dự phòng

CHỌN KHO NÀO

  • Redis: rất nhanh, có sẵn TTL để session tự hết hạn, nhưng là service riêng phải chăm
  • Bảng sessions trong Postgres: không thêm service, nhưng Postgres gánh thêm ~300 query/s lúc cao điểm
▸ Số đo trước / sau khi dời sang Redis
Dung lượng : 1.500 phiên × ~1 KB = ~1,5 MB RAM trên Redis

Khi nào chưa cần dời? Chỉ chạy 1 instance, tài nguyên còn dư, và việc mọi người bị đăng xuất mỗi lần deploy ban đêm không ảnh hưởng cam kết kinh doanh: session trong RAM vẫn là cách đơn giản và rẻ nhất.
05. Phân loại

Mất dữ liệu này thì kết quả sai, hay chỉ chậm hơn?

Stateless không có nghĩa là xoá mọi dữ liệu tạm khỏi code. Hệ thống luôn cần state; việc cần làm là dời state từ nơi không được giữ (RAM của process có thể bị tắt, nhân bản tuỳ ý) sang backing service chuyên dụng. The Twelve-Factor App (phần "Processes") gọi đây là process stateless, share-nothing.

Hình 4 — Câu hỏi phân loại: thiếu nó thì kết quả sai, hay chỉ chậm hơn?

STICKY SESSION

  • Gắn người dùng với một instance cố định qua cookie hoặc IP
  • Triệu chứng biến mất, nhưng state vẫn nằm trong instance

COOKIE ĐÃ KÝ

  • Dời toàn bộ dữ liệu phiên ra trình duyệt, ký số trong cookie
  • Instance không cần tra kho nào
▸ Trường hợp thực tế — ảnh đại diện 404
POST /avatar            → LB → App A → ghi /uploads/user1.jpg # đĩa local của A
GET  /avatar/user1.jpg  → LB → App B → /uploads/ của B không có file → 404 Not Found

GET  /categories        → LB → App B → cache trong RAM của B trống
                                       → đọc Postgres, lưu RAM → 200 # chậm hơn vài ms

Hai request đầu theo bài; request thứ ba minh hoạ trường hợp in-process cache mà bài mô tả (danh mục sản phẩm, cấu hình hiển thị).
