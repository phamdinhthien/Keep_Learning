01. Latency trung bình

Số trung bình trả lời "tính chung mỗi request mất bao lâu" — còn khách hỏi "tôi phải chờ bao lâu"

Latency của một request = thời gian từ lúc API nhận request tới lúc trả xong response. Panel "trung bình" cộng latency của mọi request thành công (2xx) trong một phút rồi chia cho số request. Vấn đề nằm ngay trong phép chia: thời gian chờ của một nhóm nhỏ bị chia đều cho tất cả. Nhóm chậm chỉ chiếm 1% số request nhưng chiếm 20% tổng latency — vậy mà kết quả chỉ nhích từ 100 lên 124 ms, còn cách ngưỡng đỏ gần 380 ms. Và nhìn con số 124 ms, bạn không biết nhóm chậm có bao nhiêu request, chờ 500 ms hay 3 giây.

Hình 2 — 1% request mang 20% thời gian chờ, nhưng phép chia làm nó gần như biến mất
▸ Ví dụ — phép chia của phút 21:00 (số trong bài)
Nhóm nhanh:   17.730 request × 100 ms   = 1.773.000 ms
Nhóm chậm:       180 request × 2.500 ms =   450.000 ms
Tổng latency:                             2.223.000 ms
Trung bình:   2.223.000 ms ÷ 17.910 request ≈ 124 ms   # không có nhóm chậm: 100 ms

Trong cùng phút, access log ghi POST /orders 200 3240ms và POST /orders 503 3010ms. Dòng 503 thậm chí không được tính vào 124 ms, vì panel chỉ lấy request 2xx.

02. Percentile

p50, p95, p99 — mỗi percentile chỉ thẳng vào một nhóm request ở cuối danh sách

Lấy latency của mọi request thành công trong phút, xếp từ nhanh tới chậm. p50 (median) là giá trị đứng giữa: một nửa xong nhanh hơn. p95 là giá trị ở vị trí 95%, p99 ở vị trí 99%. Công cụ monitoring có thể nội suy giữa hai giá trị liền kề, nhưng ý nghĩa không đổi: percentile trả lời "bao nhiêu % request xong dưới một mốc thời gian". p50 và p95 mô tả phần đông; chúng không nói gì về 1% chậm nhất — muốn biết nhóm đó chờ bao lâu thì phải nhìn p99.

Hình 3 — p50 và p95 nằm ở phần "bằng phẳng"; chỉ p99 chạm vào đoạn cong vút ở cuối
GiờTrung bìnhp50p95p99

Đọc bảng: trung bình chỉ tăng 90 → 124 ms (+38%), p99 tăng 320 → 2.000 ms (gấp hơn 6 lần). p50 đứng yên 70 ms cả buổi — một nửa khách vẫn thấy API nhanh như lúc 19:00.
▸ Ví dụ — "1%" nghe ít, nhưng là bao nhiêu người?
ĐỌC NHẦM"p99 = 2 s, chắc chỉ vài khách xui xẻo."
ĐỌC ĐÚNG1% × 17.910 = ~180 request mỗi phút — đúng vào phút đông khách đặt hàng nhất.

Edge case — ít request: nếu một phút chỉ có 50 request, p99 gần như chỉ là request chậm nhất trong phút đó; một request lạc lõng cũng đủ làm p99 nhảy vọt.

# Ví dụ minh hoạ thêm (Prometheus, không có trong bài):
# p99 của POST /orders thành công, tính từ histogram latency từng request
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket{
    route="/orders", method="POST", code=~"2.."}[1m])))

Percentile phải tính từ latency đo được của từng request (histogram/bucket). Từ tổng latency + số request chỉ ra được trung bình, không bao giờ suy ra được p99.

03. Throughput

Throughput tăng không có nghĩa là phục vụ tốt hơn — nó có thể đi cùng p99 tăng vọt

Throughput = số request API xử lý xong mỗi giây (tính mọi request, kể cả /health). Throughput nói hệ thống làm xong bao nhiêu việc; latency nói mỗi việc mất bao lâu. Hai số có thể đi theo hai hướng, nên cần hai panel. Throughput có ý nghĩa nhất khi đặt cạnh số request đang tới mỗi giây — một số khác, phải đếm riêng. Khi request tới nhiều hơn request xử lý xong, phần chênh lệch không biến mất: nó nằm lại chờ, và hàng chờ dài ra.

Hình 4 — Cột cao nhất (throughput) đúng lúc đường p99 vọt lên cao nhất

04. Error rate

Error rate = lỗi ÷ một tập request đã chọn — đổi mẫu số là đổi luôn kết luận

Cùng 90 lỗi trong cùng một phút, nhưng chia cho 18.000 request của cả API (giỏ hàng, sản phẩm, xem đơn, cả /health) thì ra 0,5%; chia cho 1.200 lần POST /orders thì ra 7,5% — gấp 15 lần. Các endpoint đọc gần như luôn thành công nên chúng pha loãng lỗi của thao tác đặt hàng. Thêm nữa, error rate chỉ cho biết lỗi xảy ra thường xuyên tới đâu, không cho biết khách chờ bao lâu rồi mới nhận lỗi — việc đó cần một panel latency riêng cho request lỗi.

Vì sao lại là 3 giây? API chờ một connection tối đa 3 giây, quá mốc đó thì trả 503. Đặt hàng ghi nhiều bảng trong một transaction nên giữ connection lâu nhất — mọi 503 lúc 21:00 đều rơi vào thao tác này. Tức là request lỗi đang chờ connection, không phải chờ CPU.

05. Utilization vs Saturation

CPU mới 45%, nhưng request đã phải xếp hàng chờ connection

Utilization trả lời "tài nguyên đang bận tới mức nào" — với CPU là % thời gian CPU bận, với pool là số connection đang dùng trên 20. Saturation trả lời câu khác: "có bao nhiêu việc đang xếp hàng vì tài nguyên đã dùng hết" — với pool là số request đang chờ connection, hoặc thời gian chờ. CPU và connection pool là hai tài nguyên khác nhau: request đang chờ connection gần như không tốn CPU, nên CPU thấp không nói gì về hàng chờ ở pool. Và utilization 100% chưa phải saturation — saturation bắt đầu khi có request phải chờ, kể cả khi hàng chờ đứng yên.

Hình 8 — Hàng chờ ở pool tăng 0 → 8 → 25 trong khi CPU chỉ nhích 30 → 45%

UTILIZATION

"đang bận tới mức nào?"
  • CPU: % thời gian bận
  • Pool: connection đang dùng / 20
  • 100% vẫn có thể phục vụ ngay mọi request

SATURATION

"bao nhiêu việc đang xếp hàng?"
  • Pool: số request chờ connection hoặc thời gian chờ
  • Bắt đầu khi có request phải chờ — kể cả hàng chờ ổn định ~8
  • Request chờ quá 3 s → 503
USE method (Brendan Gregg): nhìn mỗi tài nguyên qua Utilization · Saturation · Errors để tìm bottleneck. Dashboard mới chỉ cho thấy triệu chứng và tài nguyên request đang chờ; vì sao pool bị dồn việc thì phải lần theo từng chặng mới trả lời được.
▸ Trường hợp thực tế — kỹ sư trực lúc 21:00
CHỈ CÓ PANEL CPU"CPU 45%, còn rảnh hơn một nửa → API chịu tải tốt, hệ thống bình thường."
CÓ PANEL SATURATIONPool 20/20 + ~25 request đang chờ; request nào chờ quá 3 s nhận 503 → 90 lần/phút.

06. Checklist

Bốn câu hỏi — mỗi câu cần ít nhất một panel riêng trước khi nói "hệ thống vẫn ổn"

Mỗi số liệu trên dashboard nên gắn với một câu hỏi rõ ràng. Câu nào dashboard của bạn chưa có panel trả lời, đó là panel cần thêm trước. Kèm theo hai việc bắt buộc: ghi rõ trên mỗi panel tập request và khoảng thời gian nó tính (vài tháng sau không ai nhớ panel lỗi có tính /health không), và tính percentile từ latency từng request.

  • 1
    Bao nhiêu % request xong dưới một mốc thời gian?
    → panel p50 / p95 / p99 của request thành công. Latency trung bình không trả lời được.
  • 2
    Mỗi giây xử lý xong bao nhiêu request, so với số request đang tới?
    → panel throughput (vế đầu) + panel đếm riêng request tới mỗi giây (vế sau).
  • 3
    Lỗi được tính trên tập request nào?
    → error rate ghi rõ mẫu số (vd chỉ POST /orders) + panel latency của request lỗi.
  • 4
    Request đang xếp hàng chờ ở tài nguyên nào?
    → panel saturation của tài nguyên chính, vd số request chờ connection. % CPU không trả lời được.
