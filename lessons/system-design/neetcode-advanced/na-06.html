Google Drive lưu hàng nghìn petabyte: file chia thành block 4 MB trong object storage, deduplicate bằng hash nội dung

Upload, download, xoá file và thư mục. Ưu tiên availability và reliability; tiết kiệm chi phí lưu trữ là bài toán chính.

01. Bối cảnh 00:00–01:00

Cloud storage cho người dùng: upload, download, xoá, sửa, chia sẻ, phân quyền, tổ chức theo thư mục — đơn giản, cái khó là quy mô

Google Drive, Dropbox, Microsoft OneDrive: lưu file trên cloud. Cốt lõi: upload, download, remove. Ngoài ra sửa file (vd Google Doc), chia sẻ, quản lý permissions (ai được tải, sửa, xoá), sắp xếp bằng folders theo hierarchy. Có vẻ đơn giản, nhưng vấn đề nằm ở quy mô.

▸ Ví dụ của nguồn — tính năng của Drive
Cốt lõiUpload, download, xoá file.
Mở rộngSửa, chia sẻ, phân quyền, thư mục.
02. Yêu cầu và quy mô 01:00–05:20

200 triệu user × 15 GB = 3000 PB, còn phải replicate nhiều vùng; throughput và latency không phải vấn đề chính — availability và reliability mới là

Phạm vi: upload, download, xoá, có folder; nói qua về sửa file (phức tạp nhất); bỏ chia sẻ và phân quyền. 200 million user (Drive thật chắc hơn một tỷ), 50 million DAU. Mỗi user 15 gigabytes miễn phí — đúng như Google Drive. Một nhóm nhỏ trả tiền thêm (1 TB, 10 TB, 100 TB), nhưng đây là sản phẩm cho người dùng phổ thông nên giả định trung bình 15 GB (đa số không dùng hết).

Tổng dung lượng tính theo tổng user chứ không phải DAU: 15 GB × 1 triệu = 15 PB; × 200 → 3000 petabytes = 3 exabytes. Nhớ đơn vị tới peta là đủ, viết 3000 PB cũng được. File không được mất → replicate ở nhiều nơi trên thế giới, không chỉ một zone (lỡ thiên tai phá huỷ một data center), ít nhất 3 lần → còn lớn hơn 3000 PB.

Throughput: mỗi người upload 2 file/ngày, mỗi file ~10 megabytes; tỷ lệ đọc:ghi 2 : 1 → 4 file tải về. Ở đây throughput và latency không phải vấn đề lớn — tải chậm vài giây không sao, không như xem YouTube. Quan trọng nhất là availability (cần file quan trọng mà không tải được thì chẳng ai dám dùng) và reliability (file không được tự dưng biến mất).

Transcript có chỗ nói "15 petabytes is actually 3 exabytes"; ý đúng là 3000 PB = 3 EB.
▸ Ví dụ của nguồn — phép nhẩm
15 GB × 1.000.000    = 15 PB
15 PB × 200          = 3.000 PB = 3 EB
× ≥3 bản sao nhiều vùng → còn lớn hơn nữa
03. Metadata 05:20–06:40

Lưu hai thứ: file và metadata; metadata vào NoSQL dạng key-value như MongoDB hay DynamoDB — không phải nút thắt

File có thể là bất cứ định dạng gì (text thì bỏ vào database được, nhưng còn ảnh, video…), nên cần chỗ linh hoạt hơn. Metadata (của user và của file) vào database — SQL hay NoSQL không quan trọng; chọn NoSQL vì đơn giản, ít join, dùng như key value store: MongoDB hay AWS DynamoDB. Không phải nút thắt — khối dữ liệu khổng lồ là chính các file.

▸ Ví dụ của nguồn — hai loại dữ liệu
MetadataUser, tên file, chủ sở hữu, tham chiếu → KV store.
Nội dung fileMọi định dạng, khối lượng khổng lồ → kho lưu bền.
04. Distributed file system hay object store 06:40–10:20

File system là cây, sửa file được nhưng scale khó; object store phẳng như hashmap, scale và replicate sẵn, nhưng file bất biến — chọn object store

Hai lựa chọn bền vững: distributed file system như Hadoop Distributed File System, hoặc object store. Cả hai dùng được nếu bảo vệ được lý do. File system lưu theo hierarchy — như một tree (không nhất thiết binary): root, rồi folder như bin, abc, trong đó có file như x.txt, folder lồng nhau. Trên disk cũng tổ chức tương tự, duyệt con của một folder rất dễ. Drive có folder nên cấu trúc cây có ích, nhưng scale file system phân tán phức tạp hơn và kém scalable; object store thì scale gần như miễn phí, nhất là dịch vụ ngoài như AWS S3, Google Cloud Storage, Azure (blob store).

File system cho sửa file; object store thì file immutable — chỉ xoá rồi tạo mới. Không tập trung vào sửa, và có cách vòng: file text nhỏ thì nạp vào memory để sửa; ảnh, video có khi không cho sửa. Object store là cấu trúc phẳng: folder trên S3 là ảo giác, chỉ nằm trong tên — bin/a và bin/b; mở "bin" là liệt kê mọi file có prefix đó. Giống hash map: tên duy nhất là key. Object store còn cho sẵn reliability, availability, multi region replication → chọn object store.

Hình 2 — File system so với object store
▸ Ví dụ của nguồn — folder "bin" trên S3
bin/a     // "bin/" chỉ là prefix
bin/b     // mở "bin" = lọc các key bắt đầu bằng "bin/"
05. Thiết kế cấp cao 10:20–12:40

App server (sau load balancer) ghi file vào object storage và metadata vào KV store; object storage để riêng tư, chỉ app server truy cập

User upload → application server (qua load balancer, server nào cũng được) → lưu file vào object store, đồng thời lưu metadata kèm tham chiếu tới file. Đọc: app server lấy metadata, rồi trả file từ object store. Có thể thêm caching layer, nhưng hiếm có file nào được đọc nhiều tới vậy, nên cache không quan trọng ở bài này.

Media trên object storage thường không cần phân quyền, hay phát qua CDN. Ở đây là file cá nhân, chỉ chủ sở hữu được xem, nên cấu hình object store không public: chỉ app server của mình truy cập. App server kiểm tra quyền (qua KV store và authentication token của user) rồi mới đọc file và trả về.

▸ Ví dụ của nguồn — tải một file
  1. Client gửi request kèm token.
  2. App server tra KV store: file của ai, user có quyền không.
  3. Có quyền → app server đọc từ object storage riêng tư và trả về.
06. Block-level storage 12:40–14:00

Lưu 3000 PB trên S3 rất tốn tiền khi cho miễn phí; chia file thành block cố định khoảng 4 MB, KV store giữ danh sách block để ghép lại

S3 chắc chịu được quy mô này nhưng rất tốn tiền, nhất là khi cho miễn phí. Kỹ thuật: block level storage. File upload được chia thành block kích thước cố định, cỡ megabyte — bốn megabyte là hợp lý. Các block lưu trong object storage; đọc file thì ghép lại từ các block, dựa vào dữ liệu trong KV store: document gồm tên file (vd "ABC"), user ID, và tham chiếu tới mọi block.

Transcript nghe "lock level storage"; đúng là block level storage.
▸ Ví dụ của nguồn — document một file
{ name: "ABC", userId: "...", blocks: ["…", "…", "…"] }  // mỗi block ~4 MB

Cú pháp document là minh hoạ thêm; ba thành phần lấy từ video.

07. Deduplication và content addressable storage 14:00–18:40

Block trùng chỉ lưu một lần, tốt nhất ở mức toàn cục; nhận ra trùng bằng ID tạo từ hash nội dung; upload hỏng giữa chừng thì không phải tải lại phần đã có

Lợi ích lớn nhất của block: deduplication. Một block của file này giống hệt block của file khác → không lưu lại, chỉ tham chiếu (tiết kiệm 4 MB trong ví dụ, nhiều hơn ở quy mô lớn). Tốt hơn nữa là làm ở mức global, cho mọi user: file người khác đã upload thì không lưu lại, và kể cả file khác nhau nhưng có block giống nhau cũng không lưu trùng — tiết kiệm rất nhiều storage, tức là tiền.

Không có block thì user xoá file là xoá hết. Với dedup toàn cục, có lẽ không bao giờ xoá block ngay, vì block có thể đang được user khác dùng — xoá thì họ không ghép lại file được. Nếu dedup theo user, có thể lưu count cho mỗi block trong KV store: xoá file thì giảm count, về 0 thì xoá block. Đây là kỹ thuật dùng thật trong ngành.

Làm sao biết block đã tồn tại mà không đọc hết object store? Tạo ID duy nhất từ nội dung block: block giống nhau cho cùng ID; ID có trong KV store tức là đã lưu, và ID đó là tham chiếu tới block trong object store. Gọi là content addressable storage. Đó cũng là lý do khó sửa block: sửa nội dung thì phải tạo lại hash, và có thể làm hỏng dữ liệu người khác — nên block (và object storage nói chung) là bất biến. Thêm một lợi ích: upload 10 gigabytes hỏng ở 5 gigabytes, lần sau app server tra KV store thấy 5 GB đầu đã có, không cần lưu lại.

Hình 3 — Block-level storage và deduplication
▸ Ví dụ của nguồn — hai file có block giống nhau

File A = [h1, h2, h3], file B = [h1, h4, h3]: chỉ lưu h1, h2, h3, h4 — bốn block thay vì sáu.

Tên block và cách đặt là minh hoạ thêm cho ý "block giống nhau chỉ lưu một lần".

08. Folder và garbage collection 18:40–20:50

Folder không chiếm block nên chỉ cần lưu trong KV store với con trỏ hai chiều; block không còn ai tham chiếu thì một garbage collector định kỳ dọn

Folder không có data block nên không cần lưu trong object storage — chỉ cần metadata trong KV store: mỗi folder có tham chiếu tới mọi con, thuộc về một user; folder tham chiếu tới file, file tham chiếu tới các block. Đi ngược từ file lên folder: mỗi document file có tham chiếu tới folder → con trỏ hai chiều; folder lồng nhau cũng vậy.

Xoá file không xoá block ngay; muốn biết block còn ai dùng thì có thể phải quét cả KV store — không muốn làm mỗi lần xoá. Thêm một garbage collection service chạy bất đồng bộ, vd mỗi một giờ: quét KV store, tìm block không còn được tham chiếu, xoá khỏi object storage. Vừa có dedup vừa không giữ block thừa.

▸ Ví dụ của nguồn — con trỏ hai chiều
folder "Docs" → children: [file "cv.pdf", folder "2024"]
file "cv.pdf" → parent: "Docs", blocks: [...]

Tên folder và file là minh hoạ thêm.

09. Load balancer dự phòng với heartbeat 20:50–23:20

Load balancer active gửi heartbeat tới ZooKeeper; quá 10 giây không có heartbeat thì load balancer dự phòng nhận traffic

Về reliability: load balancer sập thì sao? Cần một load balancer khác thay thế. Biết nó sập nhờ heartbeat: load balancer active liên tục gửi heartbeat tới một kho dữ liệu, phổ biến là ZooKeeper — không hẳn database, mà là key-value store highly available (khác DynamoDB dùng cho metadata), chuyên dùng để điều phối distributed system, rất fault tolerant; được dùng với Hadoop, Spark, Kafka. Load balancer dự phòng đọc ZooKeeper; quá 10 giây không có heartbeat → coi như load balancer đầu đã sập, chuyển toàn bộ traffic sang mình.

Còn bỏ ngỏ: sửa file — không sửa được block trong object store, nên phải xử lý ở chỗ khác rồi thêm block mới cho dữ liệu mới. Bài đã phủ phần quan trọng nhất: lưu dữ liệu hiệu quả.

▸ Ví dụ của nguồn — failover
  1. LB active gửi heartbeat đều đặn tới ZooKeeper.
  2. LB dự phòng theo dõi ZooKeeper.
  3. 10 giây không thấy heartbeat → LB dự phòng nhận toàn bộ traffic.

Năm câu hỏi

Tổng dung lượng với 200 triệu user, 15 GB mỗi người?

3000 PB = 3 EB, chưa tính bản sao. (→ 02)

Vì sao chọn object store thay vì HDFS?

Scale và replicate sẵn, nhiều vùng; không cần sửa file tại chỗ. (→ 04)

Làm sao ghép lại một file từ block?

Document trong KV store giữ danh sách tham chiếu tới các block theo thứ tự. (→ 06)

Content addressable storage là gì?

Dùng hash của nội dung làm địa chỉ/ID của block, nên block giống nhau có cùng ID. (→ 07)

Load balancer dự phòng biết khi nào cần thay thế?

Khi quá khoảng 10 giây không thấy heartbeat của LB active trong ZooKeeper. (→ 09)
