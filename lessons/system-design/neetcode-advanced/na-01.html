01. Bối cảnh 00:00–02:40

Rate limiter ngăn user hay bot gửi quá nhiều request trong một khoảng thời gian — vì bảo mật, chi phí, availability hay trải nghiệm, tuỳ ngữ cảnh

Dạng đơn giản nhất: mật khẩu điện thoại 4 chữ số, nhập sai thì chỉ được thử lại vài lần, ví dụ 3 lần mỗi giờ, rồi bị khoá. Mục đích là bảo mật: mật khẩu ngắn thì brute force được, đến đứa trẻ thử ngẫu nhiên mãi cũng mở được.

YouTube giới hạn upload khoảng 20 video trong 24 giờ. Không phải vì bảo mật mà vì chi phí lưu trữ, và cả availability: upload vô hạn có thể chiếm hết storage, làm sập YouTube với mọi người. Còn comment: một người viết một triệu comment mỗi ngày? Bot trong comment là chuyện trải nghiệm người dùng và bảo mật. Nhưng comment có nên dùng cùng giới hạn với upload không? Ngữ cảnh quyết định — có thể cho 100 comment mỗi ngày.

▸ Ví dụ của nguồn — cùng là giới hạn, khác lý do
Trường hợpGiới hạnLý do chính
Mật khẩu điện thoại~3 lần thử/giờBảo mật, chống brute force

02. Functional requirements 02:40–08:40

Rate limiter bảo vệ nhiều API backend nên phải là service riêng dùng chung; khi vượt giới hạn thì throttle và trả 429

Câu đầu tiên nên hỏi: thiết kế cho backend API? Đó là nơi rate limiter thường nằm, nhất là trong distributed system. Chỉ cho một API thôi? Nếu vậy cách dễ nhất là cài ngay trong code microservice, giữ rule và số request trong một hash map. Nhưng thường câu trả lời là không: rate limiter cần tái sử dụng cho nhiều microservice, nên phải là một service riêng.

Thêm một lý do: mỗi API (vd upload API, comments API) có nhiều instance. Upload video thứ nhất vào instance 1, video thứ hai vào instance 2 — mỗi instance nghĩ bạn mới upload một video, nên vô tình lách được giới hạn. Rate limiter dùng chung thì biết bạn đã upload hai video.

Hình 2 — Rate limit trong từng instance so với service dùng chung

Khi đạt giới hạn: không cho API xử lý, báo user đang bị throttled, và nên cho biết phải chờ bao lâu (vd 24 giờ). Với HTTP, đây là lỗi nhóm 400 vì lỗi ở client, server vẫn chạy tốt; mã cụ thể là 429 (Too Many Requests).

Client-side rate limiting (JavaScript, app mobile) dễ làm và nên có, nhưng không đủ: user có thể reverse engineer request và gọi thẳng endpoint public bằng curl, không cần dùng app. Không có rate limiter thật, YouTube đã bị đánh sập từ lâu.

Định danh user thế nào? User ID nếu bắt buộc đăng ký (YouTube cần tài khoản để upload, comment), nhưng site khác thì không. Rate limiter phục vụ nhiều ứng dụng (vd Google dùng cho cả YouTube và Google Search) nên nên hỗ trợ nhiều loại ID, chung nhất là IP address — có đánh đổi nhưng không đi sâu.

▸ Ví dụ của nguồn — response khi bị chặn
HTTP/1.1 429 Too Many Requests
// kèm thông tin: chờ thêm bao lâu nữa (vd tới hết 24 giờ)

Dạng response là minh hoạ thêm; nguồn nói mã 429 và nên cho biết thời gian chờ.

03. Non-functional requirements 08:40–14:00

Latency là quan trọng nhất; dữ liệu đếm cho một tỷ user khoảng 132 GB — vừa bộ nhớ; khi rate limiter sập thì nên fail open

Latency: mọi request giờ có thêm overhead của rate limiter, nên phải thấp nhất có thể — không thể cộng thêm 1 giây vào mỗi request; muốn như thể rate limiter không tồn tại. Throughput: nhiều service dùng chung nên phải horizontally scalable.

Storage: rule không phải nút thắt — một ứng dụng như YouTube có bao nhiêu rule, 10, 100, 1000? Còn số user thì lớn: mỗi user có key (IP 4 byte) và số request (ước dư 128 byte) → 132 byte/user. Với một tỷ user → 132 tỷ byte = 132 GB (tỷ là giga). Kết luận: vừa trong bộ nhớ.

Availability: lý tưởng là five nines. Nhưng nếu rate limiter sập? Fail open: hệ thống chạy như thể không có rate limiter. Fail closed: cả hệ thống ngừng, trả lỗi 500. Fail open thì đa số user dùng bình thường, chỉ một nhóm nhỏ lạm dụng lọt qua — sập 5 phút cho spam comment chắc không phải tận thế. Fail closed thì ảnh hưởng cả một tỷ user. Thường chọn fail open, tuỳ ứng dụng.

Nên lấy đủ yêu cầu trong 5 tới 10 phút đầu (vẫn có thể hỏi chi tiết nhỏ sau). Lý do: sai yêu cầu thì thiết kế sai, cuối buổi không còn thời gian làm lại.

▸ Ví dụ của nguồn — ước lượng bộ nhớ
(4 byte IP + 128 byte đếm) × 1.000.000.000 user
= 132.000.000.000 byte ≈ 132 GB  → vừa bộ nhớ
04. Thiết kế cấp cao 14:00–17:30

Request đi qua rate limiter trước; rule nằm trong database bền vững, số đếm nằm trong KV store bộ nhớ như Redis

Request của user chạm rate limiter đầu tiên — nó như một reverse proxy, không chứa logic ứng dụng, chỉ quyết định có chuyển request tới API hay không, để API không bị quá tải.

Rule do developer định nghĩa (vd 20 video/24 giờ), cần persistent — có thể sửa nhưng không được mất — nên để trong database; SQL hay NoSQL không quan trọng vì số rule ít. Số request mỗi user lưu trong in-memory key value store như Redis hay Memcached: rate limiter vừa đọc vừa ghi (upload lần đầu → ghi "1 video trong 24 giờ"), ghi thường chậm hơn đọc, bộ nhớ nhanh hơn disk, và dữ liệu vừa bộ nhớ.

Được phép → chuyển tới API, API trả qua rate limiter về client. Bị chặn → trả 429, API không hề biết có request. Người phỏng vấn có thể góp ý cách khác: gửi thẳng tới API và để API tự đọc KV store, có khi không cần rule — nhưng ở đây ta muốn thiết kế tái sử dụng được.

▸ Ví dụ của nguồn — upload một video
  1. Rate limiter đọc rule upload: 20 video / 24 giờ.
  2. Đọc số đếm của user trong KV store.
  3. Dưới giới hạn → tăng đếm, chuyển tới Upload API; đủ rồi → trả 429.
05. Thuật toán 17:30–23:20

Fixed window rẻ và đơn giản nhưng để lọt đợt dồn ở mép cửa sổ; sliding window chính xác hơn nhưng phải lưu timestamp từng request

Rule "100 requests per minute" nghĩa chính xác là gì? Fixed window: theo đồng hồ, mỗi phút (12:01, 12:02, 12:03…) cho tối đa 100 request; sang phút mới thì cho 100 nữa. User gửi 100 request ngay trước 12:02 và 100 ngay sau → 200 request trong khoảng 2 giây. Về lâu dài vẫn khá chính xác (sau đó phải chờ ~59 giây), nhưng có thể ta không muốn spike như vậy. Ưu điểm: không cần biết request xảy ra giây nào, chỉ lưu phút và count.

Sliding window: mỗi request xét đúng 60 giây gần nhất, cửa sổ trượt mỗi giây — không bỏ qua mọi thứ trước phút hiện tại như fixed window. Gần như luôn đảm bảo 100/phút, nhưng phải lưu timestamp từng request: Unix timestamp 32 bit = 4 byte, 100 request → 400 bytes mỗi user, có thể hơn tuỳ rule. Đọc thì chỉ lấy 60 giây cuối, có thể xoá phần cũ để tiết kiệm chỗ — thêm một thao tác. Với Redis làm bằng sorted set: một key ánh xạ tới tập giá trị có thứ tự, sắp theo timestamp.

Hình 3 — Fixed window so với sliding window

Còn nhiều thuật toán khác, thiên về kiến thức chuyên ngành: token bucket (dùng tốc độ nạp lại — refill rate — thay cho cửa sổ) và sliding window counter (cân bằng giữa fixed và sliding window). Nói được các đánh đổi như trên đã là đủ.

Transcript có chỗ nói "unlike the sliding window, where we just disregard everything before this minute" — ý đúng là fixed window mới bỏ qua mọi thứ trước phút hiện tại.
▸ Ví dụ của nguồn — mép cửa sổ
12:01:59  100 request  // cửa sổ 12:01 → hợp lệ
12:02:00  100 request  // cửa sổ mới 12:02 → hợp lệ
// fixed window: 200 request trong ~2 giây đều lọt
// sliding window: request thứ 101 trong 60 giây gần nhất bị chặn
06. Schema 23:20–25:40

KV store: key là user ID hay IP, value là count, dùng EXPIRE để tự reset; bảng rule có id, api, op, time unit và số request

Trong bộ nhớ (fixed window): key là user ID hoặc IP → count. Mỗi request thì tăng count (++). Count thuộc phút 12:01, sang phút mới phải reset: Redis có expire, đặt hết hạn mỗi 60 giây hoặc đúng lúc 12:02, dữ liệu tự dọn và đếm lại từ 0 — lý do nữa khiến fixed window dễ làm.

Bảng rule trong database: id (string) để rate limiter tìm đúng rule, vd rule upload video; api — chuyển request tới API nào; op — endpoint/thao tác nào (upload, comment…); time unit (giây, phút, giờ; có thể lưu string để rate limiter tự diễn giải); requests — số request cho phép (integer).

▸ Ví dụ của nguồn — 100 request mỗi phút
// in-memory
"ip:1.2.3.4"  →  count = 37    // EXPIRE lúc 12:02

// rules DB
{ id: "...", api: "...", op: "...", timeUnit: "minute", requests: 100 }

Giá trị key, IP và count là minh hoạ thêm; các trường lấy từ bảng trong video.

07. Scale và giảm độ trễ 25:40–28:40

Chia shard KV store bằng consistent hashing; đưa rule vào cache bộ nhớ, có worker định kỳ chép từ database sang

Nếu cần lưu terabytes trong bộ nhớ thì có nhiều instance KV store, scale ngang (sharding: một nửa dữ liệu ở đây, một nửa ở kia). Một user phải luôn chạm đúng shard chứa dữ liệu của mình → dùng consistent hashing (không đi sâu).

Nút thắt latency: đọc memory gần như không thể nhanh hơn, nhưng đọc database rule chậm hơn nhiều. Rule cần lưu bền, nhưng được tạo hiếm, đọc thì liên tục. Nên thêm lớp cache bộ nhớ giữa database và rate limiter: vừa bền (nhờ DB) vừa đọc nhanh. Database không tự ghi sang chỗ khác được, nên cần một worker chạy nền đọc DB và định kỳ cập nhật cache — chạy khá thường xuyên để rate limiter không đọc rule stale; có thể scale ngang nếu cần.

Hình 4 — Shard KV store, rules cache và worker
▸ Ví dụ của nguồn — sửa một rule
  1. Developer đổi rule upload trong Rules DB.
  2. Worker định kỳ đọc DB, chép rule mới vào cache.
  3. Rate limiter đọc rule từ cache trong bộ nhớ, không chạm DB mỗi request.
