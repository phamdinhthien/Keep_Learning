01. Functional requirements 00:00–03:00

Map URL dài thành URL ngắn 8 ký tự, tự redirect; URL hết hạn (mặc định 1 năm); cùng URL dài vẫn tạo URL ngắn mới mỗi lần

TinyURL, Bitly: từ URL dài như neetcode.io/courses/system-design-for-beginners tạo URL ngắn tinyurl.com/…; mở URL ngắn sẽ redirect tự động sang URL dài. Phần path có thể là từ dễ nhớ như "happy" nhưng không phải lúc nào cũng được, nên là chuỗi ký tự lộn xộn, giới hạn 8 ký tự. Bỏ qua trường hợp user tự chọn chuỗi, và bỏ qua xoá URL (cần theo dõi ownership) — đều không đổi thiết kế nhiều.

URL hết hạn: mặc định một năm, user có thể chọn dài hơn, 5 hay 10 năm — phải nghĩ dài hạn để không cạn tài nguyên. Câu hỏi cuối: nhiều user rút gọn cùng một URL dài thì có dùng chung URL ngắn không? Không — mỗi người có hạn riêng; URL của người này hết hạn sẽ làm hỏng người kia. Vậy mỗi lần đều tạo URL ngắn duy nhất.

▸ Ví dụ của nguồn — cùng URL dài, hai user
Dùng chungUser A đặt hết hạn sớm → URL ngắn chết, user B (muốn 5 năm) bị ảnh hưởng.
Mỗi lần một keyMỗi user có URL ngắn và thời hạn riêng.
02. Non-functional và quy mô 03:00–08:40

Available, chịu lỗi, latency thấp; 1 tỷ URL/tháng → ~300–400 writes/s, ~30.000 reads/s, ~1 TB/tháng; 628 key là quá đủ

Hệ thống cần available và fault tolerant: một thành phần hỏng không làm sập cả hệ thống. Latency tối thiểu — URL ngắn mà chậm thì dùng URL dài cho rồi.

Ghi là tạo URL ngắn, đọc là dùng nó. Đọc nhiều hơn hẳn; người phỏng vấn cho tỷ lệ 1:100. Số URL tạo: một tỷ mỗi tháng. 8 ký tự có cạn không? Dùng 0–9, a–z, A–Z → 62 ký tự, 628 khả năng — con số rất lớn. Video nhẩm 60² = 3600, rồi bình phương hai lần, ra khoảng "một nghìn tỷ" (trillion); với 12 tỷ mỗi năm thì dùng gần trăm năm.

Tính đúng: 628 ≈ 2,18 × 1014 (khoảng 218 nghìn tỷ), lớn hơn nhiều so với ước lượng "một nghìn tỷ" của video (3600² ≈ 13 triệu, chứ không phải một triệu). Với 12 tỷ URL/năm thì đủ cho hàng nghìn năm — kết luận "không lo cạn key" càng đúng.

Throughput: 1 tỷ/tháng ≈ 33 triệu writes/ngày; chia ~100.000 giây → khoảng 330, làm tròn 300–400 writes per second. Đọc gấp 100 → khoảng 30,000 reads per second.

Storage: không cần lưu domain cho mỗi URL, chỉ key 8 ký tự = 8 byte (8 tỷ byte = 8 GB/tháng). Thêm URL dài, trung bình 100 ký tự (có khi 1000) → ~108 byte; chừa chỗ cho metadata như user ID → ước dư 1000 byte/URL. 1000 × 1 tỷ = một nghìn tỷ byte = 1 terabyte mỗi tháng; 10 năm khoảng một petabyte — nhỏ hơn mạng xã hội nhiều.

▸ Ví dụ của nguồn — phép nhẩm
1.000.000.000 URL/tháng ÷ 30   ≈ 33.000.000 writes/ngày
33.000.000 ÷ 100.000 s          ≈ 330 → ~300–400 writes/s
× 100 (tỷ lệ 1:100)             ≈ 30.000 reads/s
1000 byte × 1 tỷ URL            = 1 TB/tháng
03. Thiết kế cấp cao 08:40–11:50

Mapping lưu trong NoSQL: dữ liệu đơn giản, không join, chấp nhận eventual consistency vài giây; tạo URL qua server và URL generator

Dữ liệu không quá lớn; điều đáng lo là lượng đọc. NoSQL được thiết kế để scale lớn. Nó không có ACID, không relational — nhưng ta chỉ map URL dài với URL ngắn (thêm user ID và vài thông tin), không join hay query phức tạp, không cần atomic transaction. Với BASE, NoSQL có eventual consistency: vừa tạo URL, một replica có thể chưa có — không sao, vài giây sau mọi replica đều nhất quán, mà ghi lại không thường xuyên.

Tạo URL: user gọi server → server lấy một key từ URL generator → ghi vào database (có thể nhiều node, có replica, phân tán). Đọc: user gọi server với URL ngắn → tìm URL dài trong database → trả về để user được redirect. Rất cấp cao, nhưng nên chốt hướng với người phỏng vấn trước khi đào sâu.

▸ Ví dụ của nguồn — hai luồng
TạoClient → server → lấy key từ URL generator → ghi (key → URL dài) vào NoSQL.
ĐọcClient → server → tra key trong NoSQL → trả URL dài → redirect.
04. Cache 11:00–14:10

Vì đọc nhiều, đặt cache bộ nhớ khoảng 256 GB trước database; chọn LRU thay LFU để URL từng hot nhưng đã nguội không chiếm chỗ

Vài URL được dùng nhiều hơn hẳn, nên thêm caching layer giữa server và database: đọc cache trước, giữ tập URL hot → redirect nhanh hơn nhiều. Phải là in-memory cache — nhanh hơn đọc disk của database.

Kích thước: đọc gấp nhiều lần ghi, nhưng không có nghĩa là nhiều URL khác nhau đến vậy — không cần cả petabyte. Hợp lý là 256 gigabytes: đắt nhưng chấp nhận được; có thể phân tán, sharding, replicate. Eviction policy: LFU (least frequently used) hay LRU (least recently used)? Một URL từng hot, được dùng một triệu lần, rồi hết trend — với LFU nó có count lớn nên ở lì trong cache, vô ích. LRU chỉ giữ URL đang được dùng, ít cache miss hơn.

▸ Ví dụ của nguồn — đọc một URL ngắn
  1. Server đọc cache: cache hit → có URL dài, trả ngay.
  2. Cache miss → đọc database trên disk, chậm hơn.
05. Redirect: 301 hay 302 14:10–16:50

Server trả mã 3xx kèm header Location; 301 (vĩnh viễn) được browser cache, 302 (tạm thời) thì lần nào cũng hỏi lại — hữu ích cho analytics

Thử tự rút gọn một URL rồi mở DevTools, tab Network: request tới URL ngắn nhận mã nhóm 3xx — tài nguyên đã chuyển chỗ. Response header có trường Location chứa vị trí mới; browser tự đi tới đó, không phải gõ gì. Về lý thuyết chậm hơn gõ thẳng URL dài một chút, nhưng gần như nhanh nhất có thể.

301: chuyển vĩnh viễn — browser cache lại, lần sau không hỏi TinyURL nữa, như gõ thẳng URL dài. 302: chuyển tạm thời — không cache, mỗi lần đều hỏi TinyURL (hôm sau có thể khác). Video thích 301 và TinyURL cũng dùng 301; 302 hợp khi muốn mọi request đi qua mình, ví dụ cho analytics.

06. Sinh key không trùng 16:50–23:20

Hash dễ va chạm; thay vào đó sinh sẵn các key 8 ký tự vào database, lấy key chưa dùng trong một transaction SQL để atomicity và isolation chặn trùng

Sinh chuỗi 8 ký tự base 62 thế nào cho không collision? Hash có thể cho hai chuỗi khác nhau ra cùng kết quả, và khó đảm bảo đúng 8 ký tự (làm được nhưng nặng toán, kiến thức chuyên về SHA, MD). Cách đơn giản mà hiệu quả: sinh sẵn tất cả (hoặc phần lớn) chuỗi dài 8 và lưu vào một database keys — key là phần path của URL ngắn. Có thể để một service bổ sung dần khi sắp hết, không cần sinh đủ 628 ngay.

Cho nhanh: URL generator không đọc disk mỗi lần mà bulk request lấy một loạt key nạp vào bộ nhớ. Vì có thể có nhiều instance URL generator, key đã lấy phải đánh dấu used trong database (cột key và cột Boolean used). Không cần xoá key đã dùng: khi URL hết hạn, đặt lại unused để tái sử dụng, khỏi cạn key.

Nếu hai instance cùng đọc một key cho hai user? Một URL ngắn không thể trỏ tới hai URL dài — chức năng hỏng. Dữ liệu ít, không relational, nhưng SQL có ACID. Durability và consistency không giúp ở đây. Atomicity: đọc một key chưa dùng và đánh dấu used trong cùng một transaction — làm hết hoặc không làm gì. Isolation: hai transaction chạy đồng thời nhưng như thể lần lượt — transaction sau chắc chắn nhận key khác.

Hình 3 — Transaction SQL chặn hai instance lấy trùng key

Fault tolerance: một instance nạp key vào bộ nhớ, đánh dấu used rồi crash → các key đó mất. Đánh đổi: cache trong generator cho tốc độ; làm việc trực tiếp với database thì chậm hơn nhưng có ACID — với khoảng 300 writes/s, database chịu được. Tốt hơn nữa: dùng in-memory store nhưng có locking — vừa xác định key cho một request là khoá row đó, user khác không đọc được.

▸ Ví dụ của nguồn — bảng keys
key        used
9a3v326p   true    // đang dùng
x7Kp02Qa   false   // còn trống

Các key cụ thể là minh hoạ thêm (key đầu lấy từ URL trong DevTools của video).

07. Hết hạn, scale và schema 23:20–27:20

Cleanup service chạy định kỳ: trả key về unused và xoá mapping hết hạn; scale bằng load balancer, replica và partition theo user ID

Phát hiện URL hết hạn: một cleanup service định kỳ đọc database, lọc theo ngày hết hạn. Chậm 5–10 phút cũng không sao (nên bàn với người phỏng vấn). Với mỗi dòng hết hạn: lấy key, vào database keys SQL giải phóng (đánh dấu unused), rồi xoá mapping khỏi database URL. Chạy mỗi 5 phút, 10 phút hay mỗi giờ — bất đồng bộ, không phải trên mỗi request.

Scale: thêm load balancer giữa client và nhiều instance server; database có replica và cần partition — dễ nhất là hash user ID bằng consistent hashing, để mọi URL của một user nằm trên một partition, và scale lên xuống được. Có thể thêm load balancer giữa server và cache. Nhưng điểm đặc biệt của bài là URL generator service; thứ không được bỏ sót là dùng NoSQL cho mapping.

Schema NoSQL: user ID, long URL, key (URL ngắn — server ghép base URL tinyurl.com/ + key), expiration date (trường cleanup service cần). Có thể thêm thời gian tạo và các trường khác.

▸ Ví dụ của nguồn — một document
{ userId: "...", longUrl: "https://neetcode.io/courses/...",
  key: "9a3v326p", expiresAt: "mặc định +1 năm" }

Tên trường viết theo kiểu code là minh hoạ thêm; bốn trường lấy từ video.

Năm câu hỏi

Với 1 tỷ URL/tháng và tỷ lệ 1:100, throughput đọc là bao nhiêu?

Khoảng 300–400 writes/s, nên khoảng 30.000 reads/s. (→ 02)

Vì sao NoSQL ổn dù chỉ eventual consistency?

Dữ liệu đơn giản, ghi không thường xuyên; replica chậm vài giây mới có URL mới là chấp nhận được. (→ 03)

Khác biệt giữa 301 và 302?

301 là chuyển vĩnh viễn, browser cache; 302 là tạm thời, mỗi lần đều hỏi server — hợp cho analytics. (→ 05)

Thuộc tính ACID nào ngăn hai user nhận cùng key?

Atomicity (đọc và đánh dấu used trong một transaction) và isolation (transaction đồng thời như chạy lần lượt). (→ 06)

Cleanup service làm gì với một URL hết hạn?

Đánh dấu key là unused trong database keys rồi xoá mapping trong database URL. (→ 07)
