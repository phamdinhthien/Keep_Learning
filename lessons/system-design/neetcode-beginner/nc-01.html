01. Code → server ~00:00–01:30

Code của developer phải được build, deploy rồi chạy trên server — một máy tính phục vụ request

Nhìn từ phía developer: ta viết code, code phải được deploy tới một server để chạy. Tạm hiểu server là một máy tính xử lý được request, tức là phục vụ người dùng; khóa học sẽ đào sâu hơn sau.

Thường có một bước trung gian: code được build và deploy. Việc này có thể chạy trên máy local của dev, nhưng phổ biến hơn là trên một CI/CD server (continuous integration, continuous deployment), đặc biệt với ứng dụng production chuyên nghiệp. Trong sơ đồ này nó là bước tuỳ chọn.

▸ Ví dụ của nguồn — hai nơi build
Máy local của devBuild và deploy ngay từ máy mình.
CI/CD serverCách phổ biến hơn ở môi trường chuyên nghiệp, cho ứng dụng production.
02. Persistent storage ~01:30–02:45

Dữ liệu được lưu ở một storage riêng, nối với server qua network, không phải trên disk của server

Server cần lưu dữ liệu, nên có một storage bên ngoài. Nó có thể là bất cứ thứ gì: nghĩ ngay tới database là đúng, nhưng còn nhiều cách khác để lưu dữ liệu. Đây là persistent storage.

Server là một máy tính nên cũng có disk riêng, nhưng disk đó có giới hạn (như video trước). Vì vậy đây là storage phân tán: chạy trên máy riêng, không cùng server, nối với nhau qua network, thậm chí nằm ở các nơi khác nhau trên thế giới.

▸ Ví dụ của nguồn — storage không nằm cùng máy

Server chạy code ở một nơi, database chạy trên một máy khác, có thể ở một khu vực khác trên thế giới; hai bên nói chuyện qua network.

03. User & API ngoài ~02:45–05:00

User gửi request từ trình duyệt; server trả về front-end (HTML, JS) hoặc dữ liệu JSON, và có thể gọi tiếp API bên ngoài

Người dùng muốn dùng ứng dụng thì phải gửi request tới server, thường là từ trình duyệt. Nếu server phục vụ front-end, nó trả về HTML và JavaScript để trình duyệt tải trang. Nếu là back-end, trình duyệt gọi API và server trả về dữ liệu, thường ở dạng JSON, một định dạng dữ liệu phổ biến.

Server không chạy cô lập: nó có thể gọi các server khác. Có thể có rất nhiều server bên ngoài như vậy; sơ đồ chỉ vẽ một.

▸ Ví dụ của nguồn — neetcode.io gọi Stripe

Code của neetcode.io gọi các API khác, ví dụ Stripe API để xử lý thanh toán.

04. Vertical scaling ~05:00–06:30

Quá tải thì tìm bottleneck rồi nâng cấp chính máy đó — gọi là vertical scaling, và nó có trần

Nhiều user gửi request cùng lúc và một máy không kham nổi. Trước tiên xác định bottleneck: có thể CPU không đủ nhanh, thì mua CPU tốt hơn; có thể thiếu RAM, thì thêm RAM. Từ bài kiến trúc máy tính, ta có thể nâng cấp CPU, RAM, disk, hay cả chiếc máy.

Lấy một tài nguyên và làm nó tốt hơn gọi là vertical scaling, giống như "thêm một khối" vào chính server đó. Về khái niệm thì rất đơn giản. Nhưng máy tính có giới hạn: CPU nhanh tới đâu cũng không xử lý được vô hạn request.

Hình 2 — Vertical scaling (trái) so với horizontal scaling (phải)
▸ Ví dụ của nguồn — tìm đúng chỗ nghẽn

CPU là thứ làm chậm → thay CPU tốt hơn, server xử lý được nhiều request hơn. RAM là giới hạn → thêm RAM. Cả hai đều là vertical scaling vì chỉ làm một server tốt hơn.

05. Horizontal scaling & load balancer ~06:30–08:30

Horizontal scaling chạy nhiều bản sao server; load balancer quyết định mỗi request đi tới bản nào

Horizontal scaling: thay vì làm một server tốt hơn, ta tạo nhiều bản sao cùng chạy code. User không còn phải nói chuyện với một server duy nhất, nên hệ thống xử lý được nhiều request cùng lúc hơn. Không server nào được nâng cấp; ta chỉ thêm server cho cùng một việc.

Vấn đề mới: request của user nên tới server nào? Đó là việc của load balancer. Tạm hiểu nó chuyển request tới server đang ít traffic nhất, để các server có lượng traffic cân bằng. Nếu một server gánh hết còn server khác ngồi không thì horizontal scaling chẳng có ý nghĩa.

Nguồn gọi cách này là "horizontal autoscaling" ở một chỗ; ý chính vẫn là thêm máy, không nâng cấp máy. Load balancer sẽ được học sâu ở video sau.
▸ Ví dụ của nguồn — vì sao cần cân bằng
Không cân bằngMột server xử lý mọi request, server kia không làm gì: thêm máy cũng vô ích.
Có load balancerRequest được gửi tới server ít traffic nhất, mỗi server một phần tải.
06. Logging & metrics ~08:30–11:00

Log kể từng request diễn ra thế nào; metrics cho thấy server và ứng dụng chạy ra sao theo thời gian

Chạy local ta dùng log hay print để biết code đang làm gì. Server không chạy trên máy ta, nên cũng ghi log, nhưng không cần lưu hết trên server, vì người đọc log là developer, không phải server. Ta dùng một dịch vụ log bên ngoài: mỗi request, tốt hay hỏng, server đều ghi thông tin vào đó. User không bao giờ tương tác với dịch vụ này.

Log không kể hết câu chuyện. Một server chạy kém, có thể vì CPU lỗi; ta muốn biết CPU có bị chiếm hết, RAM có đầy, storage có hết chỗ. Dịch vụ metrics cung cấp các số đó: server có trả lời mọi request, có request nào lỗi, tài nguyên dùng tới đâu — gồm application metrics và resource metrics.

Một số metric lấy thẳng từ log, gọi là log-based metrics: log mỗi lần request thành công hay thất bại rồi đếm. Metrics thường hiển thị dạng biểu đồ time series (CPU theo thời gian đi lên hay đi xuống). Log hợp làm nguồn vì log vốn là dữ liệu time series: mỗi dòng log đều có timestamp.

▸ Ví dụ của nguồn — từ log thành metric
// mỗi dòng log có timestamp → ghép lại thành time series
10:00:01  request OK
10:00:02  request FAILED
10:00:02  request OK
→ metric: tỉ lệ thành công theo từng phút

Thời điểm và thứ tự dòng log là minh hoạ thêm; nguồn chỉ nói "log mỗi lần thành công, mỗi lần thất bại rồi tạo metric".

07. Alerting ~11:00–12:30

Alerting đẩy thông báo cho developer ngay khi metric vượt ngưỡng, thay vì chờ user email báo lỗi

Không ai muốn phải ngồi nhìn metrics mới phát hiện sự cố, tệ hơn là để user email báo app hỏng — user luôn dùng app nên họ thường biết đầu tiên. Ta muốn push notification: metrics được đưa vào một dịch vụ alerting, dịch vụ này báo khi một metric chạm ngưỡng (threshold).

Hình 3 — Tỉ lệ request thành công tụt dưới 95% thì alert tự động gửi đi

Developer sẽ được báo gần như cùng lúc với một số user; đó là mức nhanh nhất có thể, trừ khi đoán trước được tương lai. Sơ đồ dù đã đơn giản hoá vẫn khá lớn, cho thấy ứng dụng phức tạp tới đâu. Còn nhiều thứ chưa nói, nhất là networking: các thành phần chạy trên máy khác nhau nên giữa chúng luôn có network. Developer không cần biết hết chi tiết, nhưng hiểu cơ bản rất có ích khi thiết kế hệ thống lớn.

▸ Ví dụ của nguồn — ngưỡng 95%

Bình thường 100% request nhận response thành công. Đặt alert: khi metric này giảm từ 100% xuống 95% hoặc thấp hơn, dịch vụ alerting tự động báo developer.

Ôn tập · Tự kiểm tra

Năm câu hỏi

CI/CD là viết tắt của gì, và có bắt buộc không?

Continuous integration, continuous deployment. Đây là bước build và deploy trung gian, phổ biến ở môi trường chuyên nghiệp nhưng là tuỳ chọn trong sơ đồ. (→ 01)

Server front-end và server back-end trả về gì cho trình duyệt?

Front-end trả HTML và JavaScript để tải trang; back-end trả dữ liệu từ API, thường là JSON. (→ 03)

Server chậm vì CPU. Vertical scaling là gì trong trường hợp này, và giới hạn của nó?

Thay CPU tốt hơn cho chính server đó. Giới hạn: CPU nhanh tới đâu cũng không xử lý vô hạn request. (→ 04)

Có ba server sau load balancer. Request mới nên tới đâu?

Server đang có ít traffic nhất, để ba server có lượng traffic cân bằng. (→ 05)

Vì sao log dùng được để tạo metrics?

Log vốn là dữ liệu time series: mỗi dòng có timestamp, nên đếm request thành công và thất bại theo thời gian là ra metric. (→ 06)
