01. API là gì ~00:00–03:00

API là bất kỳ giao diện lập trình nào; trong khóa này, API chủ yếu là dịch vụ bên ngoài như HTTP API

Có HTTP, WebSockets hay giao thức khác thì ta tạo được API (application programming interface). Thuật ngữ này rất lỏng: bất kỳ giao diện lập trình nào cũng là API. Trình duyệt có local storage — lưu thông tin bền vững nhưng chỉ trên một máy — và có API để đọc ghi nó. Một object trong lập trình hướng đối tượng định nghĩa các method để truy cập dữ liệu, đó cũng là API.

Phổ biến nhất, API chỉ một dịch vụ bên ngoài, ví dụ HTTP API phục vụ request của user; đó là nghĩa dùng trong khóa. Bàn về API paradigm là bàn về các cách khác nhau để xây cùng một thứ.

▸ Ví dụ của nguồn — theme sáng/tối của YouTube

Bật light theme hay dark theme trên youtube.com, lựa chọn thường được lưu trong local storage của trình duyệt. Giao diện đọc/ghi local storage chính là một API, dù rất đơn giản.

02. Ba paradigm ~03:00–05:00

REST quan trọng nhất; GraphQL do Facebook tạo ra để sửa vài vấn đề của REST; gRPC có trade-off riêng

Ba paradigm hiện đại phổ biến nhất: REST — phổ biến và quan trọng nhất; GraphQL — mới hơn, do Facebook tạo ra, ít phổ biến hơn REST nhưng giải quyết vài vấn đề của REST, ít nhất nên biết nó tồn tại; và gRPC. Điều quan trọng là ưu nhược điểm. Không cần đã làm cả chục API bằng mỗi cái, nhưng nên bàn được một hai trade-off.

▸ Mục tiêu nguồn đặt ra cho người học

Với mỗi paradigm, trả lời được: nó giải quyết vấn đề gì, và đánh đổi gì. Bảng "Khi nào dùng" ở cuối trang gom lại các trade-off đó.

03. REST ~05:00–07:00

REST không phải giao thức mà là một bộ ràng buộc áp lên HTTP API để chúng chuẩn hoá và dễ scale

REST là viết tắt của representational state transfer. REST API thường xây trên HTTP, nhưng REST không phải giao thức; nó là tập ràng buộc lỏng — hay chuẩn hoá — áp lên HTTP API. Mục tiêu: API chuẩn hoá mà ai cũng nhận ra, dễ dùng, và có lợi ích khác như scale được.

Ngày nay "HTTP API" gần như đồng nghĩa với REST; nhiều người tưởng REST là HTTP. Không phải vậy, nhưng cũng dễ hiểu: rất có thể bạn chỉ từng dùng REST API. REST bám sát HTTP: dùng các method GET, POST… và status code như 404 hay 201.

Đính chính nguồn: transcript có chỗ nghe thành "2011"; ý người nói là status code 201.
▸ Ví dụ của nguồn — nhầm lẫn phổ biến
Nhiều người nghĩREST = HTTP.
Thực raREST là các ràng buộc áp lên HTTP API; HTTP là giao thức.
04. Resource & endpoint ~07:00–10:00

Mỗi REST endpoint gắn với một resource (danh từ); hành động là HTTP method, không viết động từ vào URL

Mỗi REST endpoint gắn với một resource — một danh từ, một "thứ". Trên YouTube, video là resource; user cũng vậy. Lấy một video: GET youtube.com/videos/:id. Lấy mọi comment của video: thêm resource /comments.

Không đặt động từ vào tên resource, kiểu "getVideos", "postVideo", "createVideo", "uploadVideo". HTTP method — GET, POST, DELETE… — chính là động từ: hành động gì trên resource này. Phần thiết kế API tốt sẽ nói thêm ở video sau.

▸ Ví dụ của nguồn — URL theo resource
GET youtube.com/videos/:id            // một video
GET youtube.com/videos/:id/comments   // mọi comment của video
GET youtube.com/getVideos           // ✗ có động từ trong URL
05. Stateless & pagination ~10:00–17:00

Stateless nghĩa là server không giữ state của user; client gửi đủ thông tin trong mỗi request, ví dụ limit và offset

Điều lớn nhất của REST: stateless. Trang chủ YouTube trả mặc định 10 video; cuộn xuống hay sang trang sau (thời chưa có news feed) muốn thêm 10. Cách thứ nhất: server giữ một session cho từng user ở phía server, nhớ bạn đã xem 10 video, rồi trả 10 video mới. Đó là stateful, không phải REST.

Stateless không có nghĩa là không lưu gì: server vẫn được đọc ghi database — dữ liệu bền vững ở đó vẫn là REST. Chỉ là bản thân server không giữ state. Trình duyệt thì gần như luôn có state: cookies, session storage; chúng nằm trên máy bạn và được gửi lên server, không lưu ở server.

Cách đúng là pagination: mỗi request tự mang thông tin phân trang. GET không có body nên đặt trong URL. :id là URL parameter (giá trị thật kiểu XYZ, không phải chữ "id"); dấu ? mở đầu query parameter. limit = lấy bao nhiêu (10, hay 100 nếu muốn); offset = bắt đầu từ đâu.

Hình 2 — Lần đầu offset 0, lần sau offset 10; server không cần nhớ gì
▸ Ví dụ của nguồn — 10 video rồi 10 video nữa
GET youtube.com/videos?offset=0&limit=10    // 10 video đầu
GET youtube.com/videos?offset=10&limit=10   // bỏ 10 đã xem, lấy 10 tiếp
06. Vì sao cần stateless ~17:00–19:00

Server không giữ state thì request rơi vào server nào cũng được — nên scale ngang bao nhiêu server cũng được

Lý do chính: khi có nhiều server, ví dụ ba server sau một load balancer. Nếu một server giữ session của bạn, request kế tiếp có thể rơi vào server khác và hỏng. REST stateless thì không server nào giữ state; chúng có thể cùng nói chuyện với một database trung tâm chứa mọi dữ liệu. Nhờ vậy ta scale ngang bao nhiêu server cũng được — lợi ích lớn nhất của REST.

Phần còn lại đã học ở bài HTTP: status code như 400 lỗi client, 500 lỗi server rất quan trọng với REST, là cách báo request tốt hay xấu.

Hình 3 — Session trên server làm hỏng khi load balancer chuyển sang server khác
▸ Ví dụ của nguồn — ba server sau load balancer

Request đầu tới server A, A biết bạn đã xem bao nhiêu video. Request sau load balancer chuyển sang server khác: nếu là stateful thì hỏng; stateless thì offset đã nằm trong request, server nào cũng trả đúng.

07. JSON ~19:00–21:00

JSON là định dạng phổ biến nhất của REST: cặp key–value dễ đọc, lồng nhau được, nhưng hiệu năng không tốt nhất

JSON là JavaScript object notation vì trông giống object JavaScript, dù không hoàn toàn giống. Ưu điểm lớn: rất dễ đọc. Nó là tập cặp key–value, mỗi key là chuỗi. Giá trị có thể là kiểu nguyên thuỷ (string, boolean, integer, double), object lồng nhau, mảng, hoặc null. Về hiệu năng thì làm tốt hơn được, như sẽ thấy ở gRPC.

▸ Ví dụ của nguồn — object JSON trong video
{
  "firstName": "John",
  "address": { … },                  // object lồng nhau
  "phoneNumbers": [                    // mảng các object
    { "type": "home", … },
    { "type": "office", … }
  ],
  "spouse": null                       // giá trị null
}

Các key ngoài firstName, address, phoneNumbers là minh hoạ thêm.

08. GraphQL ~21:00–27:00

GraphQL dùng một endpoint, chỉ HTTP POST, cho client chọn đúng field và gộp nhiều lần lấy dữ liệu vào một query

GraphQL công khai khoảng 2015, do Facebook tạo ra. Không phải giao thức; xây trên HTTP nhưng chỉ dùng POST, vì phải gửi query trong body mà GET thì không có body. Query cho server biết chính xác cần những resource nào.

Vấn đề thứ nhất của REST: over-fetching. Hiển thị năm comment, mỗi comment là một thẻ có ảnh đại diện, username và nội dung. Nhưng resource user có rất nhiều thứ khác, như tài khoản tạo năm nào (2020…). REST trả hết; muốn bớt thì phải thêm logic riêng ở server mỗi lần gặp chuyện tương tự. GraphQL chỉ định từng field cần, server chỉ trả đúng các field đó: ít dữ liệu qua network, app nhanh hơn.

Vấn đề thứ hai: under-fetching, phải gọi nhiều request nối tiếp — lấy video, rồi comment của video, rồi thông tin user của từng comment. GraphQL có một endpoint với hai loại thao tác: query (đọc, không đổi dữ liệu) và mutation (tạo, cập nhật, xoá). Cả chuỗi trên gói trong một query. Nhược điểm: POST không idempotent nên GraphQL cache kém hơn, kém chính xác hơn REST.

Hình 4 — Cùng một màn hình comment: REST và GraphQL
▸ Ví dụ của nguồn — thẻ comment

Năm comment, mỗi thẻ chỉ cần ảnh đại diện + username + nội dung. REST: gọi video, gọi comments, rồi gọi user cho từng comment và nhận cả đống field thừa. GraphQL: một query, đúng các field đó.

09. Demo SpaceX GraphQL ~27:00–30:00

GraphQL Explorer cho tick chọn từng field; khác REST, GraphQL có schema nên không hỏi được field không tồn tại

GraphQL có tooling khá tốt, ví dụ GraphQL Explorer với SpaceX GraphQL API. Dù chạy trên HTTP, ta không thấy phần HTTP, chỉ thấy query và response. Lấy launches past giới hạn 10 — GraphQL cũng có kiểu pagination. Mỗi launch chọn field: mission name, launch site…

Bỏ tick gần hết rocket, chỉ giữ first stage: lỗi, vì phải chọn sub-field; chọn cores, rồi bỏ reuse count và flight, chỉ giữ status. Có thể thêm missions, flight number, cả ships — lấy đúng thứ cần mà không cần dựng nhiều REST endpoint. Cú pháp lồng nhau giống JSON. Nhưng GraphQL có schema: đây là SpaceX nên không có field Tesla, và không tự thêm được — khác REST với JSON truyền gì cũng được.

▸ Ví dụ của nguồn — query trong demo (viết lại gần đúng)
query {
  launchesPast(limit: 10) {
    mission_name
    launch_site { … }
    rocket { first_stage { cores { status } } }
    ships { … }
  }
}

Tên field theo những gì người nói đọc trong video; cú pháp chính xác có thể khác API thật.

10. gRPC ~30:00–34:00

gRPC chạy trên HTTP/2 và gửi protocol buffers nhị phân theo schema, nên nhanh hơn REST và hỗ trợ streaming

gRPC cũng xây trên HTTP, cụ thể là HTTP/2 (HTTP đi từ 1.0, 1.1, lên 2, gần đây là 3), vì cần vài tính năng của HTTP/2. Trình duyệt không gọi gRPC trực tiếp được do gRPC cần kiểm soát HTTP/2 rất chi tiết mà trình duyệt không cho; phải qua proxy, thường là gRPC-Web. Vì vậy gRPC chủ yếu dùng cho server ↔ server.

gRPC khách quan là nhanh và hiệu quả hơn REST trong gần như mọi trường hợp. Lý do: thay vì gửi JSON — chỉ là chuỗi ký tự — nó gửi protocol buffers: object có schema (JSON không phải schema), được serialize thành nhị phân, nên gửi ít dữ liệu hơn. Nhờ HTTP/2, gRPC còn có streaming: một chiều client → server, server → client, hoặc hai chiều — đúng việc của WebSocket.

Hình 5 — JSON dạng chuỗi so với protocol buffers nhị phân
Nhắc lại từ người nói: HTTP/2 về kỹ thuật làm WebSocket gần như lỗi thời, nhưng phần lớn kỹ sư không biết điều này. Điều cần nắm là trade-off và mỗi công nghệ làm được gì, không phải chi tiết đó.
▸ Ví dụ của nguồn — nhiều server nói chuyện với nhau

Nhiều server trong hệ thống cần gọi nhau: đó là chỗ của gRPC — nhanh, có schema, và stream được cả hai chiều.

11. Nhược điểm của gRPC ~34:00–36:00

gRPC mới hơn, ít tooling, khó dùng từ trình duyệt, và không dùng status code HTTP — phải tự xử lý lỗi

gRPC mới hơn — người nói nói được tạo năm 2016 bởi Google và open-source. Nhược điểm: ít tooling hơn nhiều, kém chuẩn hoá, khó hơn. Protocol buffers nhanh nhưng schema có thể phiền khi phát triển; gRPC cần tooling tốt; và khó dùng từ trình duyệt. REST phổ biến hơn, dễ hơn, cộng đồng lớn hơn.

Dù chạy trên HTTP, gRPC không thật sự dùng status code của HTTP. Thay vào đó là error message: bạn tự định nghĩa ở server và tự xử lý ở client theo cách mình chọn.

Đính chính nguồn: transcript nói dựng API tương đương bằng gRPC "chắc chắn tốn ít thời gian hơn REST" — ngược với mạch lập luận ngay trước đó; ý người nói nhiều khả năng là gRPC tốn nhiều thời gian hơn. Về mốc thời gian: gRPC được Google công bố mã nguồn mở năm 2015, bản 1.0 ra năm 2016.
▸ Ví dụ của nguồn — xử lý lỗi
RESTNhìn status code (200, 404, 500…) là biết kết quả.
gRPCServer trả error message tự định nghĩa; client tự quyết cách xử lý.
12. Protocol buffers & service ~36:00–38:00

File .proto định nghĩa message có field đánh số và service có RPC — mỗi endpoint là một động từ, như gọi hàm

Ví dụ từ tài liệu công khai của Google: message là từ khoá định nghĩa schema. SearchRequest có ba field đánh số thứ tự: query (1), page_number (2), results_per_page (3). Phải đánh số vì dữ liệu được serialize thành nhị phân, không đọc được; khi deserialize nó thành object trong ngôn ngữ bạn chọn (Python, Go, Java…). Cú pháp proto3 là mới nhất, nằm trong file .proto.

Định nghĩa service, ví dụ Greeter, với một endpoint gọi là RPC: SayHello nhận HelloRequest (một field string name) và trả HelloReply. Request và response đều có schema nên biết chính xác sẽ nhận gì. Logic thì viết bằng Java hay Python, không trong file proto. Khác REST — resource là danh từ, method HTTP là động từ — mỗi RPC là một hành động, một hàm chạy trên máy khác; ta không quan tâm HTTP method hay status code nữa.

▸ Ví dụ của nguồn — hai đoạn proto trong video
syntax = "proto3";
message SearchRequest {
  string query = 1;
  int32 page_number = 2;
  int32 results_per_page = 3;
}
service Greeter {
  rpc SayHello (HelloRequest) returns (HelloReply) {}
}
message HelloRequest { string name = 1; }
message HelloReply { string message = 1; }

Kiểu dữ liệu của page_number, results_per_page và field của HelloReply theo tài liệu gốc của Google; video chỉ đọc tên.

Sáu câu hỏi

REST là viết tắt của gì, và ràng buộc quan trọng nhất là gì?

Representational state transfer; quan trọng nhất là stateless. (→ 03, 05)

Đã xem 20 video, mỗi trang 10. Request tiếp theo có query param gì?

offset=20&limit=10 (tính toán minh hoạ thêm theo cùng cách của nguồn). (→ 05)

Vì sao stateless giúp scale ngang?

Không server nào giữ session, nên load balancer chuyển request tới server nào cũng trả đúng; thêm server bao nhiêu cũng được. (→ 06)

Over-fetching và under-fetching khác nhau thế nào? GraphQL giải quyết ra sao?

Over: nhận thừa field; under: phải gọi nhiều request nối tiếp. GraphQL cho chọn đúng field và gộp vào một query ở một endpoint. (→ 08)

Vì sao gRPC nhanh hơn REST?

Gửi protocol buffers nhị phân theo schema thay vì chuỗi JSON, nên ít dữ liệu hơn; chạy trên HTTP/2. (→ 10)

Vì sao field trong protocol buffer phải đánh số?

Dữ liệu serialize thành nhị phân không đọc được; số thứ tự giúp deserialize đúng field thành object trong ngôn ngữ đích. (→ 12)
