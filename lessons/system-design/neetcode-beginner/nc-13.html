01. Hashing cơ bản ~00:00–03:00

Lấy IP mod số server để chọn server: cùng một IP luôn về cùng một server

Bên cạnh round robin, load balancer có thể dùng hashing. Ba server, hash theo IP của user. IP là một số nguyên; đơn giản hoá, giả sử IP là 6. Lấy mod — phần dư khi chia cho số server: 6 mod 3 = 0, nên về server 0 (đánh số 0, 1, 2). IP 7 dư 1 → server 1; IP 8 → server 2. IP phân bố khá đều nên tải cũng khá cân.

▸ Ví dụ của nguồn — 3 server
6 mod 3 = 0   → server 0
7 mod 3 = 1   → server 1
8 mod 3 = 2   → server 2

IP thật không nhỏ như vậy; đây là ví dụ đơn giản hoá của nguồn.

02. Vì sao cần cùng server ~03:00–06:00

Nếu mỗi server có cache riêng, user phải luôn về đúng server đó thì cache mới có ích

Lợi thế so với round robin: user IP 6 luôn về server 0, kể cả khi server đó không phải ít tải nhất. Nếu server là REST stateless thì chẳng quan trọng, vì server nào cũng như nhau. Nhưng nếu mỗi server gắn một Redis cache riêng trong memory (không phải cache dùng chung), và server cache dữ liệu cho user của nó, thì server 0 không bao giờ cache gì cho user 7.

Với round robin, lúc này user 6 vào server 0 và được cache, lần sau lại vào server khác: server đó tra cache, không thấy, làm lại từ đầu. Hashing hợp khi muốn request của một user map nhất quán về cùng server, để làm được những việc như cache ở mức server.

Hình 2 — Cache riêng từng server chỉ có ích khi user luôn về cùng server
▸ Ví dụ của nguồn — user 6
HashingUser 6 luôn vào server 0, cache ở đó luôn dùng được.
Round robinUser 6 lúc vào server 0, lúc vào server khác; server kia không có cache, phải xử lý lại.
03. Vấn đề khi bớt server ~06:00–11:00

Đổi từ mod 3 sang mod 2 làm cả những user có server vẫn sống bị chuyển đi — cache của họ thành vô dụng

Ví dụ mới: 9 mod 3 = 0, 10 → 1, 11 → 2. Bỏ server 2 — có thể nó crash, hoặc không đủ tiền nuôi ba server, hoặc hai là đủ cho traffic còn lại. Lý tưởng: user đang ở server 0 và 1 ở yên chỗ cũ; chỉ khoảng một phần ba user của server 2 phải dời, chia đôi 50/50 sang hai server còn lại. Đó là điều consistent hashing làm.

Nhưng còn hai server thì hàm hash đổi thành mod 2: 9 mod 2 = 1, nên user 9 rời server 0; user 10 sang server 0 — hai người đổi chỗ cho nhau; user 11 sang server 1. Có thể còn user 14, 17… (ví dụ này thậm chí không chia đều). Điều ta muốn xảy ra thì không, mà ngược lại: dữ liệu cache của user 9 ở server 0 và của user 10 ở server 1 đều vô dụng. Tải vẫn đều, nhưng không thông minh. Nếu server không có cache riêng thì consistent hashing chẳng quan trọng; nó không phải giải pháp tốt nhất cho mọi trường hợp.

▸ Ví dụ của nguồn — từ mod 3 sang mod 2
         mod 3     mod 2
user  9 → 0      → 1   // bị chuyển dù server 0 vẫn sống
user 10 → 1      → 0   // bị chuyển dù server 1 vẫn sống
user 11 → 2      → 1   // phải chuyển vì server 2 đã bỏ
04. Vòng tròn consistent hashing ~11:00–18:00

Đặt server và request trên một vòng tròn; request đi theo chiều kim đồng hồ tới server đầu tiên, nên bớt hay thêm server chỉ ảnh hưởng một vùng

Ở mức cao (chi tiết toán học không giúp gì cho system design): server được đặt trên một không gian tròn, ví dụ 0°, 120°, 240°. Hàm hash không map request thẳng vào server mà map vào một điểm trên vòng. Từ điểm đó đi theo chiều kim đồng hồ tới server (node) đầu tiên. Lúc đầu kết quả y như hashing cơ bản: tải chia khá đều.

Khác biệt nằm ở khi bỏ server. Hàm hash không phải IP mod n; ví dụ là mod một số cố định như 360, và server được đặt khéo cho cách đều. Nên bỏ một server thì hàm hash không đổi: user 9, 10 vẫn về chỗ cũ, cache vẫn dùng được. Chỉ request ở vùng của server đã mất đi tiếp chiều kim đồng hồ tới server kế tiếp — điều tốt nhất có thể, vì cache của server đã sập cũng mất theo. Nhược điểm trong hình: server nhận thêm sẽ gánh khoảng 2/3 traffic, server kia 1/3; có những tối ưu để chia đều hơn.

Hình 3 — Vòng tròn với ba server; bỏ S2 thì chỉ vùng của nó dời sang S0

Thêm server cũng vậy: chỉ những request ở vùng ngay trước server mới chuyển sang nó, phần còn lại giữ nguyên. Thêm server thường là để chịu tải lớn hơn, nên có thể thêm vài server rải khéo để mỗi server nhận lượng traffic tương đương. Ít nhất ta giảm tối đa số user phải sang server mới.

▸ Ví dụ của nguồn — bỏ server ở 240°

User 9 về server ở 0°, user 10 về server ở 120°: không đổi. User ở vùng trước 240° đi tiếp chiều kim đồng hồ, gặp server ở 0° (tức 360°). Kết quả: server 0° gánh khoảng 2/3 traffic.

05. Khi nào dùng ~18:00–21:00

Chỉ dùng khi thật cần map nhất quán — load balancer có cache riêng, CDN, database chia thành nhiều node

Consistent hashing là một công cụ cho một số trường hợp. Nếu server không cần map nhất quán từng user thì dùng cách đơn giản như round robin, vì nhược điểm của consistent hashing là phức tạp và đa số trường hợp không cần. Nó còn dùng để định tuyến request tới CDN, và được dùng nhiều trong database: thay server bằng các database node, mỗi node giữ một phần ba dữ liệu user để chịu thêm traffic; user phải tới đúng node chứa dữ liệu của mình, tới node khác thì chẳng có profile của họ.

Một thuật toán rất giống là rendezvous hashing: cùng mục tiêu, ở vài khía cạnh đơn giản hơn. Theo người nói, consistent hashing là đủ cho phỏng vấn; khác biệt giữa hai cái không lớn.

▸ Ví dụ của nguồn — ba database node

Dữ liệu user chia ba: mỗi node một phần ba. Request của một user phải về node chứa dữ liệu của họ; consistent hashing giữ việc map này ổn định khi số node thay đổi.

06. Ba thành phần ~21:00–23:00

Hash key nhận diện user, hash function chuẩn công nghiệp, và tập node có số lượng thay đổi

Hash key: ở đây là IP, nhưng có thể khác — miễn nhận diện được user để map nhất quán về một node. Hash function: chắc chắn không đơn giản như mod IP, mà là hàm chuẩn công nghiệp như SHA (secure hash algorithm) hay biến thể. Nodes: server khi làm load balancing, hoặc CDN server, hoặc database partition / shard. Số node tăng giảm theo thời gian — đó là lúc cần consistent hashing, nếu cần map request nhất quán về cùng một node.

Hình 4 — Ba thành phần
▸ Ví dụ của nguồn — ráp lại ví dụ load balancer
hash key      = IP của user
hash function = SHA (không phải IP mod n)
nodes         = 3 server → còn 2 khi một server sập

Ôn tập · Tự kiểm tra

Năm câu hỏi

Ba server, IP = 8. Server nào?

8 mod 3 = 2 → server 2. (→ 01)

Vì sao round robin làm hỏng cache riêng của từng server?

Cùng user có thể rơi vào server khác ở request sau; server đó không có cache nên phải xử lý lại. (→ 02)

Đang có 3 server, còn 2 thì user 10 đi đâu với mod n? Có hợp lý không?

10 mod 2 = 0 → server 0, dù server 1 cũ của họ vẫn sống: cache bị lãng phí, không hợp lý. (→ 03)

Trên vòng tròn, request được gán cho server nào?

Server đầu tiên gặp khi đi theo chiều kim đồng hồ từ điểm hash của request. (→ 04)

Kể ba nơi dùng consistent hashing và ba thành phần của nó.

Load balancer có cache riêng, CDN, database shard. Thành phần: hash key, hash function (vd SHA), nodes. (→ 05, 06)
