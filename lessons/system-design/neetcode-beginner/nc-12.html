Forward proxy che client, reverse proxy che server — và load balancer là reverse proxy chia đều tải

Chủ đề lớn, nhiều sắc thái, nhưng developer và người thiết kế hệ thống chỉ cần nắm khái niệm và vài trade-off.

01. Forward proxy ~00:00–04:30

Forward proxy đứng giữa, gửi request thay client và che danh tính client; nó cũng dùng để vượt hoặc áp đặt chặn truy cập

Có hai loại proxy chính. Nói "proxy" thường là forward proxy, nhưng không phải lúc nào cũng vậy, dễ nhầm. Client gửi request tới server qua một server ở giữa: server giữa nhận request rồi chuyển tiếp thay mặt client, đóng vai người dùng, và che client khỏi server đích. Request của bạn vốn mang IP của bạn; proxy giống một người bạn làm hộ. (Ví dụ người đưa thư không chuẩn lắm vì địa chỉ vẫn ghi trên phong bì.)

Vì mọi traffic đi qua proxy, nó còn dùng vào việc khác. Vượt chặn: quốc gia, máy hay mạng của bạn không được vào server đó, nhưng được vào proxy, thì proxy đi hộ. Chặn: mạng công ty hay trường học buộc mọi thiết bị đi qua proxy, và proxy đặt luật chặn một số trang, tài nguyên. Ví dụ thực tế: proxy công ty, và VPN — che IP, giả như bạn ở nước khác.

▸ Ví dụ của nguồn — chặn YouTube

Mạng công ty đôi khi chặn YouTube (người nói thấy khá bực). Proxy công ty thấy bạn định vào YouTube và từ chối, vì mọi traffic phải đi qua nó.

02. Reverse proxy ~04:30–07:30

Reverse proxy che server đích: client chỉ biết proxy, không biết có những server nào phía sau — CDN là một ví dụ

Forward proxy che client; reverse proxy không che client mà che server đích. User gửi request tới server này, nhưng nó không xử lý: nó nhận request cùng mọi thông tin (như IP — không bắt buộc nhưng thường có), chuyển cho server khác; server đó xử lý, trả về reverse proxy, reverse proxy trả cho client. Client không biết server đích tồn tại; server thường (không nhất thiết) biết client.

Ví dụ đã học: CDN. Forward hay reverse? User đi thẳng tới CDN để đọc dữ liệu; CDN có thể gọi origin server mà ta không biết và không quan tâm, lấy dữ liệu, cache rồi trả lại. CDN trừu tượng hoá origin khỏi ta: đó là reverse proxy. Một ví dụ phổ biến khác là load balancer.

▸ Câu hỏi nguồn đặt ra — CDN là loại proxy nào?

Reverse proxy: user chỉ nói chuyện với CDN; origin phía sau bị ẩn đi.

03. Load balancer ~07:30–09:30

Load balancer là reverse proxy đứng trước nhiều server giống nhau để chia đều traffic khi scale ngang

Load balancer rất quan trọng nhưng khái niệm khá đơn giản; cài đặt thật thì không, vì nhiều chi tiết networking. User gửi request tới load balancer trước; phía sau là nhiều server chạy cùng ứng dụng, cùng API, vì một server không kham nổi. Ta muốn scale ngang và chia đều traffic — "cân bằng tải".

Theo người nói, trong phỏng vấn điều này gần như buồn cười: load balancer cực phức tạp, nhưng ta chỉ nói "đặt một load balancer phía trước rồi scale ngang server" — giả định server viết bằng REST, stateless, nên scale được.

▸ Mẹo từ nguồn — câu nói quen trong phỏng vấn

"Tôi đặt một load balancer phía trước, scale ngang các server stateless." Đủ cho phỏng vấn, nhưng nên biết vài thuật toán và trade-off bên dưới.

04. Thuật toán chia tải ~09:30–14:00

Round robin chia lần lượt; weighted round robin theo sức máy; least connections tránh máy đang bận; ngoài ra còn theo vị trí và hashing

Round robin đơn giản nhất: request 1 tới server 1, request 2 tới server 2, request 3 tới server 3, request 4 quay lại server 1 — mỗi server nhận lượng traffic bằng nhau. Nhưng có thể vài server yếu hơn (ví dụ có 100 server mà một số yếu hơn): dùng weighted round robin. Server điểm 10, hai server điểm 5 — tức 50%, 25%, 25%: request 1 và 2 tới server 1, request 3 tới server 2, request 4 tới server 3. Server 1 mạnh gấp đôi nên xử lý gấp đôi: nếu nó nhận 4 request thì mỗi server kia nhận 2.

Least connections: chuyển tới server ít connection nhất. Round robin chia đều số request, nhưng có request lâu hơn — ví dụ request đầu đòi rất nhiều dữ liệu, xử lý lâu. Request thứ hai đã xong, request mới tới: server 1 vẫn đang bận, nên gửi sang server không có connection. Server ở nhiều nơi thì chia theo vị trí user: user Bắc Mỹ tới server Bắc Mỹ, châu Âu tới châu Âu, châu Á tới châu Á. Còn hashing: hash một trường của request — IP, nội dung, user ID… — lợi ích sẽ bàn ở bài sau.

05. Layer 4 & layer 7 ~14:00–17:30

Load balancer layer 4 chỉ nhìn IP nên nhanh; layer 7 đọc được HTTP nên định tuyến thông minh nhưng đắt hơn

Layer 4 ở tầng network thấp hơn — tầng transport, TCP. Layer 7 là tầng application: load balancer giống một HTTP server. Layer 4 thường nhanh hơn vì chỉ nhìn IP để chia (theo vị trí hoặc round robin), nhưng không thông minh được vì không truy cập dữ liệu ứng dụng, không giải mã, không biết user cần resource gì. Nó chỉ thay IP đích bằng IP của một server phía sau, chuyển tiếp, rồi trả response về client.

Layer 7 đọc được dữ liệu ứng dụng. Giả sử (người nói tự đặt ra) một server lo tweet, một server lo profile, một server lo authentication: layer 7 thấy request về tweet thì gửi server tweet, request auth thì gửi server auth. Mạnh hơn, nhưng có hai TCP connection (client–LB và LB–server), phải giải mã mỗi request rồi tạo request mới, nên đắt hơn. Phân biệt này nhiều khả năng sẽ không xuất hiện trong phỏng vấn.

Hình 3 — Layer 4 so với layer 7
Đính chính nguồn: câu tổng kết trong transcript là "layer 7 is faster but less flexible, layer 7 is slower but much more powerful" — người nói nhầm ở vế đầu. Đúng là: layer 4 nhanh hơn nhưng kém linh hoạt; layer 7 chậm hơn nhưng mạnh hơn nhiều.
▸ Ví dụ của nguồn — ba server, ba việc
Layer 4Chỉ thấy IP: chỉ chia được theo round robin hay vị trí.
Layer 7Thấy request là về tweet → server tweet; về auth → server auth.
06. Load balancer sập thì sao ~17:30–20:00

Một load balancer là single point of failure; giải pháp đơn giản là nhiều bản sao hoặc một bản dự phòng

Scale ngang server đã tăng availability và reliability: một server sập, load balancer chuyển request sang server khác. Nhưng chính load balancer sập thì sao? Nó là single point of failure. Dễ nhất là có nhiều bản sao load balancer nhận request, hoặc một load balancer dự phòng: bản chính sập thì chuyển sang bản kia. Load balancer chịu được lượng traffic và throughput rất lớn vì thường chỉ chuyển tiếp request, nên hiếm khi quá tải.

Năm câu hỏi

VPN là forward proxy hay reverse proxy?

Forward proxy: che IP của client, giả như ở nước khác. (→ 01)

CDN là forward proxy hay reverse proxy, vì sao?

Reverse proxy: user chỉ nói chuyện với CDN, origin phía sau bị ẩn. (→ 02)

Ba server trọng số 10, 5, 5. Trong 8 request, mỗi server nhận bao nhiêu?

4, 2, 2 (tức 50%, 25%, 25%). (→ 04)

Vì sao layer 7 đắt hơn layer 4?

Phải giải mã từng request, có hai TCP connection và tạo request mới; layer 4 chỉ đổi IP rồi chuyển tiếp. (→ 05)

Muốn tránh load balancer là single point of failure, làm gì?

Chạy nhiều bản sao load balancer, hoặc có bản dự phòng nhận request khi bản chính sập. (→ 06)
