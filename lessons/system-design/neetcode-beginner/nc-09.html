01. API contract ~00:00–04:00

API design chỉ lo bề mặt — thao tác gì trên entity nào, nhận gì trả gì — không lo phần cài đặt

Paradigm cho ta kiểm soát giao diện của API: surface area, hay API contract, mô tả cách dùng một API — Twitter API, Reddit API, YouTube API… Với Twitter: tạo tweet, xoá tweet (sửa tweet thì tới gần đây mới có, nên giả định là không), xem danh sách tweet cho home feed, like, retweet.

Phần lớn thao tác nằm trong CRUD trên các entity — danh từ, như tweet, cũng là resource. Bài này dùng REST nên động từ là HTTP method (GET, POST, PUT, DELETE); với framework RPC như gRPC thì động từ nằm trong tên endpoint. Giống viết hàm: không quan tâm cài đặt, chỉ quan tâm tham số vào và giá trị ra.

▸ Ví dụ của nguồn — tạo tweet như gọi hàm

Gọi "tạo tweet" thì mong nhận lại chính tweet đó, hoặc một error code cho biết vì sao không được. Bên trong làm gì không thuộc API design.

02. Endpoint tạo tweet ~04:00–07:00

Tạo tweet là POST với body JSON chứa userId và content

Hàm tạo tweet cần userId của người tạo và content — nội dung chữ. Twitter, và phần lớn API công khai, dùng REST: đây là POST vì tạo resource trên server. Tham số không nằm trong định nghĩa endpoint mà trong body, dạng cặp key–value — giả sử JSON vì phổ biến nhất. Không phức tạp, giống định nghĩa interface hay class, nhưng phải rất cẩn thận vì đây là API công khai.

▸ Ví dụ của nguồn — POST tạo tweet
POST /v1/tweet
{
  "userId": "…",
  "content": "nội dung tweet"
}
03. Backwards compatibility ~07:00–10:00

Thêm tham số tuỳ chọn thì backwards compatible; thêm tham số bắt buộc thì làm hỏng 100% client hiện tại

Twitter mới ra mắt, rồi muốn thêm tính năng trả lời tweet: một tweet là reply của một tweet khác. Thêm tham số parentId — ID của tweet cha. Nếu parentId là tuỳ chọn thì ổn: ai muốn reply thì truyền, còn mọi người đang dùng endpoint cũ chỉ truyền hai tham số vẫn chạy. Đó là backwards compatible: người dùng bản cũ không bị hỏng.

Nếu parentId bắt buộc, đẩy thay đổi lên sẽ làm hỏng đúng 100% người dùng hiện tại cho tới khi họ sửa request — dù sửa có thể dễ. Vì vậy phải rất cẩn thận với API design.

Hình 2 — Cùng một tính năng reply, hai cách thêm tham số
▸ Ví dụ của nguồn — thêm reply
createTweet(userId, content)               // bản đầu
createTweet(userId, content, parentId?)   // ✓ tuỳ chọn: client cũ vẫn chạy
createTweet(userId, content, parentId)    // ✗ bắt buộc: client cũ hỏng
04. Versioning ~10:00–11:30

Khi buộc phải thay đổi không tương thích, ra version mới để bản cũ và bản mới cùng tồn tại

Đôi khi buộc phải thêm tham số bắt buộc hay thiết kế lại cả API: không còn backwards compatible. Lúc đó cần versioning. Đa số API có version, thường là phần đầu của path. Ra version mới thì không làm hỏng API gốc: hai version cùng tồn tại.

▸ Ví dụ của nguồn — cách đặt version
  • /v1/tweet: version ở đầu path, cách phổ biến.
  • Twitter (theo người nói) không dùng chữ "v", chỉ có số; Stripe thì có "v". Chi tiết nhỏ.
05. Entity tweet ~11:30–15:00

Client chỉ gửi userId và content; id, thời điểm tạo và số like do server tạo

Tweet được tạo ở server và có thông tin client không truyền vào. Mỗi tweet có userId của người tạo ("creator" có lẽ là tên hay hơn), và id riêng vì userId không đủ để định danh mỗi tweet. ID phải duy nhất toàn cục nên tạo ở server — chi tiết cài đặt, client không gửi.

content do client gửi. createdAt về kỹ thuật client tạo được rồi server kiểm tra hợp lý, nhưng không nên: tweet được tạo ở server nên server chịu trách nhiệm thời điểm tạo. likes ban đầu là 0, cũng do server; like và unlike là chức năng phải thêm vào API.

Hình 3 — Phần client gửi và phần server tự sinh
▸ Ví dụ của nguồn — tweet sau khi tạo (đã đơn giản hoá)
{
  "id": "…",          // server tạo, duy nhất
  "userId": "…",      // client gửi
  "content": "…",     // client gửi
  "createdAt": …,     // server tạo
  "likes": 0          // server, ban đầu 0
}
06. Đọc & xoá một tweet ~15:00–17:00

GET và DELETE dùng chung path có URL parameter :id; quyền xoá là việc của backend

Phải đọc được tweet sau khi tạo, kể cả tweet của người khác. Endpoint gần giống: thêm một URL parameter — /v1/tweet/:id không có nghĩa URL chứa chữ "id", mà là giá trị tweet ID thật. GET đọc tweet và mọi thông tin của nó. DELETE xoá tweet, nhưng chỉ khi ta là người tạo: có lẽ phải truyền userId và backend còn authentication, authorization — thường nằm ngoài phạm vi API design.

Hình 4 — Bộ endpoint của ví dụ Twitter
▸ Ví dụ của nguồn — cùng path, khác method
GET    /v1/tweet/:id    // đọc một tweet
DELETE /v1/tweet/:id    // xoá, nếu là người tạo
07. Liệt kê tweet & pagination ~17:00–22:00

Liệt kê dữ liệu lớn phải có pagination; limit và offset nên tuỳ chọn với giá trị mặc định hợp lý

Một user có thể có hàng nghìn, thậm chí hàng trăm nghìn tweet. Trả hết trong một request có thể làm crash trình duyệt, và chẳng ai muốn xem chừng ấy. Nên dùng pagination, rất quan trọng khi liệt kê lượng dữ liệu lớn, với hai tham số. limit: số kết quả tối đa — limit 10 mà user có 100 tweet thì thấy 10 đầu (có thể sắp theo createdAt); user chỉ có 1 tweet thì chỉ thấy 1. offset: điểm bắt đầu — 0 là đầu, 10 là sau 10 cái đầu, hoặc vị trí bất kỳ như 2500.

GET không có body nên tham số phải nằm trong URL, dạng URL parameter hoặc query parameter. Không dùng lại /v1/tweet/:id được vì path đó dành cho đọc một tweet theo tweet ID. Endpoint mới: /v1/users/:id/tweets — bắt đầu từ resource users, ID đứng sau resource mà nó áp dụng, rồi tới resource tweets. Query param nên tuỳ chọn: thiếu offset thì mặc định 0; thiếu limit không có nghĩa là trả 100.000 tweet, mà là một mặc định hợp lý như 50 hay 20.

▸ Ví dụ của nguồn — endpoint liệt kê
GET /v1/users/:id/tweets?limit=10&offset=0     // 10 tweet đầu
GET /v1/users/:id/tweets?limit=10&offset=10    // 10 tweet tiếp
GET /v1/users/:id/tweets                        // offset=0, limit mặc định (vd 20 hoặc 50)
08. Mẹo phỏng vấn & GET idempotent ~22:00–26:00

Trong phỏng vấn, viết endpoint như một hàm và tập trung vào entity; tuyệt đối không tạo dữ liệu bằng GET

Phỏng vấn thường mở (có thể dùng gRPC chứ không nhất thiết REST), nên tốt nhất là được viết endpoint như một hàm, như createTweet(userId, …) trả về một entity tweet: thấy rõ input/output, khỏi lo cài đặt. Điều lớn nhất là entity nào: tweet, user — gần như chỉ vậy — nhưng rất nhiều quan hệ: user có tweet, user like tweet, user follow nhau. Đi sâu thì vẫn chỉ chạm bề mặt.

GET chỉ để đọc, không tạo resource. GET được giả định idempotent: cùng tham số thì sau lần gọi đầu luôn cùng kết quả; đọc tweet bao nhiêu lần tweet cũng không đổi. Quan trọng vì GET được cache mặc định. Về kỹ thuật, code server vẫn có thể tạo hay sửa tweet khi nhận GET — không gì ngăn cả — nhưng là thực hành rất tệ. Lỗi hiển nhiên, nhưng người nói thấy ít ai nhắc.

▸ Mẹo từ nguồn — cách viết trong phỏng vấn
createTweet(userId, content, parentId?) → Tweet
getTweet(tweetId) → Tweet
listUserTweets(userId, limit?, offset?) → Tweet[]

Tên hàm getTweet và listUserTweets là minh hoạ thêm theo cùng cách nguồn viết createTweet.

09. Twitter API v2 ~26:00–30:00

Tài liệu thật: path có version, rate limit 200 request mỗi 15 phút, body JSON phần lớn tuỳ chọn, và pagination token thay offset

Tài liệu Twitter API v2 (còn các version khác). Mục manage tweets có endpoint với path /2/tweets — "2" là version, ghép vào base URL của Twitter API. Tạo tweet không cần truyền tweet ID vì server lo; xoá thì phải truyền ID của tweet đã có. Trang POST tweet ghi URL đầy đủ và rate limit: không thể để một user gửi cả tỉ request mỗi giây làm sập API; ở đây là 200 request mỗi cửa sổ 15 phút.

API công khai cần tài liệu tốt; comment tốt trong code có thể sinh ra tài liệu như thế. Body POST là JSON, và gần như mọi trường đều tuỳ chọn — tốt cho backwards compatibility. User timeline: /2/users/:id/tweets, GET, nên một path parameter (user ID) cùng các query parameter. max_results mặc định tối đa 10 tweet nếu không chỉ định. Thay vì offset, thực tế phổ biến hơn là pagination token: request đầu trả về token, truyền token đó vào request sau để lấy tiếp, mỗi lần nhận token mới.

Hình 5 — Pagination token và rate limit trong Twitter API v2
▸ Ví dụ của nguồn — user timeline
GET /2/users/:id/tweets?max_results=10
→ 10 tweet + token
GET /2/users/:id/tweets?max_results=10&pagination_token=<token>
→ 10 tweet tiếp + token mới

Tên tham số pagination_token theo tài liệu Twitter; video gọi chung là "pagination token".

10. Stripe API ~30:00–32:00

Stripe cho field "expandable": mặc định trả ID, muốn thì mở rộng thành cả object — gần giống quyền chọn của GraphQL

Nên đọc API công khai của trang bạn thích; đa số mạng xã hội có. Tài liệu Stripe rất tốt, dễ đọc hơn, nhưng vì về thanh toán nên có khái niệm như payment intent khó hiểu nếu chưa dùng. Object payment intent rất lớn và gắn với một customer; Stripe làm field customer expandable: mặc định trả customer ID, khi request có thể chọn mở rộng thành cả object customer — không cần thì đừng mở rộng.

Tóm lại, mới chạm bề mặt API design, nhưng cốt lõi là: backwards compatible, endpoint định nghĩa rõ và không xung đột nhau, và có pagination.

▸ Ví dụ của nguồn — payment intent
Mặc định"customer": "cus_…" — chỉ ID.
Expand"customer": { … } — cả object customer.

Giá trị "cus_…" là minh hoạ thêm cho dạng ID của Stripe.

Năm chỗ dễ nhầm

✗ Thêm tham số mới vào API công khai lúc nào cũng an toàn.
✓ Chỉ an toàn khi tham số tuỳ chọn; bắt buộc thì hỏng mọi client cũ (→ 03).
✗ Client nên gửi id và createdAt khi tạo tweet.
✓ Server tạo id duy nhất và chịu trách nhiệm thời điểm tạo (→ 05).
✗ Không truyền limit thì trả về tất cả.
✓ Dùng mặc định hợp lý như 20 hay 50 (→ 07).
✗ GET tạo dữ liệu cũng được, server cho phép mà.
✓ GET phải idempotent vì được cache mặc định (→ 08).
✗ API thật luôn phân trang bằng offset.
✓ Thực tế phổ biến hơn là pagination token (→ 09).

Ôn tập · Tự kiểm tra

Sáu câu hỏi

API contract là gì?

Bề mặt của API: thao tác nào, tham số vào, kết quả ra; không gồm cài đặt. (→ 01)

Vì sao parentId phải là tuỳ chọn?

Để backwards compatible: client cũ chỉ gửi userId và content vẫn chạy. Bắt buộc thì 100% client cũ hỏng. (→ 03)

Khi nào cần ra version mới như /v2?

Khi buộc phải thay đổi không tương thích (tham số bắt buộc mới, thiết kế lại); bản cũ và mới cùng tồn tại. (→ 04)

Endpoint liệt kê tweet của một user nên có path gì, vì sao không dùng /v1/tweet/:id?

/v1/users/:id/tweets với query param limit, offset. /v1/tweet/:id đã dành cho đọc một tweet theo tweet ID. (→ 07)

Rate limit của endpoint tạo tweet trong Twitter API v2 là bao nhiêu? Một user muốn đăng 1.000 tweet thì cần tối thiểu bao lâu?

200 request mỗi 15 phút. 1.000 / 200 = 5 cửa sổ, tức khoảng 75 phút (tính toán minh hoạ thêm). (→ 09)

Field expandable của Stripe giống GraphQL ở điểm nào?

Client chọn lấy thêm object liên quan (customer) hay chỉ ID, tránh dữ liệu thừa. (→ 10)
