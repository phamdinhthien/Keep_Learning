01. CDN là gì ~00:00–03:00

CDN là mạng server rải khắp thế giới giữ bản sao dữ liệu gần user; nó chỉ chứa nội dung tĩnh, không chạy code

Content delivery network (CDN) cache dữ liệu gần user, để khỏi phải gửi request qua cả thế giới. Ta có một origin server và các CDN server. Server của mình có thể chỉ ở một khu vực, còn user ở khắp nơi, nên muốn dữ liệu gần user ở mọi khu vực. Hình vẽ chỉ có một origin và khoảng năm CDN; thực tế có thể hàng trăm hay hàng nghìn CDN server.

Nhược điểm: không đặt mọi thứ lên CDN được. CDN server khá "ngu": chỉ chứa nội dung tĩnh, không chạy application code. Có thứ mới gọi là edge server, cho chạy code trên server phân tán gần user, nhưng còn rất mới nên nằm ngoài phạm vi bài.

▸ Ví dụ của nguồn — user trên du thuyền

Người nói dời user ra xa origin trên hình (đùa là đang ở trên du thuyền hay máy bay) để thấy rõ: user ở xa thì nên lấy dữ liệu từ CDN gần mình thay vì đi tới origin.

02. Nội dung tĩnh trên CDN ~03:00–05:30

JavaScript, ảnh, video giống nhau với mọi user nên đặt bản sao khắp nơi được — giảm latency, giảm tải origin, tăng availability

File JavaScript ở bài trước giống hệt với mọi user cho tới khi người nói sửa code, nên được host trên CDN và không cần chạm origin mỗi lần. Còn nhiều loại nội dung tĩnh: ảnh, video. Ảnh tháp Eiffel thì ai xem cũng giống nhau; không cần nằm ở origin nơi chạy code, đặt bản sao khắp thế giới là được.

Lợi ích: đường đi ngắn hơn nên latency thấp hơn; giảm tải cho origin; và tăng availability, reliability: một CDN server sập thì dùng CDN gần kế tiếp.

▸ Ví dụ của nguồn — ảnh tháp Eiffel
Không CDNAi muốn xem ảnh cũng phải đi tới origin, dù ở đâu.
Có CDNẢnh đã nằm sẵn ở CDN gần mỗi user; CDN đó sập thì dùng CDN gần kế tiếp.
03. Push CDN & pull CDN ~05:30–10:00

Push CDN đẩy dữ liệu ra mọi CDN ngay khi có; pull CDN chỉ lấy từ origin khi có user hỏi, như cache truyền thống

Ví dụ Twitter: server xử lý tạo, xoá tweet… còn ảnh đại diện là ảnh tĩnh, không đổi trừ khi user đổi ảnh, nên host trên CDN được. Push CDN: user upload ảnh lên origin, và ngay sau đó dữ liệu được đẩy tới mọi CDN server. Client ở đâu cũng vào CDN gần nhất.

Pull CDN giống ví dụ caching truyền thống: upload xong không đẩy đi đâu cả. User mở trang cá nhân của ai đó, cần ảnh tròn ở góc trên: trước hết hỏi CDN gần nhất. Chưa có → cache miss; CDN đóng vai proxy thay mặt user đi hỏi origin. Origin trả về, CDN cache lại và trả cho user; user khác gần CDN đó lần sau sẽ là cache hit. Người ở nửa kia thế giới có thể chẳng bao giờ xem ảnh đó, nên không cần đẩy sang đó. Pull hợp khi mỗi khu vực quan tâm dữ liệu khác nhau.

Hình 2 — Push đẩy đi mọi nơi; pull chỉ lấy khi có người hỏi
▸ Ví dụ của nguồn — chuối và siêu thị

Có nước trồng rất nhiều chuối, rồi chuối được chở tới các siêu thị. Người mua chỉ cần lái xe ra siêu thị gần nhà, không phải đi nửa vòng trái đất tới nơi trồng. CDN cũng đưa dữ liệu tới gần người dùng như vậy.

04. Demo trên twitter.com ~10:00–13:30

Twitter tải JavaScript đăng nhập Apple từ CDN của Apple; chỉ phần động, khác nhau theo user, mới phải đi tới origin

Mở DevTools, lần này là tab Elements để xem HTML. Gần cuối trang có script tải từ một CDN — có vẻ là JavaScript cho Apple authentication, chức năng "sign up with Apple". Mở URL đó: code JavaScript do Apple viết, khó đọc, nhưng tĩnh và ít đổi. Mọi user mở twitter.com đều tải nó.

Twitter có thể tự host bản sao trên server mình, hoặc cài package nếu có, nhưng họ dùng CDN do Apple cung cấp, nên user tải nó từ server gần mình thay vì từ server Twitter. Ta vẫn phải đi tới server Twitter cho những thứ không tránh được: trang cá nhân, đăng nhập… Ý tưởng là tách một phần dữ liệu (ảnh, JavaScript, đồ của Apple) thành bản sao tĩnh rải khắp CDN, để phần phải đi cả quãng xa nhỏ đi. Làm được với tất cả thì đã làm, nhưng có thứ không tĩnh: khác nhau với mỗi user mỗi lần mở trang, gần như luôn xảy ra khi có authentication — mỗi người một feed, một nội dung khác.

▸ Ví dụ của nguồn — tách dữ liệu của twitter.com
Từ CDNẢnh, JavaScript, script Apple ID: giống nhau với mọi user.
Từ originTrang cá nhân, đăng nhập, feed: khác nhau theo từng user.
05. Cache-Control: public ~13:30–16:00

public cho phép server ở giữa như CDN cache response; private nghĩa là CDN không được cache

Tab Network lọc "CDN" thấy lại script Apple ID. Lần này Cache-Control có nhiều giá trị: max-age khoảng 86.000 giây và vài thứ khác. Đáng chú ý là giá trị public. Về phạm vi, Cache-Control có thể không ghi gì (như bài trước), private, hoặc public.

public: được cache trên các server khác ngoài trình duyệt của user, ví dụ một tầng ở giữa như CDN. private: không được cache bởi CDN server. Điều này liên quan tới pull CDN: client hỏi CDN, CDN không có, hỏi origin; origin trả về, CDN thấy header public thì cache lại, rồi trả ngay cho mọi user sau mà không phải về origin. Điều quan trọng nhất của cả bài: đưa dữ liệu tới gần user thì nhanh hơn.

Hình 3 — CDN đọc Cache-Control để quyết định có cache hay không
Video đọc max-age là "86,000 seconds". Giá trị phổ biến cho một ngày là 86400 giây; khả năng cao header thật là max-age=86400. Hình 3 dùng 86400 với ý nghĩa minh hoạ.
▸ Ví dụ của nguồn — script Apple ID
Cache-Control: public, max-age=~86000, …
// public → CDN ở giữa được phép cache script này
// nếu là private → CDN không cache

Ôn tập · Tự kiểm tra

Năm câu hỏi

Ba lợi ích của việc đặt nội dung lên CDN?

Latency thấp hơn (đường ngắn hơn), giảm tải origin, tăng availability và reliability (CDN sập thì dùng CDN gần kế tiếp). (→ 02)

Trong pull CDN, khi cache miss thì CDN làm gì?

Đóng vai proxy: hỏi origin thay user, nhận dữ liệu, cache lại rồi trả cho user. (→ 03)

Ứng dụng phần lớn user ở một quốc gia, nhưng có ảnh đại diện mà user ở mọi nơi đều xem. Push hay pull?

Push hợp nếu ảnh được xem ở mọi khu vực; nếu mỗi khu vực xem ảnh khác nhau thì pull tiết kiệm hơn. (Tình huống minh hoạ thêm → 03)

Vì sao twitter.com không đặt hết lên CDN?

Có nội dung động khác nhau theo user (đăng nhập, feed), không phải nội dung tĩnh. (→ 04)

Cache-Control: private nói gì với CDN?

Không được cache response đó ở CDN. (→ 05)
