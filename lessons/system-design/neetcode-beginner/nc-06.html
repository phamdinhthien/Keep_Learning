NeetCode · System Design Beginner · Video 6

HTTP là giao thức request–response chạy trên TCP; thêm TLS thành HTTPS để chống nghe lén

Với developer, HTTP là cách chạy code trên máy khác và nhận kết quả, như gọi một hàm trong chính codebase của mình.

01. Client–server ~00:00–03:00

"Client" chỉ là bên khởi tạo request — có thể là trình duyệt, cũng có thể là một server khác

Bài này đi qua mô hình client–server, RPC, rồi các giao thức tầng ứng dụng, chủ yếu là HTTP và một chút WebSockets — hữu ích nhất cho phỏng vấn system design. Giả định quen thuộc: client là người dùng cuối, dùng trình duyệt trên desktop hay laptop, gửi request tới server như google.com và nhận response.

Nhưng client không cần là người dùng, trình duyệt hay điện thoại. Client là thuật ngữ chung cho bên khởi tạo request. Server thường là máy trong một nhà kho hay data center, nhiệm vụ là nhận và thực hiện request. Server cũng gọi nhau: khi đó một server đóng vai client.

▸ Ví dụ của nguồn — google.com gọi dịch vụ bên thứ ba

google.com dùng một dịch vụ bên thứ ba, cũng là một server. Lúc gọi dịch vụ đó, server của Google là client, còn dịch vụ kia là server.

02. RPC ~03:00–06:30

RPC là gọi một "hàm" nằm trên máy khác qua network; gần như mọi giao thức ứng dụng về bản chất đều là RPC

RPC là remote procedure call. Remote nghĩa là hai máy cách nhau bởi network; procedure call giống như gọi hàm. Code JavaScript trong trình duyệt được tổ chức thành class, hàm, và ta gọi hàm được. Còn code nằm trên server thì sao?

Ta gọi một dòng code trông như local ở client, nhưng bên dưới là một network call; server chạy code và trả kết quả. Người nói thấy đây là thuật ngữ khá lỗi thời và mơ hồ — gần như mọi network call đều khớp định nghĩa — nhưng nhắc tới vì các giao thức tầng ứng dụng về cốt lõi đều là RPC. Khóa học tập trung vào những thứ được định nghĩa rõ như HTTP.

Hình 2 — listVideos() trông như hàm local, nhưng code thật ở server
▸ Ví dụ của nguồn — feed của YouTube

Đang ở youtube.com, muốn liệt kê video trong feed. Code tạo feed nằm trên server của Google, trình duyệt không có. Ta gọi kiểu listVideos(), server chạy code và trả về danh sách video.

03. HTTP ~06:30–09:00

HTTP chạy trên IP và TCP, theo mô hình request–response, và không giữ state giữa client với server

IP chuyển dữ liệu giữa các máy, TCP làm việc đó đáng tin cậy — đó là hạ tầng tối thiểu. HTTP là giao thức tầng ứng dụng xây trên IP và TCP, và là thứ developer thật sự kiểm soát. Chỉ cần nắm ý lớn, chi tiết nhỏ không đáng học thuộc.

Điều lớn nhất: HTTP là request–response. Client gửi request (req) mô tả code nào trên server cần chạy; server chạy rồi trả response (res), có thể là thứ ta muốn hoặc một lỗi. Bên dưới vẫn có TCP connection, handshake và mọi chi phí đi kèm, nhưng developer không thấy. Không có state giữa client và server: mọi thứ cần thiết nằm trong request và response.

▸ Ví dụ của nguồn — hai mảnh của một lần giao tiếp
RequestClient khởi tạo: muốn chạy gì trên server.
ResponseServer trả kết quả, hoặc báo lỗi đã xảy ra.
04. Demo DevTools ~09:00–15:00

Tab Network của DevTools cho thấy mỗi request có general header, request header, response header và body

HTTP có mặt mỗi lần bạn tìm kiếm hay mở một trang. Trang thường dùng HTTPS, biến thể an toàn hơn; xoá chữ S rồi Enter thì YouTube redirect về HTTPS, đa số website làm vậy. Chuột phải → Inspect mở DevTools, tab Network hiện mọi request; lọc được theo name, status, type, initiator. Bật cột protocol thấy h3, tức HTTP/3, phiên bản mới nhất.

Mỗi request có hai phần: header và body. Header chia ba nhóm. General header: URL, path, request method (ở đây là GET; phổ biến nhất là GET, POST, PUT, DELETE) và status code (200, màu xanh, thành công). Request header do client đặt: authority (base URL), method, path, user-agent (người nói dùng Chrome), accept (định dạng chấp nhận). Response header do server đặt, ví dụ content-type thực tế trả về là text/html.

▸ Ví dụ của nguồn — tìm "neetcode" trên YouTube
// general
URL:      https://www.youtube.com/results?search_query=neetcode
Method:   GET      Status: 200      Protocol: h3
// request header (client đặt)
:authority  www.youtube.com    user-agent  …Chrome…    accept  text/html,…
// response header (server đặt)
content-type  text/html   // body bắt đầu bằng <!DOCTYPE html>

Tên trường đúng theo video; giá trị đầy đủ được viết lại để dễ đọc.

05. Route & endpoint ~15:00–17:00

Một URL là một route; mỗi cặp route + method là một endpoint riêng với chức năng riêng

Mọi request đi tới một URL. Nếu đó là API, URL gọi là API route. Một route phục vụ được nhiều HTTP method; route kết hợp một method là một endpoint. GET tới youtube.com là một endpoint; POST tới chính URL đó là endpoint khác với chức năng khác.

Hình 3 — Cùng route, hai method, hai endpoint
▸ Ví dụ của nguồn — youtube.com

GET youtube.com → server trả trang HTML của YouTube. POST youtube.com → "tôi không biết, có thể tạo tài khoản" (ví dụ giả định của người nói). Cùng URL, khác method, khác endpoint.

06. HTTP method ~17:00–22:00

GET để đọc và không có body; POST để tạo; PUT để cập nhật; DELETE để xoá — tương ứng CRUD

GET dùng để lấy thông tin: trang chủ YouTube, danh sách video khi tìm "neetcode". Về lý thuyết GET cũng tạo được dữ liệu, ví dụ nhét username và password vào URL để tạo tài khoản — nhưng không an toàn, ai nhìn URL cũng thấy mật khẩu. GET request không có body, chỉ có header, nên mọi thông tin thêm phải nằm trong URL.

POST dùng để tạo: tài khoản, comment, upload video. POST và các method còn lại có body chứa dữ liệu tuỳ ý: loại tài khoản, nội dung comment, mọi kiểu form. PUT giống POST nhưng là cập nhật. Gom lại thành CRUD: create (POST), read (GET), update (PUT), delete (DELETE).

Khác biệt nữa liên quan tới caching. GET đọc tài nguyên, không làm nó thay đổi, nên idempotent và dễ cache. POST tạo tài nguyên, mỗi lần gọi lại làm thêm một hành động, nên không idempotent, không cache được. DELETE thường idempotent. Người nói cho rằng phần này không quá quan trọng.

Về kỹ thuật, đặc tả HTTP không cấm GET có body, nhưng body đó không có ý nghĩa và hầu như không được dùng; cách nói "GET không có body" của video là đúng trong thực tế.
▸ Ví dụ của nguồn — POST trong tab Network

Một POST request ngẫu nhiên của YouTube tới api/stats/… (có vẻ là dữ liệu analytics). Tab Payload là body: nhiều tham số và dữ liệu, không dễ đọc, nhưng cho thấy body chứa được dữ liệu bất kỳ.

07. Status code ~22:00–26:00

Status code cho client biết request thành công, lỗi do mình hay lỗi do server

Server gặp sự cố không xử lý được, hay client gửi request không hợp lệ — client cần biết lỗi của ai, hoặc mọi thứ ổn. Đó là việc của status code, một phần của giao thức HTTP. TCP không cần thứ này, nhưng ở mức HTTP thì rất hữu ích. Không bắt buộc dùng đúng: có người trả status code vô nghĩa, nhưng đó là thiết kế API tệ. Không cần học thuộc từng mã.

Hình 4 — Các status code được nhắc trong video, theo ba nhóm
Đính chính nguồn: 500 là Internal Server Error (video nói "internal service error"). Với ví dụ xoá video của người khác, mã thường dùng hơn là 403 Forbidden (đã đăng nhập nhưng không có quyền); 401 hợp hơn khi chưa xác thực.
▸ Ví dụ của nguồn — mỗi mã một tình huống
  • 200: request OK, trang tải với danh sách video.
  • 201: tài nguyên đã được tạo, ví dụ thêm comment — thường đi với POST.
  • 400: bad request, ví dụ chuỗi tìm kiếm có ký tự đặc biệt như dấu * mà server từ chối parse.
  • 401: unauthorized, ví dụ xoá video không phải của mình.
  • 404: không tìm thấy tài nguyên.
  • 500 / 502 / 503: lỗi server, bad gateway, service unavailable — hiếm gặp hơn.
08. SSL/TLS & HTTPS ~26:00–30:00

HTTPS là HTTP cộng TLS: mã hoá dữ liệu để kẻ đứng giữa không đọc được, chống man-in-the-middle

HTTP là hypertext transfer protocol; chữ S là secure, hay HTTP với SSL. SSL (secure socket layer) có trước; người ta vẫn nói SSL dù đã lỗi thời. TLS (transport layer security) được dùng rộng rãi hơn nhiều. Chỉ cần mức cao vì không quá quan trọng cho system design.

HTTP không tự chống man-in-the-middle attack (MITM). Gửi dữ liệu như gửi đồ trong thùng carton trong suốt có túi tiền bên trong: ai thấy thùng trên đường cũng thấy và lấy được. Network không đáng tin cũng không an toàn: ngồi quán cà phê dùng Wi-Fi công cộng, request có thể bị theo dõi. TLS mã hoá: mật khẩu 1234 thành chuỗi như XYZ; server giải mã ra 1234; dữ liệu gửi về cũng được mã hoá.

Hình 5 — Có TLS, kẻ nghe lén chỉ thấy chuỗi đã mã hoá

Vào trang như neverssl, góc trên trình duyệt báo "not secure". Không có nghĩa là sẽ nhiễm virus, chỉ là mọi dữ liệu bạn gửi — như mật khẩu — có thể bị người nghe lén thấy. Sau tất cả các bài về networking, HTTPS là đích đến: tin cậy, dễ dùng, an toàn, và gọi như hàm local dù chạy trên máy khác qua network.

▸ Ví dụ của nguồn — mật khẩu 1234
HTTPKẻ nghe lén trên Wi-Fi quán cà phê thấy rõ "1234".
HTTPSTrên đường truyền chỉ là "XYZ"; server giải mã ra 1234.

Sáu câu hỏi

RPC là gì, và vì sao người nói coi nó là thuật ngữ mơ hồ?

Remote procedure call: gọi code trên máy khác qua network như gọi hàm local. Mơ hồ vì gần như mọi network call đều khớp định nghĩa. (→ 02)

Ba nhóm header trong DevTools là gì, ai đặt mỗi nhóm?

General header (URL, method, status), request header do client đặt (user-agent, accept…), response header do server đặt (content-type…). (→ 04)

Route và endpoint khác nhau thế nào?

Route là URL; endpoint là route kết hợp một HTTP method, mỗi endpoint một chức năng. (→ 05)

Vì sao GET dễ cache còn POST thì không?

GET chỉ đọc, gọi lại không đổi tài nguyên (idempotent). POST tạo tài nguyên, mỗi lần gọi lại làm thêm hành động. (→ 06)

Người dùng gõ chuỗi tìm kiếm không hợp lệ. Server nên trả mã nhóm nào? Server sập thì sao?

4xx, cụ thể 400 Bad Request — lỗi của client. Server sập: 5xx như 500, 502, 503. (→ 07)

TLS chống được loại tấn công nào, bằng cách nào?

Man-in-the-middle: mã hoá dữ liệu (1234 → XYZ) nên kẻ nghe lén không đọc được; server giải mã. (→ 08)
