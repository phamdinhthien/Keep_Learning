01. Bối cảnh 00:00–01:40

Dùng Modern DevTools để debug chính ModernDevTools.com: course notes bài 1 mở rất nhanh, bài 3 hơi khựng, lần nào cũng vậy

Bài này "inception": debug một vấn đề hiệu năng trên trang khoá học. Tất cả xoay quanh Node.js; chưa dùng Node vẫn theo được, nhưng tác giả cho rằng biết thêm Node làm frontend developer giá trị hơn nhiều. Chủ đề Node được nhiều người bình chọn trong một GitHub issue hỏi ý kiến người học.

Course notes là phần chữ dưới mỗi video. Đi qua danh sách bài: bài 1 rất nhanh, bài 3 có một chút "stutter", không snappy bằng, và ổn định lần nào cũng thế.

02. Đo TTFB trong Network panel 01:40–03:20

Lọc Doc, mở tab Timing: Content Download chỉ ~2 ms, phần đáng chú ý là Waiting (TTFB); bài 1 10–30 ms, bài 3 200–380 ms

Mở Network panel, bấm bài 1, lọc Doc để chỉ xem document. Tab Timing: Content Download gần như bằng 0 (~2 ms). Đáng chú ý là Waiting, tức time to first byte: server mất bao lâu để trả lời. Với site production, TTFB chậm thường do truy vấn database hoặc tính toán nặng.

Bài 3 mất 380 ms, reload lại vẫn khoảng 200–300 ms, còn bài 1 luôn khoảng 10, 20, 30 ms. Vấn đề này nằm hoàn toàn ở backend; backend là PHP hay Java cũng vậy, nhưng vì là Node.js nên dùng được Node.js inspector. Ghi chú khoá học tóm tắt: bài 1 khoảng 20 ms, bài 3 khoảng 200 ms.

03. Mở DevTools cho server Node 04:00–05:20

Khởi động server với --inspect, mở chrome://inspect, bấm Inspect ở target là web server; dùng tab Profiler

Tắt server local, chạy lại với cờ --inspect. Có thêm thông báo đang listening for a debugger session. Vào chrome://inspect, thấy inspectable target là web server kèm đường dẫn đầy đủ, bấm Inspect để có DevTools riêng cho Node.js. Lần này dùng tab Profiler: bấm Start, làm hành động cần đo, bấm Stop.

▸ Ví dụ của nguồn
node --inspect entry-point.js
# rồi mở chrome://inspect › Inspect
04. Hai CPU profile 05:20–07:00

Ghi profile khi mở bài 1 (một vạch rất mảnh), không xoá, ghi tiếp khi mở bài 3 (khối dày): chiều rộng mới là thời gian

  1. Ở trang danh sách bài (localhost), Start, mở bài 1, Stop. Kết quả: một vạch rất mảnh, đúng như kỳ vọng.
  2. Đừng xoá profile cũ (không bấm clear all profiles). Quay về màn hình chính của Profiler.
  3. Start, mở bài 3, Stop. Chọn một vùng nhỏ để biểu đồ hiện ra.

Khác biệt rõ ngay: mảnh so với rất dày. Chiều rộng của thanh là thời gian nó chạy; chiều cao cũng có ý nghĩa nhưng không phải điều quan trọng nhất. Mục tiêu không phải sửa ngay, mà là trả lời được một câu "vì sao bài 3 chậm hơn bài 1".

05. Đọc flame chart 07:00–10:20

Tìm thanh vừa thấp vừa rộng nhất; phía trên là framework (app.use của Express, template renderer), càng xuống thấp càng gần code của bạn

Phương pháp "không khoa học" của tác giả: vì quan tâm chiều rộng, tìm thanh thấp nhất mà cũng rộng nhất. Không cần xuống tận đáy (thanh 0,1 ms), mà gần đáy. Flame chart thể hiện JavaScript call stack của thao tác đã ghi. Với Node, phần trên cùng thường vô nghĩa với mình: app.use của Express, template renderer… mình sẽ không đổi thứ tự chạy của chúng. Càng xuống thấp càng gần application code.

Dấu hiệu cần tìm: một chuỗi rất nhiều khối nhỏ lặp lại, nghĩa là một hàm bị gọi đi gọi lại (hover thấy processKeywords). Đi lên một chút tới thanh rộng mà vẫn thấp: markdown, marked, Parser.parse, rồi rất nhiều lời gọi highlight. Hover qua đều trỏ tới highlight.js; click vào highlightAuto là tới hàm "highlighting with language detection".

06. Nguyên nhân 10:20–13:20

Bài 1 viết bằng HTML thuần nên không phải xử lý; các bài sau viết Markdown, server parse bằng marked và tô màu code bằng highlight.js mỗi lần đọc

Course notes bài 1 viết hoàn toàn bằng HTML: code snippet trong đó không cần hậu xử lý. Các bài sau tác giả viết Markdown cho dễ (bài 3 gần như không có thẻ HTML). Mỗi khi người dùng đọc course notes:

  1. Markdown parser trên server parse course notes của bài đó.
  2. Gặp code block (bọc trong ba dấu backtick), nó giao việc tô màu cú pháp cho highlight.js.
  3. highlight.js chạy các thao tác JS nặng: parse, tokenize, regular expression… Ví dụ từ khoá new được bọc trong một thẻ span để tô màu.
▸ Ví dụ của nguồn — code gây chậm
const marked = require('marked');
const highlightJS = require('highlight.js');

marked.setOptions({
  highlight(code) {
    return highlightJS.highlightAuto(code).value;
  }
});
07. Cách sửa & bài tập 13:20–15:40

Chuyển Markdown + syntax highlighting sang lúc build (Gulp, webpack, bash) thay vì lúc chạy; luyện CPU profile với trash, Express, gulp

Từ khoá là runtime: không cần làm việc này mỗi lần tải course notes. Một script Gulp/Webpack, hay chỉ bash, có thể chuyển Markdown thành HTML lúc build. Server Node.js khi đó vẫn nhanh, gọn, không phải tính toán nặng.

Bài tập: tự chạy JavaScript CPU profile trên code Node.js, ví dụ:

  • một CLI phổ biến như trash (trash-cli): profile lúc xoá file;
  • một web server như express (có generator tạo nhanh boilerplate), chạy với --inspect;
  • một build tool như gulp hoặc webpack.
