01. Real User Monitoring 00:00–01:30

Synthetic monitoring (như WebPageTest) đo trong môi trường kiểm soát; RUM đo trải nghiệm của người dùng thật, bắt được cả CDN chập chờn ở một vùng

Synthetic monitoring mô phỏng hành vi người dùng; ví dụ phổ biến là WebPageTest: nhập URL, chạy test, trang được tải trong môi trường kiểm soát, hiệu năng thường dễ đoán. Real User Monitoring (RUM) theo dõi số đo của người dùng thật, ở đây là số đo hiệu năng, ví dụ thời gian parse JavaScript.

Bạn có thể có continuous deployment tuyệt vời, load test, functional test, test tự động… nhưng một CDN phục vụ một vùng địa lý có thể chậm hay sập mỗi ngày. Test tự động không bắt được, RUM thì rất có thể bắt được. RUM còn lộ ra lỗi không thấy ở môi trường dev, staging, QA.

02. Vì sao cần số đo sâu hơn 01:30–02:20

DOMContentLoaded và onload không cho bức tranh đầy đủ; cần time to interactive, first meaningful paint, độ hoàn chỉnh về hình ảnh và vòng đời trang khi Ajax điều hướng

Theo truyền thống, DOMContentLoaded và onload đánh dấu trang đã sẵn sàng. Với ứng dụng web hiện đại, onload nhanh là chưa đủ; quan trọng là time to interactive, first meaningful paint… Ghi chú bài thêm: cần quan tâm độ hoàn chỉnh về hình ảnh (visual completeness) và vòng đời trang, nhất là khi Ajax đảm nhận điều hướng. Vì vậy nên tự đo dựa trên hiểu biết về code của mình.

03. Đo bằng new Date() 02:20–04:00

Ghi thời điểm đầu và cuối quanh đoạn code nghi chậm rồi lấy hiệu; vòng lặp querySelector càng nhiều lần càng lâu; gửi kết quả về server và phải hành động theo nó

▸ Ví dụ của nguồn
const start = new Date().getTime();
// Expensive operation here which we are "timing"
const now = new Date().getTime();

const duration = now - start;

Dán vào Console: không có gì ở giữa thì ra 0. Thay comment bằng vòng for 9999 lần gọi document.querySelector một phần tử không tồn tại: vẫn nhanh. Thêm một số 9: lâu hơn hẳn. Triển khai trong ứng dụng thì gửi duration về server để hiểu người dùng đang trải nghiệm gì. Nhưng chỉ gửi về là chưa đủ, phải hành động theo kết quả.

04. User Timing API 04:00–05:20

API chuẩn để ghi mốc (mark) và khoảng thời gian (measure); chính xác dưới mili giây, đáng tin hơn new Date(), và các công cụ hiểu được nó

User Timing API là một specification thật, để ghi timestamp (marks) và khoảng thời gian (measures), ứng với các method trên đối tượng performance. Vì sao tốt hơn kỹ thuật dùng new Date():

  • Đáng tin hơn: timer JS không phải lúc nào cũng chính xác.
  • Mặc định có độ phân giải dưới mili giây (sub-millisecond).
  • Vì là chuẩn, nhiều công cụ, kể cả DevTools, đọc được và hiển thị nó theo cách thống nhất.
▸ Ví dụ của nguồn
performance.mark("Start");

let myCounter = 0;
for (let i = 0; i < 1000000; i++) {
  myCounter++;
  document.querySelector("IDoNotExist");
}

performance.mark("End");
performance.measure("Some name", "Start", "End");
performance.getEntriesByType("measure");
05. Demo 1: mark và measure 05:20–10:00

Bốn mark cách nhau 100 ms; chỉ có mark thì Performance panel không hiện gì đáng kể; thêm measure thì có hàng User Timing với outer 306 ms và inner 100 ms

Hàm sleep resolve một promise sau 100 ms. init là async function nên viết await sleep() trông như code đồng bộ. Gọi performance.mark bốn lần với chuỗi '1' tới '4', giữa mỗi lần ngủ 100 ms. Comment phần measure và reload với Performance panel mở (nó tự ghi): không thấy gì, dù ngủ tới 300 ms.

Bỏ comment: init().then() gọi performance.measure. Tham số đầu là nhãn bất kỳ (có cả emoji), hai tham số sau là mark đầu và mark cuối. Giờ có hàng mới User Timing: outer từ mark 1 tới 4 mất 306 ms (ba lần ngủ), inner từ mark 2 tới 3 mất 100 ms. Giữ Shift và kéo để đo một đoạn trên bản ghi.

06. Demo 2: blocking script 10:00–15:20

Đo quanh thẻ script bigcode.js bằng marky; file tải trước cả mark (preload scanner), parse ~460 ms trên script streamer rồi evaluate, compile; HTML còn lại phải chờ

Thư viện Marky (marky.js) cho viết marky.mark / marky.stop thay vì mark và measure. Chỉ đo quanh một thẻ script tải bigcode.js, một file JS khổng lồ. Performance panel giờ có cả thông tin network, không phải chuyển qua lại với Network panel.

  • bigcode.js bắt đầu tải trước khi đoạn đo kịp chạy. Đoán: nhờ preload scanner của Chrome, nó lướt nhanh document và chọn trước vài thứ để tải.
  • Tải xong rất sớm, nhưng evaluate và compile trên main thread xảy ra muộn hơn nhiều. Khoảng trống ở giữa là script streamer thread: Parse Script mất khoảng 460 ms.
  • Thanh with script boundaries bao trọn parse, evaluate và compile: cách đo tổng thời gian rất hay.
  • Trong suốt thời gian đó gần như không gì khác chạy; chỉ khi xong, phần HTML còn lại mới được parse và bigcode2 mới được evaluate. Đây là hình dung rõ nhất về blocking script. Event Parse HTML còn ghi range các dòng HTML được parse.

07. Công cụ khác 15:20–18:00

Lighthouse liệt kê user timing marks and measures; WebPageTest ghi mark vào từng lượt test; bookmarklet in bảng bằng console.table; SpeedCurve, Boomerang

  • Lighthouse: trong báo cáo, phần Performance có User Timing marks and measures.
  • WebPageTest: nhiều tính năng (giao diện đang tốt dần); thêm mọi marking vào từng test run, dù gọi qua marky.
  • Performance bookmarklet (micmro/performance-bookmarklet): dán vào Console, in các mark bằng console.table và vẽ chồng biểu đồ lên trang (tìm "boundaries" trong phần DOM processing).
  • Khác: SpeedCurve (trả phí), Boomerang (mã nguồn mở, tự thu thập số đo), Marky.js, Speedgun.
08. Kết luận 18:00–19:40

Phải hành động theo số đo; User Timing giúp làm RUM nhưng cũng dùng được khi dev cục bộ; hỗ trợ toàn cầu hơn 80%, thiếu thì quay về new Date()

  • Công cụ và API đều tốt, nhưng phải hành động theo số đo: gửi về server, phân tích cơ bản.
  • User Timing là một cách làm RUM; cũng có thể chỉ dùng khi dev cục bộ rồi xem bằng Performance panel.
  • Ghi chú bài gợi ý: báo cho người dùng, kiểu "Trang này tải lâu bất thường, chúng tôi đang xem xét".
  • Hỗ trợ trên Can I Use: hơn 80% toàn cầu; lúc quay chưa có trên iOS Safari, nhưng API không thiết yếu cho chức năng nên có thể quay về dùng Date.
