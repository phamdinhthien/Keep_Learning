01. Vấn đề 00:00–02:20

gulp xo lint mọi file JS trong thư mục (đệ quy) và mất khoảng 8,5 giây mỗi lần; build tool chậm là vấn đề vì mỗi lần lưu lại phải chờ

Gulp là build tool tác giả dùng; webpack hay Grunt khác bên trong nhưng đạt mục tiêu tương tự, nên bài học áp dụng cho mọi tool viết bằng JavaScript. Task xo chạy XO, một "JavaScript happiness style linter", rất giống ESLint: kiểm tra thụt lề, dấu chấm phẩy… theo bộ quy tắc định sẵn, qua plugin gulp-xo.

Nó chạy đúng, nhưng chậm: khoảng 8 giây rưỡi. Mỗi lần lưu file và chạy lại là chờ ngần ấy. Mục tiêu của khoá là làm việc hiệu quả hơn, nên tool nào chậm thì nên điều tra ít nhất một chút: biết đâu lại phát hiện điều gì.

▸ Ví dụ của nguồn — task và thời gian chạy
gulp.task('xo', () => {
  return gulp.src(['js/**/*.js']).pipe(xo());
});

02. Chạy CPU profile 02:20–04:00

Chạy gulp qua node với cờ --inspect-brk, mở chrome://inspect, bấm Inspect, sang Profiler, Start rồi Stop khi đã đủ dữ liệu

Không thể gõ node gulp xo; cần gọi binary của gulp qua Node với cờ --inspect-brk (Node 7.8 lúc quay): Node dừng ở dòng JS đầu tiên và chờ debugger. Vào chrome://inspect (tác giả dùng bookmarklet), thấy inspectable target, bấm Inspect. Lần này đi thẳng sang Profiler, bấm Start: gulp xo bắt đầu chạy. Không cần chờ hết mọi file, ghi một lúc là đủ rồi Stop. Nếu biểu đồ chưa hiện, chọn một vùng nhỏ.

▸ Ví dụ của nguồn
node --inspect-brk ./node_modules/.bin/gulp xo

04. Đi xuống flame chart 05:30–07:20

Bỏ qua phần trên (Node, Gulp); gần đáy có globSync 342 ms cho một file, nhưng glob quá chung chung; đi lên một chút thấy lintText rồi getIgnores

Như bài trước, tránh các lời gọi trên cùng vì đó là phần của Node.js hay Gulp. Xuống tận đáy (thanh 0,1 ms, một regular expression) thì quá vụn. Gần đáy mà vẫn rộng có các glob sync: 342 ms chỉ cho một file. Nhưng glob là code rất chung chung, nhìn vào không biết ai gọi và vì sao. Đi lên một chút: lintText, đúng chỗ rồi. Luôn để ý tên hàm: nếu đặt tên tốt, nó cho biết mình có đang debug đúng chỗ không.

Ở giữa có getIgnores trong options-manager.js, nghe như code của node module chứ không phải lời gọi Node.js phía trên. Click vào để tới hàm; chuột phải › Reveal in navigator để biết file nằm ở node_modules/xo, phòng khi DevTools mất vị trí.

05. getIgnores làm gì 07:20–10:50

Hàm tìm mọi file .gitignore bằng globby.sync('**/.gitignore'); ** là đệ quy mọi thư mục con, và việc này chạy lại cho từng file

Mục tiêu bài không phải sửa bug, mà là đi từ một biểu đồ choáng ngợp tới mức có thể mở một GitHub issue với phân tích chi tiết. Hãy thử đọc hàm và tự đoán trước. Theo tên và ngữ cảnh: linter tìm các file .gitignore, parse chúng để biết file nào không cần lint. Hai dấu ** là wildcard: tìm .gitignore ở thư mục hiện tại và mọi thư mục con, đệ quy. Kết hợp với lượng glob khổng lồ trong biểu đồ, đây là ứng viên hoàn hảo để thử.

▸ Ví dụ của nguồn
function getIgnores(opts) {
  …
  const gitignores = globby.sync('**/.gitignore', {
    ignore: opts.ignores,
    cwd: opts.cwd || process.cwd()
  });
  …
}

Ghi chú khoá học tóm lại nguyên nhân: tìm .gitignore đệ quy, cộng với dự án có rất nhiều thư mục con, nên getIgnores có nhiều việc hơn.

06. Live edit để đo 10:50–13:40

Đặt breakpoint ở đầu getIgnores, chạy lại; bọc console.time/timeEnd, lưu, resume: mỗi file hàng trăm ms; bỏ **/ thì còn 1–2 ms

Gulp xo đã chạy xong, nên đặt breakpoint ở dòng đầu thân hàm, đóng DevTools, chạy lại lệnh, Inspect target mới, Resume và chờ dừng ở breakpoint. Không cần profile lại. Thêm console.time với một nhãn bất kỳ ở đầu và console.timeEnd cùng nhãn ở cuối, chuột phải › Save để nạp lại vào V8, resume. Terminal in ra mỗi file mất hàng trăm ms.

Dừng lại ở breakpoint lần nữa, xoá **/, lưu, resume: còn khoảng 1–2 ms. Thay đổi này đổi chức năng (chỉ tìm ở thư mục hiện tại), nhưng mục đích là tìm ra nguyên nhân gốc.

▸ Ví dụ của nguồn — mẫu đo bằng live edit
function someFunction() {
  // <-- Paused at a breakpoint here
  console.time('Some Label');
  // Expensive operations here
  console.timeEnd('Some Label');
}
07. Kiểm chứng & cách sửa 13:40–17:00

Sửa thẳng file trong node_modules (chỉ để demo): gulp xo còn ~3 giây, hoàn lại thì ~8–9 giây; nên mở issue kèm CPU profile, hoặc chỉ lấy gitignore một lần

Mở options-manager.js của XO trong node_modules bằng Sublime, sửa giống hệt rồi chạy lại: 3 giây, chạy lần nữa vẫn 3 giây. Hoàn tác: lại khoảng 8–9 giây, gấp khoảng ba lần. Lưu ý: bình thường đừng bao giờ sửa code node module như vậy, quên hoàn tác là hỏng việc.

Không thể gửi PR này và mong được merge, vì nó đổi chức năng. Nhưng có thể mở GitHub issue: giải thích đã tìm ra gì, dán CPU profile, thảo luận với maintainer; làm vậy giúp người bảo trì rất nhiều. Một cách sửa khác có thể đúng hơn: getIgnores đang chạy cho mỗi file, trong khi chỉ cần làm một lần lúc đầu.

  • Dùng JavaScript CPU profile cho code Node: server, task runner (Gulp, Grunt, Webpack), cả JS chạy trên Raspberry Pi.
  • Hãy thử trên code Node có sẵn, kể cả khi không có vấn đề hiệu năng, để quen đọc biểu đồ.
