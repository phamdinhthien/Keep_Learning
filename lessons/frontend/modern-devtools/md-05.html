01. Vì sao cần biết frame 00:00–01:20

Frame chứa dữ liệu để debug hiệu năng, frame quá dài thì người dùng nhận ra, và nó là khái niệm nền của Performance panel

Nếu chưa nghe về frame trong bối cảnh render, hãy nghĩ tới chữ F trong FPS (frames per second). Ba lý do nên quan tâm:

  • Frame chứa dữ liệu dùng cho debug hiệu năng; hiểu hiệu năng sâu hơn thì tạo được trải nghiệm tốt hơn.
  • Một frame mất quá lâu nhiều khả năng người dùng nhận ra: frame ảnh hưởng trực tiếp tới người dùng.
  • Đây là khái niệm nền tảng của Performance panel.
02. Frame là gì 01:20–02:00

Frame gồm các event cấp thấp trình duyệt phải xử lý để vẽ trang; trang đã lên màn hình thì thôi, có thay đổi (cuộn, thêm phần tử, animation) thì cần frame mới

Một câu: frame đại diện cho các event cấp thấp mà trình duyệt phải thực hiện để vẽ trang lên màn hình. Khi trang đã hiện xong thì không cần thêm frame. Nhưng bất kỳ thay đổi nào: cuộn trang, thêm phần tử, animation… đều tạo ra một frame mới chứa một loạt event.

03. Phép so sánh: quầy thu ngân 02:00–03:40

Một quầy, một thu ngân: giỏ hàng là frame, món hàng là event, quét từng món một; người trước chậm thì cả hàng phía sau phải chờ

Hai dòng cuối quan trọng nhất. Có thể xử lý 50 event rất nhanh, nhưng cũng có thể chỉ một event mà rất chậm vì bản chất của nó. Và nếu một người mất thêm năm phút, mọi người sau đều chậm theo: một frame dài hơn mức cần làm trễ mọi frame sau.

04. Frame trong DevTools 04:00–06:40

Hình dung bản ghi như một bảng: mỗi thread là một hàng, mỗi frame là một cột; đường đứt dọc là ranh giới frame, Summary cho thời lượng, FPS và screenshot

Nút reload trong Performance panel tự reload trang, bắt đầu ghi, và tự dừng khi không còn event. Nếu thấy rối, hãy hình dung như một bảng: mỗi thread (main thread, script streamer thread, raster thread…) là một hàng; "tiêu đề cột" chính là các frame, hover lên là thấy.

Chọn một frame bất kỳ, Summary hiện: frame mất bao lâu (ở đây 43 ms, khá dài), FPS tương đương, screenshot của frame và layer tree. Frame được chọn có viền xanh. Ranh giới frame khó thấy, nhưng có các đường đứt dọc (frame boundaries): đó là chỗ frame bắt đầu và kết thúc. Mở main thread là thấy các event bên trong.

05. Ngân sách 16 ms 06:40–08:20

Màn hình 60 Hz nên trình duyệt cố vẽ 60 frame mỗi giây; 1000 / 60 ≈ 16 ms là ngân sách của một frame, thực tế nên thấp hơn

Mỗi frame có thời lượng và FPS riêng: frame này 22, frame kia 73. FPS cao tốt hơn, thời lượng thì càng ngắn càng tốt. DevTools tính thế nào? Display settings của macOS cho thấy màn hình có refresh rate 60 Hz. Để theo kịp, trình duyệt cố render 60 FPS. Để nhét 60 frame vào một giây:

06. Các event trong frame 08:20–09:40

Sơ đồ “The Anatomy of a Frame” của Paul Lewis giải thích từng event như Layout, Update Layer Tree; thử thách là tự kích hoạt chúng bằng ít JS nhất

Sơ đồ trong bài lấy từ blog The Anatomy of a Frame của Paul Lewis (Chrome team), giải thích chi tiết từng event xuất hiện khắp bản ghi như Layout, Update Layer Tree. Ghi chú bài thêm: có thể coi Recalculate Style là việc trình duyệt tính ra mọi thứ bạn thấy trong Computed pane của Elements.

Thử thách: tìm ra dòng JS nào kích hoạt event nào, và vì sao, nhất là các event trên main thread. Dùng thật ít JS, đừng tải plugin, vì chỉ thêm nhiễu vào bản ghi.

07. Tạo hoạt động frame bằng JS 09:40–14:20

Click → requestAnimationFrame → tạo thẻ p, gán innerHTML, appendChild; bản ghi lần lượt có Input, Animation Frame Fired, Parse HTML, Recalculate Style, Layout…

▸ Ví dụ của nguồn
const el = document.querySelector('.hello');

el.addEventListener('click', () => {
  requestAnimationFrame(() => {
    const newEl = document.createElement('p');
    newEl.innerHTML = 'Some text';
    document.body.appendChild(newEl);
  });
});

Ghi thật ngắn: start, click, stop. Screenshots giúp biết ngay việc xảy ra ở đâu mà không phải dò biểu đồ. Đối chiếu:

  • Interactions › Input (mouse up) khớp với event đầu tiên trên main thread: input event handler.
  • Animation Frame Fired gọi function: chính callback requestAnimationFrame.
  • Parse HTML (do innerHTML); click vào event, DevTools chỉ đúng dòng code gây ra.
  • Recalculate Style: phần tử mới được thêm thì trình duyệt phải tính CSS nào áp cho nó (cả user agent stylesheet). Ví dụ 50vw là bao nhiêu pixel? Đó là recalc style.
  • Layout: tương tự nhưng là tính hình học của các phần tử bị ảnh hưởng; DevTools báo layout bị invalidate bởi đúng dòng appendChild.
  • Sau đó là Update Layer Tree, Paint, Composite.

Tất cả nằm trong một frame rất ngắn. Ví dụ đơn giản là cố ý: ví dụ thực tế thú vị hơn nhưng nhiễu, dễ hiểu sai dòng JS nào gây ra event nào.

08. Kết luận 14:20–15:20

Frame là lô việc để đưa trang lên màn hình; mỗi thay đổi qua JS, CSS hay cuộn đều cần thêm frame; các event định nghĩa sẵn có thể có hoặc không trong một frame; frame ngắn thường là trải nghiệm tốt
