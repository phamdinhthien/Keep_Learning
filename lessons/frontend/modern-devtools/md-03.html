01. Mục tiêu 00:00–01:40

Định vị đoạn code nên đo trong một app thật, đo bằng User Timing API, gửi kết quả về server Node.js, và dùng PerformanceObserver

Mục tiêu bài: định vị các đoạn code để profile và gửi kết quả về server. Nội dung: profile một phần của app thật, dùng User Timing API ghi lại JS tốn kém, gửi số đo về server Node.js, dùng Performance Observer API, kết luận. App ví dụ là StackEdit, một trình soạn Markdown trên web, có hướng dẫn chạy cục bộ trên GitHub. Với người dùng thì đơn giản, nhưng codebase là app JS rất nặng, hợp để profile.

02. Profile app thật 01:40–03:40

Bôi đen chữ, Start recording, bấm nút Bold, Stop; ghi thật ngắn; 26 ms lúc thường, bật CPU 5x thì khác hẳn

Cả bài tập trung vào nút Bold: chữ được in đậm ở editor bên trái và ở markdown preview bên phải.

  1. Bôi đen một đoạn chữ trong editor.
  2. Bắt đầu ghi trong Performance panel.
  3. Bấm nút Bold trên toolbar.
  4. Dừng ghi.

Luôn giữ bản ghi ngắn gọn để bớt nhiễu. Có hai "bướu"; hover một cái thấy 26 ms, có vẻ ổn, nhưng throttle CPU 5x rồi ghi lại thì khác hẳn.

03. Hai đỉnh & screenshots 03:40–06:20

Bấm một lần mà có hai đỉnh; bật Screenshots và hover lên từng ảnh: đỉnh 1 là editor đổi chữ URL thành đậm, đỉnh 2 là phần preview

Vì đang debug từ ngoài vào, đừng vội đo và kết luận: trước hết hiểu chuyện gì xảy ra. Khó hiểu là chỉ một hành động mà có hai đỉnh. Tính năng Screenshots của Performance panel giải quyết: ghi lại, phóng to dải screenshot. Đoạn phẳng thì trang không đổi. Ở đỉnh 1, chữ URL trong editor chuyển đậm; ở đỉnh 2, chữ URL bên preview chuyển đậm. Hai đỉnh là hai lần đổi DOM phản ứng với cú bấm. Bài chỉ tập trung vào đỉnh bên trái, của code editor. Có thể dùng phím W, A, S, D để di chuyển trong biểu đồ.

04. Đọc flame chart 06:20–08:40

Event click → Function Call ở markdown-editor.js:1452; màu khối là theo file; 7,87 ms lúc thường, 54,64 ms ở CPU 5x; frame chỉ 4 FPS

Có một event click, khả năng là cú bấm Bold. Rồi một Function Call, bên cạnh là Run Microtasks. Coi chúng là hai cột riêng. Cột đầu tạo ra một chồng hàm JS; màu thể hiện file, cùng màu là cùng file. Function Call trong markdown-editor chỉ mất 7.87 ms; ở CPU 5x cùng chỗ đó thành 54.64 ms. Không phải chê StackEdit, chỉ là ví dụ. Bấm vào frame thấy thời lượng, FPS tương đương chỉ 4, và CPU time.

Ghi chú bài: tìm một thanh chữ nhật cấp cao (lời gọi gần đỉnh stack) làm vị trí đặt số đo lý tưởng.

05. Đặt mark và measure 08:40–14:20

Bấm link markdown-editor.js:1452 tới button onclick; bọc bằng mark start/end và measure; lần đầu đặt sai chỗ nên thanh rất ngắn, sửa lại thì đúng 11,39 ms

Flame chart có sẵn file và số dòng: markdown-editor 1452, bấm vào tới button onclick. Bọc khối code bằng performance.mark('bold button click start'), performance.mark('bold button click end'), rồi performance.measure('bold button click', start, end). Mark một mình không làm gì; phải có measure. Nhớ tắt CPU throttling trước khi reload, không thì trang tải rất lâu.

Ghi lại: hàng User Timing có bold button click nhưng rất ngắn, vì mark đặt sai chỗ (trước click thay vì bên dưới). Sửa lại, ghi lại: 11.39 ms, và thanh này dài đúng bằng Function Call của button onclick, xác nhận đã đo đúng hàm. Vẫn nên throttle CPU khi đánh giá.

Thử thách: đo cả đỉnh thứ hai (khoảng 13 ms). Bấm event, tới editor.js:675, thấy trackContentChange được gọi bởi một MutationObserver. Vì vậy Function Call nằm dưới Run Microtasks: đó không phải tên hàm JS, mà là DevTools báo việc này chạy ở "tick" kế tiếp (một cách nói đơn giản hoá).

06. Vì sao gửi về server 14:20–16:00

Đo trên máy dev mạnh có thể sai lệch (ví dụ do extension); số đo phải đến từ máy người dùng; cách nhanh: getEntriesByType('measure') rồi gửi qua Ajax

Mọi thứ đến giờ chỉ cho chính ta, trên máy dev mạnh. Nếu môi trường của bạn làm một việc chậm bất thường, bạn có thể mất cả tuần sửa một lỗi người dùng chẳng hề gặp, ví dụ một Chrome extension làm lệch kết quả. Vì vậy cần thu số đo từ máy người dùng về một nơi tập trung để phân tích. Cách nhanh: performance.getEntriesByType('measure') trong Console, lấy tên và duration, gửi bằng Ajax dưới dạng query string. Nhưng có sẵn công cụ trưởng thành hơn.

07. Boomerang 16:00–21:40

Boomerang thu số đo và beacon về server; plugin UserTiming lấy mark/measure; UserTiming Compression nén payload; gọi BOOMR.sendBeacon() để thử

  • Boomerang: thư viện JS phía client thu và báo số đo hiệu năng (tác giả nhớ là ban đầu do Yahoo khởi xướng).
  • UserTiming plugin của Boomerang: báo cả mark và measure (plugin mới được viết khoảng 12 ngày trước lúc quay).
  • User Timing Compression: nén số đo trước khi gửi, và giải nén khi cần xem; không muốn payload lớn chỉ vì số đo.
  • Boomcatch: beacon receiver cho Boomerang, chạy trên Node.js. Tác giả nói rõ công ty họ đang làm duy trì công cụ này, nhưng bản thân không tham gia phát triển.

Production thì nên dùng bundler, chỉ build Boomerang với plugin cần. Ở đây nạp thẳng bản raw git bằng thẻ script trong editor.html. Đặt code khởi tạo ở đâu trong app lạ? Mở DevTools tìm script chính: app dùng require.js, entry point là main.js; đặt vào callback chạy khi mọi dependency đã tải. Kiểm tra: gọi BOOMR.sendBeacon() trong Console, Network thấy request tới localhost:8081/beacon (đỏ vì chưa có server). Bấm Bold rồi gửi lại: query string có tham số usertiming đã nén.

▸ Ví dụ của nguồn
BOOMR.init({
  beacon_url: 'http://127.0.0.1:8081/beacon',
  UserTiming: { enabled: true }
});
08. Boomcatch: mapper & forwarder 21:40–27:20

Server trả 204 No Content và in dữ liệu kèm IP, user agent; mapper giải nén usertiming, forwarder lọc measure rồi chuyển đi (StatsD, Graphite)

npm run liệt kê script; npm run boomcatch khởi động server (qua nodemon). Lặp lại: bấm Bold, BOOMR.sendBeacon(): lần này thành công, 204 No Content vì server chỉ cần trả status code. Terminal in ra dữ liệu, kèm method, IP, user agent. Có thể đưa vào dashboard, thậm chí gửi sang Google Analytics. Mẹo: kéo nhãn panel để sắp xếp lại panel trong DevTools.

Mapper chuyển dữ liệu thành thứ hữu ích, chỗ hợp lý để giải nén: gán data.usertiming bằng bản đã giải nén. Forwarder chuyển dữ liệu đi nơi khác; ở đây lọc lấy measure (Boomerang gửi cả mark) và in ra. Boomcatch có sẵn mapper StatsD, thường đi cùng Graphite trên các màn hình dashboard ở văn phòng. Ước muốn: frontend dev đẩy thời gian chạy JS lên các dashboard đó để ưu tiên việc. Throttle CPU 5x và gửi lại: duration lên 51 ms, trên điện thoại có thể gấp đôi.

▸ Ví dụ của nguồn — server, mapper, forwarder
boomcatch.listen({
  port: 8081, path: '/beacon', log: console,
  mapper: path.resolve('./mapper'),
  forwarder: path.resolve('./forwarder')
});

// mapper.js
function map (data, referer, userAgent) {
  if (data.usertiming) {
    data.usertiming = UserTimingDecompression.decompressFromString(data.usertiming)
  }
  return JSON.stringify(data);
}

// forwarder.js
function log (data, type, separator, callback) {
  console.log(data)
  callback(null, data.length);
}
09. PerformanceObserver 27:20–28:40

PerformanceObserver gọi callback mỗi khi có mark/measure mới, thay vì phải tự gọi getEntriesByType; có thể chỉ đăng ký loại entry cần

▸ Ví dụ của nguồn
const perfObserver = new PerformanceObserver(list => {
  console.log(list.getEntries());
});

perfObserver.observe({entryTypes: ['mark', 'measure']});

performance.mark('Hi');

Tạo một PerformanceObserver với callback nhận list, gọi list.getEntries(). Tạo mark "Hi" là callback chạy ngay. Không chỉ lấy được số đo qua getEntriesByType, mà còn lắng nghe theo thời gian thực và hành động ngay khi chúng xuất hiện; có thể xoá entry, và chỉ đăng ký loại cần.

10. Kết luận 28:40–30:00

Dùng User Timing để thu số đo từ người dùng; ghi Performance cục bộ trước để chọn chỗ đo; gửi tới Google Analytics, dashboard sẵn có, hoặc server riêng

  • Thu số đo JS cấp thấp từ máy người dùng bằng User Timing API.
  • Ghi Performance cục bộ trước để thấy chỗ chậm, chọn ứng viên để đo.
  • Gửi số đo tới Google Analytics (có tài liệu cho user timing), dashboard sẵn có của công ty, hoặc server riêng qua beacon_url của Boomerang.
  • Dùng PerformanceObserver để được báo khi có số đo mới.
