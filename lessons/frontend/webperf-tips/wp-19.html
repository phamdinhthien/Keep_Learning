WebPerf Tips · Bài 19 · Network

Nghẽn CPU hay nghẽn mạng?

Một mẹo nhìn trace: main thread kín việc là CPU, main thread trống trải là đang chờ mạng. Rồi lần ra request đang bắt CPU chờ.

Bài gốc: “Identifying Network vs. CPU Bottlenecks in Load Flows” ↗
00 · CHUẨN BỊ

Ghi trace đúng kịch bản

Ghi trace (bài 05) cho kịch bản “tải” cần phân tích, ví dụ: mở thẳng trang, chuyển trang trong SPA, mở một modal. Dùng screenshot để đi từ trái sang phải, tìm điểm bắt đầu và kết thúc kịch bản, rồi chọn đúng đoạn đó.

01 · XEM CPU TRƯỚC

Main thread kín việc: nghẽn CPU

Nếu track Main phủ kín bởi các task (thường là JS) với flamegraph rộng và nhiều màu, thì CPU là điểm nghẽn chính.

Nên nhìn CPU trước mạng: request mạng là bất đồng bộ, dù có nhiều request đang bay thì chúng cũng không trực tiếp làm main thread bận. Main thread bận thì thường là vấn đề CPU, kể cả khi mạng cũng đang hoạt động.

02 · KHOẢNG TRỐNG

CPU rảnh thường là đang chờ mạng

Kịch bản có những khoảng trống lớn giữa các task nghĩa là main thread không được giao việc, thường vì đang đợi một tài nguyên mạng. Rất có thể đường tải quan trọng của bạn đang mắc mẫu “request nối đuôi nhau” (bài 20).

03 · TÌM REQUEST THỦ PHẠM

Request nào kết thúc thì CPU chạy lại?

Ứng dụng hiện đại thường bắt đầu render tiếp ngay khi một dữ liệu cần thiết về tới (ví dụ React effect kích hoạt render lại). Tận dụng điều đó:

  1. Tìm thời điểm CPU bắt đầu hoạt động trở lại sau khoảng trống.
  2. Dóng thẳng lên track Network, tìm request kết thúc ngay sát thời điểm đó.
  3. Đó gần như chắc chắn là phụ thuộc mạng đang làm chậm kịch bản.

Bài gốc minh hoạ bằng một trace thật: sau cú click, một request API mất vài trăm ms mới xong, và CPU chỉ hoạt động trở lại sau đó.

▣Ảnh/ví dụ gốc ảnh trace thật với request kết thúc đúng lúc CPU chạy lại↗
  • Kín đặc → tối ưu CPU (bài 09–11, 23–26). Trống trải → tối ưu phụ thuộc mạng (bài 20–22).
  • Request kết thúc đúng lúc CPU chạy lại là ứng viên số một.
