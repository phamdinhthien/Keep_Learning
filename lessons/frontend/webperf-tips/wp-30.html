WebPerf Tips · Bài 30 · Browser internals

Đo thời điểm frame thật sự được vẽ

Phần lớn số đo “render time” dừng lúc JS sửa xong DOM, trong khi người dùng chỉ thấy gì đó khi frame xuất hiện. Kết hợp rAF và MessageChannel để chạm gần đúng thời điểm ấy.

Bài gốc: “Detecting when the Browser Paints Frames in JavaScript” ↗
00 · VẤN ĐỀ

Số đo của bạn có chạm tới pixel không?

Đa số đội đo “thời gian render” ở một thời điểm tuỳ ý trong lúc React hay JS đang dựng DOM. Dễ hiểu thôi: ngoài mấy lần vẽ đầu khi tải trang, trình duyệt không có API nào báo “vừa paint xong”. Bài này chỉ cách đo lúc pixel xuất hiện ở bất kỳ thời điểm nào trong vòng đời ứng dụng, và giải thích vì sao cách đó hoạt động. Cần nắm event loop (bài 01) và mark/measure (bài 12).

01 · VÌ SAO ĐO PAINT

Khoảnh khắc người dùng thực sự thấy UI

Đo paint là đo đúng điều người dùng quan tâm: giao diện đã hiện ra. Nó còn làm lộ phần thời gian “rơi rớt” giữa lúc JS sửa DOM xong và lúc frame được tạo:

  • Render steps dài: UI phức tạp, nhiều phần tử, thuộc tính hiển thị đắt.
  • Task JS dài: chính task sửa DOM quá chậm.
  • Task chen ngang: hàng đợi đầy task khác, chạy xen vào giữa task của bạn và frame.
02 · PAINT XẢY RA KHI NÀO

Sau khi task JS chạy xong

Event loop xen kẽ task JS và render steps trên main thread (bài 01). Nên mọi thay đổi DOM trong JS phải đợi task kết thúc mới có thể được vẽ. React có sửa DOM bao nhiêu thì cũng chỉ hiện ra sau khi Paint chạy.

03 · KỸ THUẬT

requestAnimationFrame + MessageChannel

/** Gọi cb ngay sau khi frame kế tiếp được tạo (gần đúng). */
function afterNextPaint(cb) {
  requestAnimationFrame(() => {          // chạy ngay TRƯỚC render steps
    const { port1, port2 } = new MessageChannel();
    port1.onmessage = () => cb();       // task ưu tiên cao, chạy SAU render steps
    port2.postMessage(null);
  });
}

Gọi nó trong cùng task đang sửa DOM:

function showSearchResults(items) {
  performance.mark('search:start');
  renderResults(items);                 // sửa DOM trong task này
  afterNextPaint(() => {
    performance.mark('search:painted');
    const m = performance.measure('search:frame', 'search:start', 'search:painted');
    console.log(`Kết quả lên màn hình sau ${m.duration.toFixed(1)} ms`);
  });
}

requestAnimationFrame thường được gọi tắt là “rAF”.

04 · VÌ SAO NÓ HOẠT ĐỘNG

Hai API “lạc đề” nhưng đúng chỗ

Thoạt nhìn lạ: không animate gì sao lại dùng rAF? Không gửi tin cho ai sao lại dùng MessageChannel?

requestAnimationFrame

Callback của rAF chạy ngay trước khi trình duyệt chạy render steps cho frame kế tiếp. Nó không phải task thường lấy từ hàng đợi, mà gắn với nhịp tạo frame.

MessageChannel

Vốn dùng để gửi tin giữa các luồng/ngữ cảnh, nhưng ở đây ta chỉ tận dụng nó như một cách xếp một task vào hàng đợi. Và task từ MessageChannel được ưu tiên cao hơn phần lớn task khác. Tức là: “chạy cb như một task ưu tiên cao”.

Ghép lại

  1. Trong callback rAF, postMessage xếp một task ưu tiên cao vào hàng đợi.
  2. Trình duyệt tiếp tục chạy render steps (luôn chạy sau callback rAF) và tạo frame.
  3. Render steps xong, event loop lấy task tiếp theo, chính là task onmessage ưu tiên cao.

05 · ĐỘ CHÍNH XÁC

Không tuyệt đối, nhưng là tốt nhất hiện có

  • rAF không chạy khi trang bị ẩn (tab nền), nên loại các lần đo khi document.visibilityState === 'hidden'.
  • Task onmessage ưu tiên cao, nhưng sự kiện input (click, phím) còn ưu tiên hơn, nên không phải lúc nào nó cũng chạy ngay sau frame.
06 · VÍ DỤ

Hai con số trên cùng một cú click

Trang demo của bài gốc đo hai thứ khi bấm nút:

  • Thời gian JS dựng DOM: từ click tới khi sửa DOM xong.
  • Frame time: từ click tới khi thay đổi lên màn hình.

Trong trace, frame time luôn dài hơn vì nó gồm cả render steps. Khoảng chênh đó chính là phần mà cách đo thông thường bỏ sót.

▣Ảnh/ví dụ gốc ảnh trace đo frame time và trang demo↗
  • Đo tới lúc pixel xuất hiện, không chỉ tới lúc DOM đổi.
  • rAF (trước render) + MessageChannel (task ưu tiên ngay sau render).
  • Bỏ các lần đo ở tab ẩn; chấp nhận sai số nhỏ.
