WebPerf Tips · Bài 14 · Network

Đọc track Network trong Performance panel

Màu cho biết loại tài nguyên, hình dạng thanh cho biết thời gian kẹt ở pha nào: xếp hàng, chờ server, tải về hay chờ main thread.

Bài gốc: “How to Read the Chromium Profiler Network Pane” ↗
00 · VÌ SAO QUAN TRỌNG

Web vận hành bằng việc tải tài nguyên từ xa

Nghẽn mạng là một trong những loại vấn đề hiệu năng hay gặp nhất. Track Network trong Performance panel cho thấy tài nguyên tải như thế nào và lúc nào, đặt cạnh hoạt động CPU trên track Main. Nó khác với tab Network (bài 13), vốn dùng để xem, debug và phát lại request; hai công cụ bổ sung cho nhau.

02 · HÌNH DẠNG

Mỗi request có bốn pha

request

tải về
① xếp hàng② đã gửi, chờ③ tải byte④ chờ main thread
Đường mảnh bên trái · khối nhạt · khối đậm · đường mảnh bên phải

① Xếp hàng trước khi gửi

Yêu cầu dữ liệu không có nghĩa request được gửi ngay. Network process có event loop riêng và có thể bị nghẽn; nó cũng hoãn một số request theo độ ưu tiên (rê chuột lên request để xem). Một file Highest gần như không phải chờ, trong khi các file Low yêu cầu cùng lúc lại xếp hàng lâu hơn. Ngoài ra với HTTP/1.1, mỗi domain chỉ có tối đa 6 kết nối song song; vượt quá thì request phải chờ.

② Đã gửi, chờ dữ liệu

Trình duyệt đang đợi phản hồi. Nếu pha này dài, thường do mạng của người dùng chậm/chập chờn khi thiết lập kết nối, hoặc backend xử lý lâu trước khi trả byte đầu tiên.

③ Tải dữ liệu

Thời gian nhận đủ byte. Nghẽn ở đây thường do payload lớn hoặc đường truyền của người dùng chậm.

④ Đã tải xong, chờ main thread

Tải xong chưa có nghĩa là trang đã nhận được. Nếu main thread đang bận, tài nguyên phải đợi tới khi có event Finish Loading / Receive Data trên main thread. Nguyên nhân phổ biến: main thread đang tranh chấp CPU, quá bận chạy JS hay task khác.

03 · HIỂU LẦM THƯỜNG GẶP

Request đang bay không chặn main thread

Thấy thanh request trên track Network, nhiều người nghĩ nó đang “chặn” ứng dụng. Thực ra request mạng là bất đồng bộ: trong lúc nó bay, main thread vẫn chạy JS và phản hồi input bình thường. Trong trace bạn sẽ thấy task JS chạy ngay trong khoảng thời gian một request đang tải.

Cái thực sự làm chậm là khi code của bạn phải đợi kết quả request đó mới làm tiếp được (bài 19, 20).

04 · CHI TIẾT

Click vào request

Chọn một request để tab Summary hiện thông tin: URL, độ ưu tiên, MIME type, kích thước, thời gian từng pha.

▣Ảnh/ví dụ gốc ảnh Summary của một request↗
  • Màu: vàng JS, tím CSS, xanh dương HTML, xanh lá ảnh, xám còn lại.
  • Pha ① dài: ưu tiên thấp hoặc hết kết nối HTTP/1.1. Pha ②: mạng hay backend chậm. Pha ③: payload lớn. Pha ④: main thread bận.
  • Request không chặn main thread; chỉ có code chờ kết quả mới bị chặn.
