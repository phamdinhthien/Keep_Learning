Forced reflow và layout thrashing

Style và Layout là việc đắt nhất của trình duyệt. Đọc vị trí ngay sau khi sửa DOM là ép nó chạy sớm, và làm vậy trong vòng lặp thì chạy đi chạy lại.

Bài gốc: “Layout Thrashing and Forced Reflows” ↗
00 · ĐỊNH NGHĨA

Hai khái niệm cần phân biệt

Reflow là quá trình Style + Layout: gán style và tính toạ độ cho các phần tử (bài 02). Đây là một trong những việc tính toán tốn kém nhất trong vòng đời ứng dụng web.

Forced reflow

Code JS buộc trình duyệt chạy reflow ngay lập tức, ngoài nhịp bình thường.

Layout thrashing

Forced reflow xảy ra nhiều lần liên tiếp trong cùng một task/frame.

Cần nắm trước rendering pipeline (bài 02) và event loop (bài 01).

01 · REFLOW BÌNH THƯỜNG

Một lần mỗi frame, do trình duyệt chủ động

Để vẽ pixel, trình duyệt phải tính style và toạ độ số thực cho từng phần tử. Bình thường việc này chạy một lần mỗi frame, ngay trước khi vẽ, do trình duyệt khởi động, trên main thread. Vì không bị ép chạy giữa chừng nên gọi là reflow bất đồng bộ.

02 · REFLOW BỊ ÉP

Hỏi vị trí khi trình duyệt chưa tính xong

Một số API trình duyệt trả về thông tin style hoặc toạ độ một cách đồng bộ từ engine Style/Layout. Ví dụ getBoundingClientRect():

const box = document.querySelector('.product-card').getBoundingClientRect();
console.log(box.width, box.top);   // DOMRect với toạ độ số thực

Nếu toạ độ/style của phần tử chưa được tính, trình duyệt buộc phải tính ngay để trả lời. Lần reflow bị ép này gọi là forced reflow hay synchronous reflow, và nó chạy bên trong task JS của bạn.

03 · CACHE & TĂNG DẦN

Trình duyệt cố tránh tính lại

Khi trang vừa tải, DOM được parse nhưng chưa phần tử nào có style hay vị trí. Sau lần reflow đầu tiên, trình duyệt cache style và toạ độ trong Render Tree. Từ đó, đọc getBoundingClientRect() chỉ là lấy từ cache, rất nhanh.

Nhưng ứng dụng hiện đại liên tục thêm, sửa, xoá phần tử bằng JS. Mỗi thay đổi DOM có thể làm mất hiệu lực (invalidate) một phần cache. Ví dụ chèn một modal:

const modal = document.createElement('div');
modal.className = 'modal';
modal.append(buildHeader(), buildBody());
document.body.append(modal);   // các node mới: chưa có style, chưa có vị trí

Các node mới chưa có mặt trong Render Tree đã tính. Tới lượt reflow bất đồng bộ (trước frame kế tiếp), trình duyệt chỉ tính lại phần cây bị ảnh hưởng, không tính lại toàn bộ: reflow là tăng dần (incremental). Phạm vi phải tính lại tuỳ loại thay đổi: thêm một phần tử, đổi một class hay xoá cả cụm node.

04 · GHÉP LẠI

Ghi rồi đọc ngay = ép reflow

const panel = document.querySelector('#filters');
panel.classList.add('expanded');          // ① ghi: node bị đánh dấu "dirty"
const h = panel.getBoundingClientRect().height; // ② đọc: cache miss → reflow ngay, có thể CHẬM

Bước ① chỉ đánh dấu node là dirty: thông tin vị trí cũ không còn đúng. Bước ② hỏi vị trí của node dirty, nên trình duyệt phải tính ngay. Task JS dài ra, có thể thành long task.

Tuy vậy, kết quả được cache lại; nếu không có thay đổi nào khác, reflow bất đồng bộ sau đó có thể nhẹ đi hoặc bỏ qua. Vì thế một lần forced reflow không hẳn là thảm hoạ: nhiều khi nó chỉ dời chi phí sang sớm hơn. Dù vậy, forced reflow vô tình vẫn nên tránh, vì lý do ở phần tiếp theo.

05 · LAYOUT THRASHING

Ghi–đọc xen kẽ trong vòng lặp

const cards = [...document.querySelectorAll('.card')];
for (const card of cards) {
  card.classList.add('compact');               // ghi → dirty
  card.dataset.h = card.getBoundingClientRect().height; // đọc → reflow (lặp N lần!)
}

Khác với một lần forced reflow (chỉ dời thời điểm), thrashing tăng số lần layout chạy. Nếu mỗi lần ghi làm mất hiệu lực một phần lớn cây, hậu quả rất nặng: long task và tụt frame rate.

06 · PHÒNG TRÁNH

Gom đọc, gom ghi

Đọc trên cây đã tính xong thì nhanh; ghi chỉ đánh dấu dirty chứ không ép tính ngay. Tận dụng hai điều đó:

// 1. đọc hết trước (cây còn sạch → lấy từ cache)
const heights = cards.map(c => c.getBoundingClientRect().height);
// 2. rồi mới ghi hết
cards.forEach((c, i) => { c.classList.add('compact'); c.dataset.h = heights[i]; });
// reflow chỉ chạy một lần, đúng nhịp, trước frame kế tiếp
MẹoNếu buộc phải đọc sau khi ghi, có thể dùng requestAnimationFrame để sắp xếp thời điểm đọc.

Biết API nào gây layout

Không cần tránh bằng mọi giá, nhưng cần biết chúng: getBoundingClientRect(), offsetTop/Left/Width/Height, clientWidth/Height, scrollTop, scrollHeight, getComputedStyle(), innerText, focus()… Dùng chúng ở đâu thì profile ở đó để chắc không có reflow bất ngờ.

07 · REACT

Framework không che chắn cho bạn

Dùng React không miễn nhiễm thrashing. Cú pháp khai báo còn làm khó nhìn ra lúc nào DOM thực sự bị sửa. Hay gặp nhất là trong useEffect đo DOM để định vị tooltip hay khôi phục vị trí cuộn:

function Tooltip({ anchorRef }) {
  const [pos, setPos] = useState(null);
  useEffect(() => {
    // effect này chạy lúc nào so với các cập nhật DOM khác? Có thể ép reflow
    const r = anchorRef.current.getBoundingClientRect();
    setPos({ top: r.bottom, left: r.left });
  }, []);
  /* … */
}

Không chắc effect có ép reflow không? Ghi trace và tìm trong flamegraph call stack dẫn tới khối Layout. React có useLayoutEffect, chạy ngay sau khi React đã đẩy hết thay đổi vào DOM, là nơi phù hợp để đọc số đo. Nhưng nếu lại ghi DOM trong đó thì dễ gây thêm reflow.

useLayoutEffect(() => {
  const r = anchorRef.current.getBoundingClientRect();  // đọc sau khi DOM đã cập nhật
  setPos({ top: r.bottom, left: r.left });
}, []);
▣Ảnh/ví dụ gốc ví dụ React gốc↗
  • Reflow bình thường: một lần mỗi frame. Forced reflow: bị ép chạy giữa task JS.
  • Layout thrashing: ghi–đọc xen kẽ nhiều lần trong một frame.
  • Gom đọc trước, ghi sau; biết các API gây layout; profile để xác nhận.
