JavaScript đã cache vẫn chậm: vì sao?

Cache chỉ xoá chi phí mạng. Đọc ổ đĩa, IPC, parse, compile, chạy và compile trễ vẫn đổ lên CPU người dùng ở mọi lần mở trang.

00 · HIỂU LẦM

“JS đã nằm trong cache rồi, trang phải nhanh chứ”

Lập trình viên thường chăm chút việc gửi tài nguyên tới máy người dùng, mà quên mất phần tính toán diễn ra sau khi tài nguyên tới nơi. Các SPA nặng JavaScript ngày nay dội rất nhiều việc lên CPU người dùng. Vài niềm tin sai phổ biến:

  • “JS được cache trên trình duyệt nên trang sẽ nhanh.”
  • “Bundle to cũng không sao, đằng nào cũng nằm trong cache.”
  • “Vừa chuyển sang React xong, cache JS rồi thì hiệu năng phải tốt lên nhiều.”

Cả ba đều sai. Cache tài nguyên vẫn rất nên làm, nhưng nó không làm cho code chạy nhanh hơn trên máy người dùng.

01 · HAI LOẠI NGHẼN

Mạng và tính toán trên thiết bị

Mạng

Thời gian đi–về để lấy tài nguyên hay dữ liệu từ server.

Tính toán trên thiết bị

Khối lượng xử lý trên máy người dùng. Hay bị bỏ qua, nhưng ngày nay lại là phần quan trọng nhất.

Khi JS được cache, chi phí mạng bằng 0, nhưng chi phí tính toán vẫn còn nguyên. Lấy một SPA React làm ví dụ:

<body>
  <div id="root"></div>
  <script src="/vendor.8f2c.js"></script>
  <script src="/app.41ab.js"></script>   <!-- render <App /> vào #root -->
</body>

Đặt Cache-Control dài hạn cho hai bundle, hay cài sẵn bằng Service Worker, là tối ưu đúng đắn. Lần ghé sau, file được đọc từ disk cache. Vậy chuyện gì xảy ra lúc đó?

Renderer xin file→IPC→Network process đọc đĩa→IPC→Parse→Compile→Execute + compile trễ

02 · IPC

Chuyển file giữa các tiến trình

Cache nằm trên đĩa, mà tiến trình chạy trang của bạn không có quyền đọc đĩa (bài 03). Network process đọc hộ cho mọi tab rồi gửi lại qua IPC. Tin nhắn IPC không tức thời, file càng to truyền càng lâu, và gzip/brotli không giúp gì ở đây.

Dấu hiệu: trong tab Network, một script lớn dù lấy từ cache vẫn có thời gian Content Download đáng kể. Đó chính là chi phí IPC.

03 · ĐỌC ĐĨA

Đĩa không phải lúc nào cũng nhanh

Nhiều người dùng vẫn chạy ổ cứng cơ, hoặc ổ đang bận (quét virus, gần đầy). Đọc nhiều file cache cùng lúc còn làm nghẽn luồng và event loop của Network process, sinh thêm thời gian xếp hàng. File lớn đọc lâu hơn, và nén văn bản cũng không giảm được chi phí này.

04 · PARSE & COMPILE

Văn bản phải thành lệnh máy chạy được

File đã về tới tiến trình của trang, nhưng JS vẫn chỉ là văn bản. Engine phải:

  1. Parse văn bản thành cây cú pháp trừu tượng (AST).
  2. Duyệt AST và sinh bytecode.
  3. Nạp bytecode lên luồng và bắt đầu chạy.

Tất cả tốn CPU, và file càng lớn càng lâu. Trình duyệt có tối ưu như parse/compile trễ, hay đẩy một phần sang luồng phụ (streaming), nhưng chi phí vẫn đáng kể. Trong trace bạn sẽ thấy các khối parse/compile ở luồng phụ và khối Compile Script trên main thread.

Bytecode cache có cứu được không?

Trình duyệt có cache bytecode theo heuristic, là tối ưu mạnh nhưng không xoá hết chi phí. Bytecode thường lớn hơn nhiều so với mã nguồn, nên đọc nó từ đĩa lên luồng cũng tốn thời gian; nguồn lớn thì bytecode càng lớn. Profiler có hiện kích thước cache compile. Các cách cache cũng khác nhau: trong Chromium, script cache trong sự kiện install của Service Worker được sinh bộ lệnh đầy đủ hơn, giảm việc sinh code lúc chạy, nhưng file to hơn nên lúc nạp lại tốn hơn.

05 · THỰC THI

Rồi mới tới chạy code, và vẫn còn compile

Chi phí chạy không phụ thuộc kích thước file mà phụ thuộc khối lượng và hiệu quả của đường code: logic nghiệp vụ, thao tác DOM qua React… Nhìn chung, dựng DOM bằng JS chậm hơn nhiều so với HTML tĩnh, và JS chạy rất kém trên máy cấu hình thấp. Dùng mark/measure (bài 12) để đo các đường code trên đường găng.

Compile trễ

Để khởi động nhanh, engine chỉ compile phần ít nhất cần để chạy. Khi script chạy tới những nhánh trước đó bị bỏ qua, engine phải compile chúng ngay lúc đó, kể cả khi script lấy từ cache. Trong profiler, các khối compile nhỏ này xen kẽ với JS đang chạy, cộng thêm vào đường găng.

06 · KẾT LUẬN

Cache giải quyết mạng, không giải quyết CPU

  • Liên tục đo và profile để thấy chi phí CPU của JS.
  • Ưu tiên HTML và CSS tĩnh thay cho dựng giao diện bằng JS lúc chạy, khi có thể.
  • Cắt mạnh kích thước bundle để giảm IPC, đọc đĩa, parse, compile.
  • Tối ưu hiệu quả của các đường code bắt buộc phải chạy, để trình duyệt kịp vẽ frame.
