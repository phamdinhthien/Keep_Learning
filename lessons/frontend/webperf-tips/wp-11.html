Từ flamegraph lần về đúng dòng code chậm

Thấy một vùng đáng ngờ trên flamegraph rồi, làm sao biết nó là hàm nào trong code đã minify?

Bài gốc: “Identifying the source of slow codepaths in the Chromium Profiler” ↗
00 · MỤC TIÊU

Flamegraph chỉ ra “ở đâu”, Sources cho biết “là gì”

Flamegraph giúp thấy cái gì đang ngốn CPU trong task. Nhưng để sửa, bạn phải tìm ra đoạn code tương ứng trong ứng dụng. Bài này là quy trình làm việc đó. Cần có trace (bài 05) và biết đọc flamegraph (bài 08–09).

01 · BẢY BƯỚC

Quy trình khoanh vùng

  1. Tìm vùng đáng ngờ. Dùng kiến thức về hình dạng flamegraph. Ví dụ thấy một loạt gai hẹp lặp lại dày đặc: một thao tác tần suất cao, đáng để tối ưu.
  2. Zoom vào. Chỉnh vùng chọn cho tới khi thấy rõ một gai.
  3. Chọn một khối. Bắt đầu từ ngọn gai. Bản production đã minify nên tên hàm chỉ là kiểu o; click vào nó để Summary hiện chi tiết.
  4. Mở script. Cuối Summary có link màu xanh dạng app-bundle-8c1….js:27165. Click để nhảy sang tab Sources đúng vị trí hàm.
  5. Pretty-print. Sources hiện code minify một dòng dài. Bấm nút { } nhỏ ở góc dưới trái để định dạng lại.
  6. Đọc code. Giờ đã xem được hàm o làm gì. Nếu là code của đội bạn, bản đã format thường đủ quen để nhận ra trong codebase. Nếu không quen, có thể là thư viện được bundle kèm; đi dọc call stack để biết nó được gọi khi nào.
  7. Tìm chỗ kém hiệu quả (xem ví dụ bên dưới).
Lưu ý với trace importBước 4 chỉ hoạt động khi bạn tự ghi trace trên chính trình duyệt đó. Với trace được import từ file, click link sẽ không đưa tới code, và Chromium cũng không báo gì.

02 · VÍ DỤ PHÁT HIỆN

Những gì thường lộ ra khi đọc code

Giả sử hàm minify o bị gọi rất nhiều lần, và sau khi format nó trông như sau (ví dụ minh hoạ):

function o(html) {
  const doc = new DOMParser().parseFromString(html, 'text/html'); // ① mỗi lần gọi parse lại HTML
  return e(doc.body.textContent);
}
function e(t) { return t.split('\n').map(l => r(n(l))); }
function n(l) { return l.split(' ').reduce((a, w) => a + w.trim(), ''); }  // ② reduce + trim chuỗi
function r(s) { let x = ''; for (let i = 0; i < s.length; i++) x += s[i]; return x; } // ③ vòng for nối chuỗi
  • ① DOMParser.parseFromString là API trình duyệt, thường chậm nếu gọi với tần suất cao. Mỗi lần tạo một DOMParser mới để parse lại là dấu hiệu đáng ngờ (bài 32 phân tích sâu trường hợp này).
  • ② và ③: chuỗi gọi o → e → (anonymous) → r, n. Chọn từng khối r, n trong flamegraph rồi mở Sources như bước 4. Mỗi hàm đều làm việc đồng bộ (vòng for, reduce với trim). Riêng lẻ thì nhẹ, nhưng bị gọi hàng nghìn lần thì cộng lại thành điểm nghẽn của task.
▣Ảnh/ví dụ gốc ảnh parseFromString và các hàm r, n trong flamegraph và Sources↗
  • Flamegraph → chọn khối → link script trong Summary → Sources → { } pretty-print.
  • Tìm việc đồng bộ bị gọi với tần suất cao, API trình duyệt đắt tiền, vòng lặp và thao tác chuỗi.
  • Ánh xạ đoạn code đã format về source của bạn rồi tối ưu.
