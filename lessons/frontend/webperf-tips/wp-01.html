Event Loop: nền móng của hiệu năng frontend

Main thread, task, task queue, render steps và vòng lặp điều phối tất cả: hiểu cái này thì mọi bài sau đều dễ.

Bài gốc: “Event Loop Fundamentals” ↗
00 · VÌ SAO HỌC TRƯỚC

Khái niệm quan trọng nhất của hiệu năng frontend

Nếu chỉ được hiểu một thứ về hiệu năng phía trình duyệt, hãy hiểu Event Loop. Cách nó vận hành quyết định ứng dụng web của bạn phản hồi nhanh hay chậm khi đang chạy. Nhưng trước khi nói về Event Loop, cần nắm vài khái niệm nền.

01 · MAIN THREAD

Một luồng chính duy nhất cho code của bạn

Khi người dùng mở ứng dụng web, trình duyệt cấp cho trang một luồng gọi là Main Thread. Phần lớn hoạt động lúc chạy của ứng dụng diễn ra trên đúng luồng này, và mỗi hoạt động được gói trong một đơn vị gọi là Task.

02 · TASK

Task: đơn vị công việc trên main thread

Task là một đơn vị thực thi chạy trên main thread. Vài ví dụ thường gặp:

Parse HTML / CSSXử lý input: click, gõ phímCompile + chạy JavaScriptNhận dữ liệu mạngRender steps: Style, Layout, Paint
Các loại task điển hình

Một số task bắt buộc chạy trên main thread. Ví dụ mọi thứ cần đụng trực tiếp vào DOM (document), vì DOM không an toàn khi truy cập từ nhiều luồng. Nghĩa là hầu hết code liên quan tới UI phải chạy ở đây.

Hai quy tắc then chốt:

  1. Mỗi lúc chỉ một task chạy trên main thread.
  2. Task phải chạy hết rồi task khác mới được chạy. Trình duyệt không có cách nào chạy “dở một nửa” task rồi chuyển sang việc khác.

03 · TASK QUEUE

Hàng đợi chứa các task chưa tới lượt

Vì không thể chạy nhiều task cùng lúc trên main thread, những task chưa chạy được giữ trong một cấu trúc dữ liệu tên là Task Queue. Trong lúc ứng dụng chạy, trình duyệt liên tục đẩy task vào hàng đợi này, và lấy task ra khi main thread rảnh.

Không phải FIFOTask Queue không đơn thuần “vào trước ra trước”. Phần lớn trình duyệt có logic lập lịch dựa trên heuristic, ưu tiên một số loại task hơn các loại khác.
04 · RENDER STEPS & FRAME

Task đặc biệt biến DOM thành pixel

Render Steps là task chịu trách nhiệm chuyển DOM và CSS hiện tại thành pixel trên màn hình. Kết quả sau khi render steps chạy xong được gọi là một Frame.

Khi bạn sửa DOM hoặc CSS, trình duyệt được báo là cần tạo frame mới. Lúc đó, thay vì lấy task tiếp theo từ task queue, nó sẽ chen task render steps vào:

Render steps xen giữa các task thường và tạo ra một frame

Render steps thường gồm 3 bước chính:

  • Style: gán màu, font và các thuộc tính CSS khác cho từng phần tử hiển thị.
  • Layout: tính toạ độ, kích thước chính xác cho từng phần tử.
  • Paint: ra lệnh cho thư viện đồ hoạ vẽ các phần tử đã có style và vị trí.

Chi tiết từng bước nằm ở bài 02 (Rendering Pipeline).

05 · EVENT LOOP

Người điều phối: một vòng lặp vô hạn

Event Loop là thứ gắn kết tất cả các khái niệm trên. Về bản chất nó là một vòng lặp chạy mãi, mỗi vòng làm một trong hai việc:

  • Lấy một task có sẵn từ task queue, đặt lên main thread và chạy tới khi xong.
  • Thỉnh thoảng chọn task render steps thay vì đọc hàng đợi, để tạo frame.

Viết lại bằng giả mã cho dễ hình dung:

for (;;) {
  let task;
  // trình duyệt báo cho event loop biết đã tới lúc vẽ frame chưa
  if (timeToRenderFrame()) {
    task = renderStepsTask();       // Style → Layout → Paint
  } else {
    task = taskQueue.pickNext();     // task thường tiếp theo
  }
  runToCompletion(task);          // luôn chạy hết, không ngắt giữa chừng
}
Điểm mấu chốtỞ mỗi vòng, trình duyệt hoặc chạy một task, hoặc tạo một frame, không làm cả hai cùng lúc (có vài ngoại lệ hiếm, bài gốc không bàn). Thứ nào được chọn thì chạy tới khi xong.

Hệ quả: task càng ngắn thì trình duyệt càng sớm có cơ hội chạy render steps và đưa frame mới tới người dùng. Đây là lý do cần tránh Long Task (bài 04).

Event Loop thật được viết bằng C++ trong trình duyệt; giả mã JavaScript ở trên chỉ để minh hoạ.

06 · NON-BLOCKING

Bất đồng bộ cũng chỉ là task được xếp hàng sau

Event Loop không bao giờ tự dừng hay chặn main thread: nó cứ lặp, chạy task và tạo frame. Vậy những việc bất đồng bộ như gọi mạng hay hẹn giờ thì sao?

Mỗi API bất đồng bộ của trình duyệt đều được biểu diễn thành task tương thích với mô hình event loop:

  • Tải dữ liệu bằng fetch hoặc XMLHttpRequest
  • Phản hồi sự kiện qua addEventListener(...)
  • Hẹn giờ bằng setTimeout, setInterval

Ví dụ setTimeout(cb, 500) không chặn main thread 500 ms. Nó chỉ dặn trình duyệt: “sau 500 ms, hãy xếp một task chạy cb vào task queue”.

07 · VÍ DỤ: TIMER

Đi qua từng bước với một bộ đếm

Ghép mọi thứ lại bằng một script nhỏ: cứ 500 ms cập nhật một dòng chữ trên trang.

let ticks = 0;
const label = document.querySelector('#ticks');

// Mỗi 500 ms trình duyệt xếp một task vào task queue
setInterval(() => {
  // đoạn này chạy bên trong một task
  ticks += 1;
  label.textContent = `Đã chạy ${ticks} lần`;   // sửa DOM → cần frame mới
}, 500);

Diễn biến trên main thread:

  1. Sau khi script chạy xong: main thread rảnh, task queue trống. Trong 500 ms chờ, luồng không làm gì nhưng vẫn sẵn sàng xử lý click, gõ phím hay task khác nếu có.
  2. Hết 500 ms: trình duyệt xếp một task chạy callback vào task queue.
  3. Event loop thấy có task, main thread đang rảnh, nên lấy nó ra và chạy. Callback sửa DOM.
  4. Vì DOM đã đổi, event loop chạy render steps và tạo frame. Dòng chữ mới hiện trên màn hình.

08 · TÓM TẮT

Ghi nhớ

  • Gần như mọi việc ứng dụng web làm đều quy về task được xếp vào task queue rồi chạy trên main thread nhờ event loop.
  • Mỗi lúc chỉ một task chạy, và task luôn chạy hết.
  • Thay đổi cần hiển thị phụ thuộc vào việc event loop chen render steps giữa các task để tạo frame.
  • Tối ưu hiệu năng phần lớn là tối ưu khi nào và bao lâu các task của bạn chạy.
