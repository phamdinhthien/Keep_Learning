Bốn cách né CORS preflight

Gọi API khác origin có thể tốn hai vòng đi–về thay vì một. Cache preflight, iframe cùng origin, proxy, hoặc biến nó thành simple request.

Bài gốc: “Techniques for bypassing CORS Preflight Requests to improve performance” ↗
00 · CORS PREFLIGHT

Một request “vô hình” chen vào trước

CORS (Cross-Origin Resource Sharing) cho phép ứng dụng web giao tiếp an toàn với server khác origin. Thường nó hoạt động thế này: trình duyệt tự gửi một request preflight bằng method OPTIONS tới origin đích; server trả lời origin của bạn có được phép gọi không. Được phép thì trình duyệt mới gửi request thật (GET, POST…). Code JS không hề viết request OPTIONS; trình duyệt tự làm.

shop.vn → api
OPTIONS (preflight)
GET /api/items
Hai vòng đi–về cho một lần lấy dữ liệu: chính là mẫu nối đuôi ở bài 20

Trên mạng chậm hoặc chập chờn, nếu dữ liệu này nằm trên đường găng để vẽ frame tiếp theo, vòng thừa đó là điểm nghẽn. (Request thuộc loại simple request thì không cần preflight, xem chiến lược 4.)

01 · CHIẾN LƯỢC 1

Cache kết quả preflight

Server trả kèm header Access-Control-Max-Age (đơn vị giây) trong response của OPTIONS. Các lần sau với cùng method và URL, trình duyệt dùng lại kết quả và bỏ qua vòng preflight.

Access-Control-Max-Age: 7200   # 2 giờ

Lưu ý

  • Trình duyệt giới hạn thời gian tối đa: Chromium chỉ nhận tối đa 2 giờ, Firefox tối đa 1 ngày. Đặt số lớn hơn cũng không giúp tăng tỉ lệ cache hit.
  • Khoá cache là method + URL đầy đủ. Gọi cùng endpoint nhưng query string thay đổi thì không dùng lại được: /sync?cursor=abc được cache, nhưng /sync?cursor=def lại phải preflight. Với API mà mỗi lần gọi một tham số khác, cách này gần như vô dụng.

02 · CHIẾN LƯỢC 2

Gửi request qua iframe cùng origin với API

CORS chỉ áp dụng khi bên gọi khác origin với server. Nếu backend phục vụ một trang HTML nhỏ, ta nhúng trang đó bằng <iframe>; iframe gửi request giúp (cùng origin nên không preflight) và trả kết quả qua postMessage.

<!-- trên https://shop.vn -->
<iframe id="api-bridge" src="https://api.shop.vn/bridge.html" hidden></iframe>
<script>
  const bridge = document.getElementById('api-bridge');
  window.addEventListener('message', (e) => {
    if (e.origin !== 'https://api.shop.vn') return;   // luôn kiểm tra nguồn
    resolvePending(e.data);
  });
  function callApi(req) {
    bridge.contentWindow.postMessage(req, 'https://api.shop.vn');
  }
</script>
<!-- https://api.shop.vn/bridge.html -->
<script>
  window.addEventListener('message', async (e) => {
    if (e.origin !== 'https://shop.vn') return;
    const data = await fetch(e.data.url).then(r => r.json()); // cùng origin: không preflight
    e.source.postMessage(data, e.origin);
  });
</script>

Cái giá

  • Backend phải phục vụ thêm trang HTML. Không kiểm soát backend thì khó hoặc không làm được.
  • Phải đợi iframe tải xong mới gọi được API, nên bản thân iframe có thể thành điểm nghẽn. Cache mạnh tay, đặt trên CDN/edge.
  • Tốn tài nguyên trình duyệt: iframe có thể được cấp process riêng (bài 29). Mỗi lần gọi đi qua nhiều chặng IPC: trang → iframe → Network process → iframe → trang. Trên máy đang tải nặng, chi phí này có thể lớn hơn chính CORS. Phải đo.
  • Chỉ đáng khi gọi nhiều lần trong một phiên: trả chi phí dựng iframe một lần, lời ở mọi request sau. Gọi một lần thì không bõ.

03 · CHIẾN LƯỢC 3

Proxy để API “trông như” cùng origin

Cũng là căn chỉnh origin, nhưng dùng HTTP proxy: ví dụ https://shop.vn/api/* được chuyển tiếp tới https://api.shop.vn/*. Với trình duyệt, request là cùng origin nên không cần preflight.

Có nhiều cách dựng: dịch vụ của nhà cung cấp cloud (Azure Front Door, AWS CloudFront…), cho backend đang phục vụ trang làm proxy luôn, hoặc nếu bạn sở hữu API thì cấu hình DNS để API nằm cùng origin với ứng dụng.

Cái giá: thêm một chặng mạng trên đường tới service. Luôn đo để chắc rằng người dùng thật nhận được lợi ích.

# ví dụ nginx trên shop.vn
location /api/ {
  proxy_pass https://api.shop.vn/;
}
04 · CHIẾN LƯỢC 4

Biến thành simple request

Theo đặc tả CORS, một số request không cần preflight, gọi là simple request. Đại ý: method là GET, HEAD hoặc POST; chỉ dùng các header “an toàn” (như Accept, Content-Language); và nếu có Content-Type thì phải là text/plain, multipart/form-data hoặc application/x-www-form-urlencoded.

Khó ở đâuSimple request không cho header tuỳ biến, nên mẫu Authorization: Bearer <token> quen thuộc đã đủ để kích hoạt preflight. Muốn né thì phải sửa backend/gateway để nhận thông tin theo cách khác.

Ví dụ request cần preflight:

GET https://api.shop.vn/items
Authorization: Bearer <token>
X-Client-Version: 3.2

Cách A: đưa metadata vào body của POST

POST https://api.shop.vn/items
Content-Type: text/plain

{ "method": "GET", "authorization": "Bearer <token>", "clientVersion": "3.2" }

Không còn header tuỳ biến nên trình duyệt coi là simple request. Đổi lại backend phải hiểu cú pháp riêng này (một POST nhưng thực chất là GET), tăng độ phức tạp và làm mờ ngữ nghĩa REST.

Cách B: đưa metadata vào query string

GET https://api.shop.vn/items?clientVersion=3.2

Đơn giản hơn cách A. Nhưng không nên đặt access token (JWT) vào query string vì lý do bảo mật: URL dễ bị ghi vào log, lịch sử, header Referer.

▣Ảnh/ví dụ gốc sơ đồ trạng thái quyết định khi nào cần preflight↗
  • Preflight = thêm một vòng đi–về cho mỗi request khác origin không “simple”.
  • Max-Age: dễ nhất, nhưng bị giới hạn 2 giờ (Chromium) và khoá theo URL.
  • Iframe hoặc proxy: căn chỉnh origin, có chi phí riêng.
  • Simple request: không header tuỳ biến; đừng đưa token lên URL.
  • Áp dụng cách nào cũng phải đo lại với người dùng thật.
