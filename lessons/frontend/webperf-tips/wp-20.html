Request nối đuôi nhau: anti-pattern cần tránh

Mỗi request phải đợi request trước mới gửi được: mỗi mắt xích cộng thêm trọn một vòng đi–về vào thời gian người dùng chờ.

00 · MẪU HÌNH

Request sau phụ thuộc kết quả request trước

const user = await fetch('/api/me').then(r => r.json());
// chỉ gửi được khi đã có user.id
const orders = await fetch(`/api/orders?user=${user.id}`).then(r => r.json());
renderOrders(orders);

Request thứ hai chỉ bắt đầu khi request thứ nhất xong hẳn; UI chờ cả hai

Các tên gọi sequential, serial, pipelined request pattern được dùng thay nhau. Vấn đề này không chỉ có ở client, nhưng bài này nhìn từ phía ứng dụng web.

01 · BIẾN THỂ KHÓ THẤY

Ba dạng hay gặp trong production

① Lấy token rồi mới gọi API

const token = await getAccessToken();          // vòng 1
const res = await fetch('https://api.shop.vn/cart', {   // vòng 2
  headers: { Authorization: `Bearer ${token}` },
});
renderCart(await res.json());

② CORS preflight

Trang ở https://shop.vn gọi https://api.shop.vn kèm header tuỳ biến như X-Session-Key: trình duyệt phải gửi một request OPTIONS trước, xong mới gửi request thật. Một vòng đi–về bị chèn thêm mà code không hề viết (bài 21).

③ Tải bundle rồi mới tải dữ liệu

<!-- index.html -->
<script src="https://cdn.shop.vn/app.js"></script>

// app.js: chỉ khi file này tải, parse, compile, chạy xong mới gọi API
fetch('https://api.shop.vn/products').then(renderProducts);

02 · VẤN ĐỀ

Mạng là một ống hút mỏng và chập chờn

Mọi thiết kế API hay luồng gọi buộc client và server “qua lại” tuần tự đều tạo ra điểm nghẽn do mạng. Với kịch bản quan trọng của người dùng, mỗi phụ thuộc mạng cần được soi rất kỹ.

Mô hình tư duy nên dùng: kết nối giữa người dùng và datacenter là một ống hút mỏng, không đáng tin. Mục tiêu là hút qua nó càng ít lượt nối tiếp càng tốt.

Máy bạn khác máy người dùng

Trên máy dev với mạng công ty, các request nhanh nên chuỗi nối đuôi trông vô hại. Người dùng trên 4G yếu có thể chịu độ trễ gấp nhiều lần. Hãy throttle khi test (bài 13), và gửi Resource Timing (bài 18) về telemetry để thấy số liệu thật.

Mỗi mắt xích cộng thêm một vòng đi–về

Một chuỗi điển hình trên đường găng:

  1. Tải index.html.
  2. Tải app.js.
  3. Gọi API khác origin: trình duyệt gửi preflight OPTIONS.
  4. Preflight xong mới gọi API thật lấy JSON, rồi mới hiện UI.

Bốn vòng đi–về nối tiếp; mỗi vòng cộng trọn thời gian của nó vào lúc người dùng thấy giao diện.

03 · GIẢM THIỂU

Không phải lúc nào cũng xoá được, nhưng rút ngắn được

  • Cache các phụ thuộc mạng cho lần truy cập sau (ví dụ token, cấu hình).
  • Gom việc về phía datacenter: để server gọi các server khác (gần nhau, mạng tốt) thay vì client gọi lần lượt.
  • Proxy ở điểm gần người dùng (point of presence, edge) để kết nối ổn định hơn.
  • Chạy song song những request không thật sự phụ thuộc nhau.
  • Né CORS preflight cho request khác origin (bài 21).
// thay vì await lần lượt, gửi cùng lúc những gì độc lập
const [products, banners] = await Promise.all([
  fetch('/api/products').then(r => r.json()),
  fetch('/api/banners').then(r => r.json()),
]);
